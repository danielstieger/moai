## Key question 1: SAP RAP Behavior Definitions – what is declared, how it runs, phases, draft, locking, numbering, EML

### Takeaway
RAP splits a business object into a CDS data model, a *behavior definition* (BDL, purely declarative) and a *behavior implementation* (ABAP handler/saver classes whose method signatures are derived from the BDL). The BDL declares operations, actions, functions, determinations (on modify / on save), validations (on save), feature control, authorization, locking, ETags, numbering, draft handling, side effects and events; the runtime enforces a strict two-phase transaction (interaction phase on a transactional buffer, then an early and late save sequence) and derives Fiori UI behaviour from it.

### Cited Findings

**BDL header and implementation types [BIG: managed vs. unmanaged persistence]**
- Managed: `managed implementation in class zbp_demo_abap_rap_entity unique;` is for greenfield work "with CRUD handled by the framework"; unmanaged: `unmanaged implementation in class zbp_demo_abap_rap_entity_u unique;` is for brownfield, "where the provider implements the buffer and all operations". `strict(2);` is the recommended strict mode and "enables extra syntax checks without ABP code". `with draft;` enables draft handling; `with collaborative draft;` allows multiple users to edit the same draft. `with additional save` adds steps to the default save; `with unmanaged save` replaces it and then no `persistent table` may be specified; options `and cleanup`, `with full data`. — [SAP cheat sheet 36: RAP Behavior Definition Language](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- `define behavior for some_entity alias root` — the root entity is required; `persistent table some_table` is for managed BOs only; `draft table some_draft_table` "must mirror the CDS fields and include a client field", late numbering needs a `DRAFTUUID` key and it must include `"%admin": include sych_bdl_draft_admin_inc;`. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- `mapping for demo_dbtab_root { KeyFieldRoot = key_field; DataFieldRoot = data_field; }` is "Required when database field names differ from CDS element names. Otherwise a syntax warning appears"; variants `control` and `corresponding`. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Managed scenario per SAP Press: "a ready-made implementation of the business object provided by the ABAP RESTful application programming model" supplying CRUD and buffer handling, with hooks into the save sequence; unmanaged lets you "integrat[e] the API of an existing application and wrapping it with RAP resources". — [SAP Press, Exploring the architecture of RAP](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model)
- Practitioner view: managed "let[s] the framework handle CRUD operations, draft persistence, locking, and change documents automatically", unmanaged means "you write every single save, lock, and buffer operation yourself"; a hybrid (managed root, unmanaged children) is suggested for complex objects. — [aixsap, Managed vs Unmanaged Part 2](https://aixsap.com/abap-rap-behavior-definitions-deep-dive-managed-vs-unmanaged-scenarios-in-sap-s-4hana-part-2/) (practitioner blog)
- Unmanaged cost: "create, update, delete, and save methods all need explicit implementation"; teams that "default to unmanaged out of familiarity … then spend weeks reimplementing what the framework would have given them for free". — [aixsap, Architect's guide](https://aixsap.com/abap-restful-application-programming-model-rap-a-senior-architects-practical-guide-to-building-modern-sap-applications/) (practitioner blog, search excerpt)

**Standard operations and field characteristics [SMALL: options on entity/field]**
- "Unlike reading operations, modifying operations are not enabled by default"; "read operations are always implicitly enabled for each entity listed in a BDEF". Example: `create; update; delete; action some_act;`. — [SAP cheat sheet 08: EML/ABAP for RAP](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- Operation options: `create ( features : global, precheck, authorization : none );`, `create { default function GetDefaultsForCreate; }`, `update ( features : instance );`, `delete ( authorization : update );`. "features : instance applies to update and delete, not create"; "Deleting a managed parent also deletes its composition children." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Field characteristics (verbatim): `field ( readonly ) field_a, field_b, field_c; field ( readonly : create ) field_d; field ( readonly : update ) field_e; field ( mandatory ) field_f; field ( mandatory : create ) field_g; field ( mandatory : update ) field_h; field ( suppress ) field_i; field ( features : instance ) field_j;` — combinable, e.g. `field ( mandatory : create, readonly : update ) field_k;`. `suppress` removes the field from derived types and APIs; `features : instance` requires a `FOR INSTANCE FEATURES` handler. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)

**Actions and functions [SMALL-to-BIG: typed operations with cardinality/result/factory semantics]**
- Action forms: `action act1; internal action act2; static action act3; repeatable action act4; action ( features : instance ) act6; action ( precheck ) act7; action ( authorization : none ) act11; action ( lock : none ) act12; action act13 parameter SOME_ENTITY; action act14 parameter SOME_ENTITY result [1] $self; action act16 deep result selective [1] SOME_ENTITY; factory action act19 [1]; default factory action act20 [1]; save(...) action act21;`. "Factory actions cannot have output parameters"; cardinalities `[1]`, `[0..1]`, `[0..*]`, `[1..*]`; `result selective` requires `REQUEST` in the handler. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Functions: `function func1 result [0..*] $self; static function func2 result [1] SOME_ENTITY;` — "A result parameter is mandatory. Functions do not lock or modify data." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Handler signature: `METHODS some_action FOR MODIFY IMPORTING keys FOR ACTION bdef~some_action.` Actions are triggered via EML `EXECUTE multiply_by_2 FROM VALUE #( ( %cid_ref = 'cid_x2' ) ( key_field = 1 ) )`. — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- Action parameters are typed with CDS abstract entities (same mechanism as event parameters: "you have to use a CDS abstract entity"). — [SAP Learning, Working with Event Parameters](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/working-with-event-parameters) (search excerpt)

**Determinations [BIG: declared derived-value rules with trigger operations and phase]**
- Syntax: `determination det1 on save { create; } determination det4 on modify { create; } determination det5 on modify { field some_field; }`. "`on modify` runs immediately in the buffer"; "`on save` runs during the save sequence"; "The execution order among determinations is arbitrary." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Tutorial example: `determination setStatusToOpen on modify { create; }` — `on modify` is the determination time, `{ create; }` restricts the trigger to creation; the handler carries `FOR DETERMINE ON MODIFY`, imports `keys`, and has an implicit `CHANGING reported`. Implementation reads and updates via EML `IN LOCAL MODE`, which is used "to exclude feature controls and authorization checks" and "can currently only be used for the business object's own implementation". — [SAP tutorial RAP100 determination](https://developers.sap.com/tutorials/abap-environment-rap100-determination.html)
- Timing: "A determination declared on modify runs immediately after the operation that triggers it"; it may fire several times before save (a field changed three times fires it three times), whereas "A determination declared on save runs there, exactly once" because the framework aggregates operations on an instance into one effective operation; on-save determinations run in the FINALIZE phase. Decision model: use on modify when other fields/determinations/validations in the same transaction need the value, or when the user should see it while working; "The deciding factor is dependency, not cost." Pitfall: "A field used as a trigger condition fires whenever that field changes value" — react to a specific status inside the implementation. — [SAP Press, On modify or save: a decision model for RAP determinations](https://blog.sap-press.com/on-modify-or-save-a-practical-decision-model-for-rap-determinations)
- Saver phases in managed BOs: `finalize` "In managed scenarios, determinations with ON SAVE run here"; `check_before_save` "validations with ON SAVE run here". — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- Criticism: developers "put too much logic in determinations, making them behave like mini workflows"; advice "Keep determinations focused on field value derivation. Complex orchestration belongs in actions." Named failure modes: "Validations that actually fire at the right time. Determinations that don't cause infinite loops. Side effects that don't corrupt your transactional buffer." — [dev.to, ABAP RAP Deep Dive Part 2](https://dev.to/oktayates/abap-rap-deep-dive-part-2-implementing-business-logic-validations-and-determinations-in-sap-1mi9); [aixsap ?p=873](https://aixsap.com/?p=873) (practitioner blogs, search excerpts)

**Validations [BIG: declared save-phase checks with trigger conditions, rejecting the whole buffer]**
- Syntax: `validation val1 on save { create; update; } validation val2 on save { delete; } validation val3 on save { field some_field; }`. "Triggers are create, update (only together with create), delete, and field changes." "A failed validation rejects the entire buffer, not only the inconsistent instances." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Tutorial: `validation validateCustomer on save { create; field CustomerID; }`, `validation validateDates on save { create; field BeginDate, EndDate; }`; draft: `draft determine action Prepare { validation validateCustomer; validation validateDates; }`. Handler `FOR VALIDATE ON SAVE` imports `keys`, changing `failed`/`reported`; reject with `APPEND VALUE #( %tky = travel-%tky ) TO failed-travel.`; report with `%tky`, `%state_area` (makes the message a state message stored with the draft), `%msg` (`NEW /dmo/cm_flight_messages(...)` with severity), `%element-CustomerID = if_abap_behv=>mk-on` to flag the field in the UI. "Validations … always execute during save"; "Frontend validations can be bypassed, for example through EML APIs, so backend validations are required." — [SAP tutorial RAP100 validation](https://developers.sap.com/tutorials/abap-environment-rap100-validation.html)
- Response structures: `MAPPED`, `FAILED`, `REPORTED` are "containers for information passed to the consumer". — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)

**Determine actions and draft determine action Prepare [SMALL: grouping of on-save rules for explicit invocation]**
- `determine action det_act { determination det1; determination ( always ) det2; validation val; }` — "Only `on save` items can be assigned", "`always` forces execution regardless of triggers", "Determinations run before validations." `draft determine action Prepare` "runs `on save` determinations and validations and may be empty." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)

**Feature control (static and dynamic) [BIG: instance-state-derived permitted operations/field modes]**
- Dynamic feature control is declared by adding `( features : instance )` to operations/actions, e.g. `update ( features : instance ); delete ( features : instance ); action ( features : instance ) deductDiscount parameter /dmo/a_travel_discount result [1] $self; draft action ( features : instance ) Edit;`. The handler `FOR INSTANCE FEATURES` imports `keys` and `requested_features`, changing `result/failed/reported`; e.g. `%features-%update = COND #( WHEN travel-OverallStatus = travel_status-accepted THEN if_abap_behv=>fc-o-disabled ELSE if_abap_behv=>fc-o-enabled )`. "The logic runs in the backend. The SAP Fiori elements preview shows the result as enabled or disabled buttons." — [SAP tutorial RAP100 dynamic feature control](https://developers.sap.com/tutorials/abap-environment-rap100-dynamic-feature-control.html)
- Static feature control = the `readonly`/`mandatory` field characteristics listed above. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)

**Authorization [SMALL-to-BIG: declared authorization master with global/instance checks]**
- `authorization master ( global )`, `( instance )`, `( global, instance )`, `( none )`, `authorization dependent by _Assoc`; "The root must declare `authorization master`"; global and instance checks require handlers `FOR GLOBAL AUTHORIZATION` and `FOR INSTANCE AUTHORIZATION`; per-action `authorization : global/instance` replaces the master's check. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- `IN LOCAL MODE` bypasses authorization and feature control; `get_current_context` exposes `for_permissions` and `privileged`. — [SAP Press architecture article](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model); [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)

**Locking and ETags [SMALL: options; note `total etag` over a composition tree]**
- Pessimistic: `lock master` and `lock dependent by _Assoc`; "The lock master must be the root." Optimistic: `etag master some_etag_field`, `etag dependent by _Assoc`, `total etag some_total_etag_field`; managed BOs use `@Semantics.systemDateTime.localInstanceLastChangedAt: true` for the ETag field and `@Semantics.systemDateTime.lastChangedAt: true` for the total ETag; field types `utclong`, `timestamp`, `timestampl`. "`total etag` applies only to draft-enabled BOs"; "Unmanaged RAP BOs need custom ETag handling in the save sequence." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- An ETag "is used to manage data concurrency, preventing multiple users from overwriting the same record simultaneously, similar to the functionality of lock objects"; typically based on a `last_changed_at` timestamp. — [SAP Community, ETag in RAP](https://community.sap.com/t5/application-development-blog-posts/etag-in-rap/ba-p/13982291) (search excerpt)
- Actions may opt out: `action ( lock : none ) act12;`; functions "do not lock or modify data". — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)

**Numbering [SMALL: option on entity; late numbering interacts with save sequence]**
- "Default is external numbering." `early numbering` assigns keys during the interaction phase, implemented in `FOR NUMBERING`; `late numbering` assigns keys during the save sequence in saver method `adjust_numbers`; managed internal early numbering uses `numbering:managed` with a 16-byte UUID key. "Uniqueness checks for numbering are the developer's responsibility where the framework does not perform them." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Late numbering mechanics: before `adjust_numbers` the framework copies preliminary `%key` values into `%tmp`, `%pid` stays, `%pre` (= `%pid` + `%tmp`) must be unique and mapped to final keys in `mapped`; key conversion in the interaction phase: `COMMIT ENTITIES BEGIN. CONVERT KEY OF some_bo FROM ...-%pid TO DATA(some_key). COMMIT ENTITIES END.` — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- Late numbering means the framework assigns key values "once the save sequence starts, after the point of no return has passed". — [SAP tutorial RAP100 early numbering](https://developers.sap.com/tutorials/abap-environment-rap100-early-numbering.html) (search excerpt)

**Transaction model: interaction phase, early/late save, point of no return [BIG: phased unit of work with fixed hook points and phase-specific restrictions]**
- Saver methods: `finalize` ("For final calculations and data modifications involving all BOs in the current RAP transaction"), `check_before_save` ("Checks the consistency of the transactional buffer before the save method saves data"), `adjust_numbers` ("Preliminary IDs are mapped to final keys. Only for late numbering."), `save` ("Saves the current state of the transactional buffer to the database"), `cleanup`/`cleanup_finalize` ("Clear the transactional buffer"; `cleanup_finalize` is called if an earlier saver method fails so `finalize` changes can be rolled back). "If there are errors in the early save phase, `sy-subrc` returns the value 4 after `COMMIT ENTITIES` statements." "Unlike the early save phase, you cannot return to the interaction phase when you reach the late save phase." — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- Phase restrictions (strict mode): "Database modifications are allowed only in the late save phase … because the data being processed is always potentially inconsistent"; Dynpro and transaction processing are not allowed in behavior implementations; raising a RAP business event is recommended only in `save`/`save_modified`; `COMMIT WORK`/`ROLLBACK WORK` are not allowed in some RAP contexts; `CL_ABAP_BEHV_AUX=>GET_CURRENT_PHASE` reports the current phase. — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- "The subsequent save sequence is triggered by a commit"; "The state of the transaction buffer isn't kept across multiple requests, as this would violate a key REST principle." — [SAP Press architecture article](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model)
- Practitioner warning: "calling commit yourself will break draft handling and leave your business object in an inconsistent state"; a legacy-BAPI wrapping blog lists raising business events or calling bgPF in the interaction or early-save phase as patterns that "cause runtime errors under strict mode". — [aixsap ?p=836](https://aixsap.com/?p=836); [SAP Community, Cloud-ready RAP object using legacy BAPI](https://blogs.sap.com/t5/enterprise-resource-planning-blogs-by-members/cloud-ready-rap-object-using-legacy-bapi-clean-core-objective/ba-p/13572339) (search excerpts)

**Additional save / unmanaged save [SMALL: option on managed BO]**
- `managed with additional save implementation in class bp_some_abp unique;` — `save_modified` receives `create`, `update`, `delete` tables which "By default … contain only keys and changed fields"; `with full data` passes all instance data. `managed with unmanaged save implementation in class bp_some_abp unique;` replaces the default save entirely. — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)

**Draft handling [BIG: persisted, resumable unit of work with exclusive lock, Prepare/Activate]**
- Draft actions are implicit: `draft action Edit; draft action Resume; draft action Activate optimized; draft action Discard; draft determine action Prepare { validation validate; }`. `Edit`, `Activate`, `Discard`, `Resume` accept `with additional implementation`; "`Activate optimized` reduces the determinations and validations it runs." "Draft tables must not be accessed directly with ABAP SQL." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Drafts "temporarily store the state of the transaction buffer with inconsistent application data" in the database so that interaction can span several requests/sessions "without violating the REST principles of stateless communication"; "The RAP runtime fully implements draft handling." — [SAP Press architecture article](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model)
- Draft stores buffer content in draft tables so a transaction can "expand over different ABAP sessions"; `%is_draft` is part of `%tky`; "Registering update function modules outside the late save phase interferes with draft scenarios." — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- Concurrency model shown in SAP training slides: optimistic concurrency via ETag vs. "Locking – Pessimistic concurrency control". — [SlideShare, Overview of RAP](https://www.slideshare.net/slideshow/overview_of_rap_abap_restful_programming_model_1729458306-pdf/273905649) (search excerpt)
- Pain point: an unmanaged, draft-enabled, late-numbered RAP BO on legacy non-GUID tables (EKKO) hit a duplicate-key error on the draft table; the fix was a separate temporary GUID key on the draft table; the author says the question went unanswered for about a year. Behavior definition used `etag master LoclLastChangedAt`, `lock master total etag LastChangedAt`. — [SAP Community, Unmanaged draft for non-GUID-key legacy objects](https://blogs.sap.com/2022/03/13/abap-restful-application-programming-unmanaged-draft-for-non-guid-key-based-legacy-objects./) (search excerpt)

**Side effects [BIG-ish, UI-derived: declared dependency graph between fields/actions/messages/permissions]**
- Syntax (verbatim): `field a affects field b; $self affects field y; field g affects permissions(field h); action act1 affects field *, permissions(action act2), messages; event evt affects field j;` — "No custom implementation is needed"; targets include fields, `$self`, `entity`, `permissions(...)`, `message`; `determine action ... executed on ... affects` runs a determination when its sources change. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)

**EML (Entity Manipulation Language) [BIG: typed, set-oriented API over the buffer with per-field control flags and CID correlation]**
- Short form: `MODIFY ENTITY root_ent CREATE FIELDS ( key_field field1 field2 ) WITH cr_tab MAPPED ... FAILED ... REPORTED ...`; long form `MODIFY ENTITIES OF root_ent ENTITY root CREATE FROM VALUE #( ... )` where `FROM` requires `%control` to be filled explicitly; `EXECUTE` for actions; dynamic form `MODIFY ENTITIES OPERATIONS op_tab`; "EML MODIFY statements for delete operations can only use the field specification option FROM." `READ ENTITIES OF root_ent ENTITY root_ent ALL FIELDS WITH ... RESULT ... FAILED ... REPORTED ...`; read-by-association `BY \_child ... LINK DATA(links1)`. `%cid` "must" be provided and "is only valid within one ABAP EML request"; `%control` flags use `if_abap_behv=>mk-on/mk-off`, set automatically by `FIELDS ( ... ) WITH`. Handler signatures: `METHODS create FOR MODIFY IMPORTING entities FOR CREATE bdef.`, `METHODS read FOR READ IMPORTING keys FOR READ bdef RESULT result.` ("Specifying a read result is mandatory."). — [SAP cheat sheet 08](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- EML is "a standardized, type-safe API used to access the data and functionality of a business object"; `MODIFY ENTITIES` writes, `READ ENTITIES` reads from the transaction buffer; it serves both provider (behavior implementation) and consumer (incl. unit tests). — [SAP Press architecture article](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model)

**RAP business events [BIG: post-commit domain events declared in the BDL]**
- Syntax: `event evt1; event evt2 parameter SOME_ENTITY; managed event evt4 on evt1 parameter SOME_ENTITY; event evt5 for side effects;` — "Events are raised with `RAISE ENTITY EVENT` in the ABP during late save. An event binding is required after creation. Managed (derived) events are raised automatically with the referenced event." — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- `RAISE ENTITY EVENT Z##_R_Travel~TravelCreated FROM CORRESPONDING #( create-travel ).` "can only be used in ABAP behavior pools" and "can only raise events that are defined in the behavior definition for the same RAP BO"; SAP "recommends" raising in saver methods (for managed BOs: in an additional save). "Business event consumption is always asynchronous and supports internal and external consumers." Local handler: a local class `FOR EVENTS OF <BO>` inheriting from `CL_ABAP_BEHAVIOR_EVENT_HANDLER` with `METHODS on_travel_created FOR ENTITY EVENT IMPORTING new_travels FOR Travel~TravelCreated.`; external consumers need an Event Binding. Limitation: FOR EVENT types lack `%is_draft`/`%tky`, so events cannot be raised for draft instances. — [SAP Learning, Raising and Handling Business Events](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/raising-and-handling-business-events)
- On-premise: the event "is raised during the SAVE sequence after the point of no return has passed". — [SAP blog, RAP business events in S/4HANA on-premise 2022](https://blogs.sap.com/2023/01/25/how-to-create-rap-business-events-in-s-4hana-on-premise-2022/) (search excerpt)


**Additional primary findings from SAP Learning (fetched after retry; official SAP course content)**
- Determinations (official): `determination <determination_name> <trigger time> { <trigger_conditions> }`; "on modify: Runs immediately after changes reach the transactional buffer, so results are available within the transaction"; "on save: Runs during the save sequence, when changes are persisted to the database"; trigger conditions `create; update; delete; field <f1>, <f2>;` are OR-linked and at least one is mandatory; "For determinations defined as on save, trigger condition update; only works with the trigger condition create;"; "The execution order of determinations is not fixed"; determinations return messages via `reported` only ("There is no failed parameter"); "Not available for unmanaged, non-draft scenarios"; changing the trigger time later produces a syntax error only in the behavior pool, not in the BDL. — [SAP Learning, Setting Values Using Numbering and Determinations](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/setting-values-using-numbering-and-determinations)
- Validations (official): `validation <validation_name> on save { <trigger_conditions> }` — "Only the trigger time on save is supported"; conditions `Create; Update; Delete; Field ...;` OR-linked; "The trigger condition update; is only allowed in combination with the trigger condition create;"; "The order of execution for validations is not fixed"; "If you reject an entity instance, it is mandatory, that you return a message to the consumer"; messages are bound to an instance (`%tky`, `%msg`, `%element-<field> = IF_ABAP_BEHV=>MK-ON`) or placed in `%OTHER`; validations "are not available for unmanaged, non draft scenarios". — [SAP Learning, Implementing Input Checks Using Validations](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/implementing-input-checks-using-validations)
- Static field control (official): "There is no runtime check for mandatory fields and no runtime error occurs if a mandatory field is not filled" (only `mandatory:create` raises a runtime error); "If a runtime check is required, the application developer must implement it using a validation"; "EML statements using the IN LOCAL MODE addition bypass the static field control"; `readonly:update` "is technically a dynamic field attribute". — [SAP Learning, Defining Static Field Control and Value Helps](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-static-field-control-and-value-helps)
- Numbering (official): external numbering = consumer supplies keys (`field ( readonly: update, mandatory: create )`), needs validations and pessimistic locking against duplicate keys; managed internal numbering `field ( numbering: managed ) TravelUUID` — "A unique value is assigned automatically on create, and no ABAP implementation is required", only for managed scenarios, a single RAW(16) key field that must be `readonly`/`readonly:update`; unmanaged early numbering `early numbering` + handler `FOR NUMBERING` with `entities` in and `failed/reported/mapped` out — "for each %cid value in entities you return a corresponding entry in either failed or mapped", else runtime error; late numbering: `adjust_numbers` in a saver class inheriting `CL_ABAP_BEHAVIOR_SAVER`, "has no importing parameters and no failed", temporary keys in `%pid`, consumer values in `%tmp`; "If a parent entity uses late numbering, all its child entities must also use it"; "External and managed internal numbering are always early." — [SAP Learning, Setting Values Using Numbering and Determinations](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/setting-values-using-numbering-and-determinations)
- Late numbering example (practitioner): `unmanaged implementation in class zbp_i_carrier_uln unique; strict ( 2 ); with draft; define behavior for Z_I_CARRIER_ULN alias Carrier late numbering draft table zjp_d_carr_uln lock master total etag LastChangedAt`; "This scenario is useful for a gapless assignment of unique keys"; "The key value for an instance is assigned just before the instance is saved on the database"; `mapped-carrier = VALUE #( for ls_carrier in lt_carriers ( intid = ls_carrier-intid ) )`; the UI shows key 0 until save. — [discoveringabap, Unmanaged late numbering](https://discoveringabap.com/2023/03/07/abap-restful-application-programming-26-unmanaged-late-numbering) (community blog)
- Concurrency (official): "Pessimistic concurrency control is done by exclusively locking data sets" in a global lock table; "Before data is changed on the database, the corresponding data set receives a lock entry"; conflicting requests are rejected; "After the change request has been successfully executed, the lock entry on the lock table is removed"; in managed scenarios "the business object framework assumes all locking tasks", in unmanaged ones "the application developer has to implement the method for lock". Optimistic: "Concurrency control based on ETags does not lock the data set"; the OData client "reads the current ETag value with every read request and sends this value back with every modifying operation"; `etag master ChangedAt`, `etag dependent` for sub-entities ("instances of that sub entity are not protected with an ETag field of their own"), `use etag` in the projection; recommended field type `abp_lastchange_tstmpl` annotated `@Semantics.systemDateTime.lastChangedAt: true`; "for every modify operation, except for the delete operation, the ETag value must be uniquely updated"; `createdBy/createdAt/lastChangedBy` are unsuitable because "none of those annotations come with a guarantee that the value changes in any update". — [SAP Learning, Understanding Concurrency Control](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-concurrency-control)
- Locking is mandatory in managed BOs: "it is also mandatory to set a lock type and an authorization type for each entity"; "The root entity is always used as lock master and authorization master"; `unique` means "each operation can be implemented exactly once"; "There is no way that the RAP framework can determine the table field name in which to store a certain entity element" (hence `mapping`). — [SAP Learning, Defining Business Objects and their Behavior](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-business-objects-and-their-behavior)
- Draft (official): drafts exist because "Stateless RESTful protocols such as OData have no fixed session, so the server cannot hold interim versions"; `with draft;` works for managed and unmanaged — "In all scenarios, the draft is managed"; two kinds: new-draft (no active instance yet, "Created data is stored immediately, regardless of validity") and edit-draft (created with `EDIT`, "The whole active instance is copied to the draft table"). Header example: `with draft; define behavior for Z##_R_Travel alias Travel persistent table z##_travel draft table z##_travel_d lock master total etag ChangedAt`. The draft table has one field per view element plus the technical fields from include `SYCH_BDL_DRAFT_ADMIN_INC`; `suppress`ed elements get no draft field; changing the CDS view requires regenerating the draft table. Draft actions: EDIT copies active→draft (feature/authorization control possible); PREPARE enriches/validates; ACTIVATE "Runs an implicit PREPARE, then UPDATE (edit-draft) or CREATE (new-draft). Removes the draft afterward. No feature control"; "The ACTIVATE action does not save the active instance on the database" (a separate `COMMIT ENTITIES`/OData save does); DISCARD deletes the draft, no feature/authorization control; RESUME "Re-creates the active lock when the user continues a draft after the exclusive lock expired" and is only exposed if explicitly declared. Draft actions "exist only for lock master entities and cover the whole lockable subtree"; strict mode demands `draft action Edit; draft action Activate; draft action Discard; draft action Resume; draft determine action Prepare;`. — [SAP Learning, Understanding the Draft Concept](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-the-draft-concept)
- Draft concurrency (official): pessimistic phase — creating a draft locks the active instance exclusively; "The exclusive lock is not bound to the ABAP session", persists across requests of the same user, removed on save/discard; default maximum lifetime "15 minutes". Optimistic phase — after expiry the draft is unprotected: others may edit the active instance or create a second draft, which "implicitly deletes the first one"; a draft is removed automatically after "28 days" of inactivity; resuming starts a new pessimistic phase. Total ETag: "In draft-enabled RAP BOs, it is mandatory to define a total ETag field"; its value must change whenever the active version changes and must not change during the draft lifetime (`lastChangedAt` qualifies); if active and draft values differ, the draft is invalid. The `etag master` field must change on every draft write, so use `@Semantics.systemDateTime.localInstanceLastChangedAt: true` (`total etag ChangedAt`, `etag master LocChangedAt`). Projections need `use draft`. — [SAP Learning, Understanding the Draft Concept](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-the-draft-concept)
- Actions and messages (official): "By default, actions have an instance reference and are accessible from outside the business object"; `internal`, `static`, factory (instance or static) variants; "If a result parameter is declared in the action definition, it must be filled in the implementation"; "Instance factory actions are not supported for the managed implementation type"; messages are class-based (`IF_ABAP_BEHV_MESSAGE` incl. `IF_MESSAGE`, severity error/warning/information/success, T100 key); instance messages go to `reported-<entity>` with `%msg`, static ones to `%other`; `IN LOCAL MODE` "provides a privileged data access by suppressing certain features of the RAP BO framework, for example authorization checks and feature control", and using it outside the behavior implementation causes runtime errors. — [SAP Learning, Defining Actions and Messages](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-actions-and-messages)
- Authorization (official): with `strict`, "every entity has to be flagged as either authorization master or" dependent; `(global)` "grants or refuses access for all instances of a BO entity" (`FOR GLOBAL AUTHORIZATION`), `(instance)` "based on the state of the entity instance" (`FOR INSTANCE AUTHORIZATION`), `(global, instance)` needs both methods; `requested_authorizations` flags allow checking only what was requested; result flags e.g. `<result>-%action-cancel_travel = if_abap_behv=>auth-unauthorized. <result>-%update = if_abap_behv=>auth-unauthorized.`; "In case of missing authorizations, the modification request is rejected" and the UI disables the button. — [SAP Learning, Implementing Authority Checks](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/implementing-authority-checks)
- Implementation options (official): managed with managed save requires "a one-to-one relation between BO entities and database tables"; unmanaged — "the business object runtime relays most of the external requests to the behavior implementation", CRUD + lock in the handler class, DB writes in the saver class, "best suited for integrating existing application logic that already works with an application buffer"; managed with unmanaged save — runtime does standard ops and most save logic, `save_modified` writes to DB, suited when there is no one-to-one table mapping; managed with additional save — `save_modified` "is executed in addition to the managed write access and not instead of it". In unmanaged BOs "determinations and validations are supported only if the business object is draft-enabled"; "Draft-handling is always done by the business object runtime." — [SAP Learning, Exploring the Behavior Implementation Options](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/exploring-the-behavior-implementation-options)
- Change documents: no declarative support found; a 2022 SAP Community answer says that in a managed BO "you would have to create an additional local class and in the save_modified( ) you would be able to call the API to work with change documents", and in unmanaged BOs the create/update/delete methods write them directly. — [SAP Community Q&A, RAP managed service change documents](https://community.sap.com/t5/technology-q-a/sap-btp-abap-rap-managed-service-change-documents/qaq-p/12526738) (search excerpt; page returned 403)

### Inferences
- RAP's core trick is that *trigger conditions* (operation kind + field set) and *phase* (on modify vs on save) are declared, while the rule body stays imperative. For ObjectFlow this suggests an "entity rule" family: `determination <name> on modify|on save { create; update; field a, b; }` and `validation <name> on save { ... }`, where the generator derives method stubs and the session (unit of work) runs them at check-in. The warning about arbitrary determination order and loops suggests a checker rule (dependency cycle detection over `affects`/field triggers).
- Feature control is RAP's substitute for a declarative state machine: status → permitted operations/fields. It is a strong candidate for ObjectFlow's status types (declare which commands/updates a status permits; generate the "enabled/disabled" evaluation once).
- The save sequence (finalize → check_before_save → adjust_numbers → save → cleanup, with a point of no return) maps onto ObjectFlow's explicit check-in; the new idea is naming the phases and letting a checker forbid phase-inappropriate code (e.g. DB writes before check-in succeeded, events before commit).
- Draft handling is the one RAP mechanism MoWare has no analogue for: a persisted, lockable, resumable unit of work. It is expensive (shadow table per entity, `%is_draft` in every key) and SAP's own community shows sharp edges with legacy keys; it is a [BIG] idea but an optional one.

## Key question 2: SAP RAP – CDS views, projections, associations vs compositions, annotations, what "managed" saves

### Takeaway
A RAP BO is a composition tree of CDS *view entities* (root + children, each with `association to parent`), re-exposed through *projection views* for a service; compositions carry lifecycle semantics (cascading delete, lock/authorization/ETag "dependent by") that the managed runtime executes, and CDS annotations attach semantics (ETag timestamps, UI) to the model rather than to code.

### Cited Findings
- "a composition always leads from the parent to the direct child, and every composition needs a matching to-parent association pointing from the child back to its parent"; a plain association has no lifecycle link. — [SAP Learning, Defining Composite Business Objects](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-composite-business-objects) (search excerpt)
- Sample: the parent is changed to a root view and the standard association to the child is replaced with a composition; the child declares an association to parent pointing back at the root. — [SAP-samples RAP openSAP repo](https://docsearch.algolia.com/mcp/docs/repo/sap-samples/abap-platform-rap-opensap) (search excerpt)
- Projection layer: compositions must be re-declared; "it is not sufficient to simply expose the associations defined in the underlying data definition views"; in a transactional query projection the parent uses a redefined association "redirected to composition child"; interface views cannot have new associations defined. — [SAP Learning, Defining Compositions in OData UI Services](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-compositions-in-odata-ui-services) (search excerpt)
- Projection view flavors: "transactional queries are intended for modeling the projection layer of a RAP business object" (vs. transactional interface and analytical query projections). — [SAP blog, CDS projection views: what's your flavor](https://blogs.sap.com/2022/07/04/cds-projection-views-in-abap-cds-whats-your-flavor/) (search excerpt)
- Behavior-level consequences of compositions: `lock dependent by _Assoc`, `authorization dependent by _Assoc`, `etag dependent by _Assoc`; "Deleting a managed parent also deletes its composition children"; association behaviour `association _Assoc { create; link action ...; unlink action ...; inverse function ...; }` enables create-by-association. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Projection BDEFs use `use create; use action act;` to expose a subset of the base BO's behaviour. — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Annotations carrying persistence semantics: `@Semantics.systemDateTime.localInstanceLastChangedAt: true` (ETag) and `@Semantics.systemDateTime.lastChangedAt: true` (total ETag). — [SAP cheat sheet 36](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/36_RAP_Behavior_Definition_Language.md)
- Business objects "have to revolve around a CDS view"; BDL is "a specialized type of CDS view"; criticism that UI control lives in CDS annotations: "a data model has no business knowing how its data is going to be interacted with". — [SAP Press architecture article](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model)
- Composition vs association summarised by a third-party guide as "regular associations for independent entities such as master-data lookups, and compositions for parent-child trees with lifecycle dependency". — [skills.sh, cds-view-entities](https://www.skills.sh/likweitan/abap-skills/cds-view-entities) (third-party, search excerpt; not relied on for facts)


**Additional primary findings from SAP Learning (fetched after retry)**
- A composition is "a specialized association that defines a whole-part relationship"; "The definition of a composition always requires the definition of a corresponding to-parent association"; "for a composition no ON-condition is defined explicitly" (generated), while the to-parent association is written explicitly with cardinality generated as [1..1]. Syntax: `define root view entity Z##_R_Travel as select from z##_travel composition [0..*] of Z##_R_TravelItem as _TravelItem { ... _TravelItem }` and in the child `association to parent Z##_R_Travel as _Travel on $projection.AgencyId = _Travel.AgencyId and $projection.TravelId = _Travel.TravelId`. To-parent ON-condition rules: only and all parent key fields, each child field once, `$projection` prefix, only `=`, no `OR`/`NOT`. "Fields from a composition target can't be used locally in the SELECT list, WHERE clause". — [SAP Learning, Defining Composite Business Objects](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-composite-business-objects)
- Lifecycle/behaviour: "A child entity (composite part) only exists together with its parent entity (whole)"; children can be created through the parent but "parents can't be created via their child nodes"; compositions are read- and create-enabled automatically; `association _TravelItem { create; with draft; }` (root) / `association _Travel { with draft; }` (child); in a draft-enabled BO all associations must be draft-enabled; the root is lock master and children `lock dependent by _Travel` (mandatory in managed scenarios); a child may have its own `etag master`; "Only the root can be the authorization master", create-by-association is checked as an update on the master. Tree rules: "There is exactly one root entity"; "The root entity may be the source but must not be the target of a composition"; only root entities may be lock/authorization master. — [SAP Learning, Defining Composite Business Objects](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-composite-business-objects)
- Projection layer: exposing the base associations is not enough because "the targets of those associations are a data definition views and not projection views"; syntax `_TravelItem : redirected to composition child Z##_C_TravelItem`, `_Travel : redirected to parent Z##_C_Travel`, plain `_X : redirected to Z##_C_X`; "The redirected to keyword is only available in views that are defined with projection on"; plain redirection loses "the special characteristics of compositions and to-parent associations". Behavior projection: `use association _TravelItem { create; with draft; }` / `use association _Travel { with draft; }`; "each entity has to be exposed in the service definition explicitly". — [SAP Learning, Defining Compositions in OData UI Services](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-compositions-in-odata-ui-services)

### Inferences
- ManMap's repositories with mapped queries/joins are already a projection mechanism; the RAP-specific addition is a *typed* distinction between composition (owned, cascaded, locked/authorized/versioned with the parent) and association (reference). Since MoWare explicitly has no cascades, a [BIG] but deliberate idea would be an opt-in `composition` relation whose save/delete/lock/version semantics are generated, leaving plain references as today.
- "Projection BDEF" (`use create; use action`) is a [SMALL] idea: a command/service can expose a subset of an entity's operations.

### Gaps
- Composition/to-parent syntax and projection redirection are now quoted from SAP Learning. The SAP cheat sheet 15 (CDS view entities) was fetched but is only an index of sample files without syntax text, so general CDS view-entity syntax (joins, parameters, path expressions) is not quoted verbatim here.
- Cascading delete in managed scenarios is stated only in the BDL cheat sheet ("Deleting a managed parent also deletes its composition children"); the SAP Learning page does not mention it.
- No primary source captured on which CDS annotations are specifically used for read-only (non-transactional) consumption views; the CDS projection-views blog (community.sap.com) returned 403.

## Key question 3: Business Central AL – table triggers, field validation, data model rules

### Takeaway
BC puts business logic on the *table*: OnInsert/OnModify/OnDelete/OnRename triggers and per-field OnValidate triggers run in a fixed order around the database operation, but only when the caller asks for them (`Insert(true)`, `Modify(true)`, `Validate(...)`), and there is no implicit cascade — deleting children is coded in OnDelete.

### Cited Findings
- OnModify "is run before the default modify behavior … It runs automatically when the user changes at least one field … of a record in a page … If a user modifies a record using AL code, then the RunTrigger argument of MODIFY … must be set to true for the OnModify Trigger to run, or otherwise it will not. If an error occurs in the trigger code, the record changes are canceled." Microsoft recommends "that you do not include code that can stop the user from recording a change in the OnModify trigger". — [Microsoft Learn, OnModify (Table) trigger](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/triggers-auto/table/devenv-onmodify-table-trigger)
- `[Ok := ] Record.Modify([RunTrigger: Boolean])` — RunTrigger default is false. — [Microsoft Learn, Record.Modify](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/methods-auto/record/record-modify-method)
- Field OnValidate "is run after the default validation behavior when data is entered in a field … the system checks that the data type of the value entered matches … and that it complies with the property constraints … If both the table field and page field triggers are defined, then the OnValidate trigger on the table field is run before the OnValidate trigger on the page field." — [Microsoft Learn, OnValidate (Field) trigger](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/triggers-auto/field/devenv-onvalidate-field-trigger)
- `Record.Validate(Field [, NewValue])` "Calls the OnValidate trigger for the field that you specify" and "not only assigns the value but also triggers any validation logic defined for the field in the table". — [Microsoft Learn, Record.Validate](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/methods-auto/record/record-validate-method)
- Typical trigger responsibilities per table type: Master OnInsert "Assigns the No. field from the appropriate number series if the user hasn't provided the value manually" and default dimensions; Document (line) OnInsert "Makes sure that the status can accept new lines if the document supports different statuses"; Master OnModify "Sets the Last Date Modified field"; Master OnDelete "Makes sure that started, but incompleted, transactions … don't exist … deletes all subsidiary information"; Document (header) OnDelete "deletes all document lines and subsidiary document information"; OnValidate on relation fields "Assigns the default dimensions … Assigns certain default values to other fields … Validates any case-specific complex business rules". — [Microsoft Learn training, Use typical data triggers](https://learn.microsoft.com/en-us/training/modules/implement-data-process-model-business-central/3-typical-data-triggers)
- Order of execution around a delete: 1 trigger event (before) OnBeforeDeleteEvent, 2 table trigger OnDelete, 3 global table trigger OnDatabaseDelete, 4 database operation, 5 OnAfterDeleteEvent. — [Microsoft Learn, Event types](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-event-types)
- TableRelation syntax: `TableRelation = <TableName>[.<FieldName>] [WHERE(<TableFilters>)] | [IF(<Conditions>) ... ELSE <TableRelation>]`; conditional example `TableRelation = if (Type = const (Customer)) Customer else if (Type = const (Item)) Item;`; "This property is also used to define where to look to validate entries"; table extensions may add conditions ("Modifications to the TableRelation are additive and evaluated after the existing value … the first unconditional relation will prevail"). — [Microsoft Learn, TableRelation property](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/properties/devenv-tablerelation-property)
- Collectible errors: `[ErrorBehavior(ErrorBehavior::Collect)]` on a procedure makes `Error(ErrorInfo.Create(...))` calls collect instead of stop; `HasCollectedErrors`, `GetCollectedErrors()`, `ClearCollectedErrors()`; "scenarios where users are presented with a list of things to fix". — [Microsoft Learn, Collecting errors](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-error-collection)
- Table keys: `key(Name; Fields) { Clustered = true; Unique = true; Enabled = false; IncludedFields = ...; SumIndexFields = ...; MaintainSqlIndex = false; }`; primary key up to 16 fields; unique secondary keys allowed; schema restrictions on upgrade: "Don't delete primary keys … Don't add or remove primary key fields … Don't add more unique keys … Don't add more clustered keys". — [Microsoft Learn, Table keys](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-table-keys)

- OnInsert "is run before default insert behavior, which checks that the record to be inserted does not already exist … If a user inserts a record using AL code, then the RunTrigger argument of INSERT … must be set to true … The new record is not inserted if an error occurs in the trigger code"; for pages with `DelayedInsert` "we recommend that you write any code that is in an OnInsert trigger so that it will always succeed. For example, this applies to journal lines." — [Microsoft Learn, OnInsert (Table) trigger](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/triggers-auto/table/devenv-oninsert-table-trigger)
- OnDelete "runs before the default delete behavior, which checks that the record exists … If a user deletes a record using AL code, then the RunTrigger argument of DELETE … or DELETEALL … must be set to true for the OnDelete Trigger to run, or otherwise it will not. The record is not deleted if an error occurs in the trigger code." — [Microsoft Learn, OnDelete (Table) trigger](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/triggers-auto/table/devenv-ondelete-table-trigger)

### Inferences
- BC's per-field OnValidate is functionally RAP's "determination on modify { field X; }" plus validation in one imperative hook, and BC's OnInsert/OnModify/OnDelete are RAP's operation-triggered rules without a save phase. For ObjectFlow these are [SMALL]: lifecycle hooks on entities, if the session already owns check-in. The explicit `RunTrigger` flag is a known source of bugs (logic silently skipped) — an argument for ObjectFlow to run rules unconditionally at check-in rather than exposing a flag.
- TableRelation with conditional (`if Type = const(...)`) targets is a [SMALL] option worth copying for ManMap/ObjectFlow references (polymorphic reference by discriminator), and it doubles as validation metadata.
- Collectible errors confirm the value of ObjectFlow validations reporting *all* violations (RAP does the same via `reported`).

- The OnRename reference page was not fetched; its semantics (fires on primary-key change, must mirror OnModify on master tables) rest on the training module and a search excerpt of the Learn page.

## Key question 4: Business Central AL – FlowFields, FlowFilters, SIFT/NCCI, Query objects (declarative aggregates and read models)

### Takeaway
FlowFields are virtual fields whose value is a declared aggregate (`Sum/Count/Exist/Average/Min/Max/Lookup ... where(...)`) computed in SQL on demand, parameterised by user-settable FlowFilters and accelerated by SIFT indexed views or, newer, columnstore indexes; Query objects are declarative multi-table joins with aggregation that bypass the record API.

### Cited Findings
- "FlowFields aren't physical fields that are stored in the database. They're a description of a calculation and a location for the result to be displayed. Because the information in FlowFields exists only at run time, values in FlowFields are automatically initialized to 0." Seven types: Sum, Average, Exist, Count, Min, Max, Lookup. Example: `Sum("Customer Entries".Amount where(CustNo=field(CustNo)))`, `Exist("Customer Entries" where(CustNo=field(CustNo)))`. Calculated when the field is on a page, when `CalcFields` is called, or when a FlowFilter is applied. "By default, the calculation happens even if the FlowField isn't visible on the page … This behavior can lead to unnecessary computations and performance issues. Starting in version 26.0 … Calculate only visible FlowFields". — [Microsoft Learn, FlowFields overview](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-flowfields)
- FlowFields read in AL code "are always zero because the calculation formula isn't run in AL code" unless `CalcFields`/`SetAutoCalcFields` is used. — [Microsoft Learn training, Use different field functions](https://learn.microsoft.com/en-us/training/modules/manipulate-data-via-code/5-field-functions) (search excerpt)
- FlowFilters: "You use FlowFilter fields to set ranges on the calculations that are shown in FlowFields"; "FlowFilter fields aren't saved in the database. Instead, each user sets their own FlowFilter values at run time"; the CalcFormula filters "can consist of constants, values from ordinary fields, and filters given as parameters in FlowFilter fields". — [Microsoft Learn, FlowFilters overview](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-flowfilter-overview)
- SIFT implementation: "Business Central uses Indexed Views to maintain SIFT totals … one indexed view for each SIFT key that is enabled"; `MaintainSIFTIndex` true creates it and SQL Server maintains it on every change; the view is "always created at the level of finest granularity" (e.g. per account per date, so "in the worst case scenario, 365 records must be summed … for a year"). Generated SQL: `CREATE VIEW GLEntry$VSIFT$1 AS SELECT SUM(Amount) as SUM$Amount, AccountNo, PostingDate FROM GLEntry GROUP BY AccountNo, PostingDate; CREATE UNIQUE CLUSTERED INDEX VSIFTIDX ON GLEntry$VSIFT$1(AccountNo, PostingDate)`; AL `GLEntry.SetCurrentKey(...); SetRange(...); GLEntry.CalcSums(Amount);`. Max 20 SumIndexFields per key. — [Microsoft Learn, SIFT and SQL Server](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-sift-and-sql-server)
- Cost/limits: "When data is inserted, updated, or deleted in a table, the SIFT keys for that table are maintained. Maintaining these SIFT indexes has performance overhead"; NCCI "is envisioned to be the successor of SumIndexField Technology (SIFT)": `ColumnStoreIndex = Code,FirstNames,ECTSPoints,NumberOfCourses;` replaces several SIFT keys, "there's no need to consider which query scenarios should be indexed". — [Microsoft Learn, Migrating from SIFT to NCCI](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-migrating-from-sift-to-ncci)
- NCCI "without the locking issues that SIFT indexes sometimes impose on the system"; "Ensure appropriate SIFT indices for all FlowFields of type sum or count." — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer)
- SIFT is used only if the current key contains the FlowField filter fields and `MaintainSIFTIndex` is true; otherwise "Business Central traverses all records in the base table". — [Microsoft Learn, SIFT technology / CalcFields (search excerpt)](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-sift-technology)
- Query objects: `dataitem(DataItem2; Table2) { DataItemLink = FieldY = DataItem1.FieldX; SqlJoinType = InnerJoin; column(...) {} }`; two types normal and API; `DataAccessIntent = ReadOnly` reads from a replica; "You cannot run a query that gets data from both the application database and the business data database". — [Microsoft Learn, Query object](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-query-object)
- Aggregation: `column(Qty; Quantity) { Method = Sum|Average|Min|Max|Count; }` — "Setting an aggregate method on a column will automatically group the resultant data set by the other columns in the query … similar to the GROUP BY clause"; Count needs a column without a source field; DISTINCT is emulated via Count. — [Microsoft Learn, Aggregating data in query objects](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-query-totals-grouping)
- Pros/cons of queries: "Bypasses the AL record API where server reads all fields … Can join multiple tables" vs "Query object result sets aren't cached in the server's primary key (data) cache. No writes are allowed. You can't add a page on a query object." — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer)
- Partial records: "you can use the partial records capability to only load out these fields initially"; limits fields read and table-extension joins. — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer)

- CalcFields (reference): "FlowFields are virtual fields. The values in these fields are not saved in the table … if you retrieve a record using the Find Method and Next Method, the FlowFields in those records are set to zero (0). Then, when you call CalcFields, their values are updated." "SumIndexField Technology (SIFT) is used by default when the calculation method for a FlowField is Count or Average." Setting `MaintainSIFTIndex` to false means "Business Central will traverse all records in the base table to perform the calculation instead of using SIFT. This can reduce the number of required SIFT indexes, which can improve performance." Example with FlowFilter: `CustomerRec.SetRange("Date Filter",20080101D,20081231D); CustomerRec.CalcFields(Balance, "Net Change");`. — [Microsoft Learn, Record.CalcFields](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/methods-auto/record/record-calcfields-method)

### Inferences
- FlowFields are the single most "declarative-persistence" idea in BC and a clear [BIG] candidate for ManMap: a mapped entity/DTO field whose value is a declared aggregate over another mapping (`sum(Entry.amount) where Entry.customerNo = this.no`), computed via generated SQL at read time (never stored), optionally parameterised by caller-supplied filters (FlowFilter ≙ query parameter). The platform-side lessons are also explicit: aggregates must not be calculated implicitly (hidden-page problem) and need an index story (SIFT/NCCI) — ManMap could emit an index/materialisation hint as a [SMALL] option.
- Query objects with implicit GROUP BY mostly overlap ManMap's custom SQL + row mappers; the [SMALL] gains are `Method = Sum/Count` on a mapped-query column and a `readOnly` data-access intent.

### Gaps
- The CalcFields reference page is now cited. The SIFT tuning/performance pages were not fetched; the claim that SIFT is used only if the current key contains the FlowField's filter fields still rests on a search excerpt of Microsoft Learn.

## Key question 5: Business Central AL – enums, interfaces, table extensions, codeunits, schema evolution

### Takeaway
BC models status types as *extensible enums* that can implement interfaces (value → codeunit dispatch), lets third parties add fields/keys/triggers via table extensions stored in a companion table, and handles schema evolution with compiler-enforced obsoletion states plus upgrade codeunits rather than migrations.

### Cited Findings
- Enum: `enum 50121 Loyalty { Extensible = true; value(0; None) { } value(1; Bronze) { } ... }`; `enumextension 50130 LoyaltyWithDiamonds extends Loyalty { value(50130; Diamond) { Caption = 'Diamond Level'; } }`; "Only enums with the Extensible property set to true can be extended"; UI sorting is by declaration order with base values before extension values; "Conversion to and from enum is more strict than for Options". — [Microsoft Learn, Extensible enums](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-extensible-enums)
- Enum implements interface: `enum 50200 SendTo implements IAddressProvider { Extensible = true; value(0; Company) { Implementation = IAddressProvider = CompanyAddressProvider; } value(1; Private) { Implementation = IAddressProvider = PrivateAddressProvider; } }` and `iAddressProvider := sendTo;` dispatches to the codeunit. Interfaces introduced 2020 wave 1; default interface methods (2026 wave 2, runtime 18) with `[RequiredPending]` lifecycle; "Avoid adding required methods to published interfaces. Analyzer rule AS0066 catches this condition." — [Microsoft Learn, Interfaces in AL](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-interfaces-in-al)
- Table extension: `tableextension 50115 RetailWinterSportsStore extends Customer { fields { field(50116;ShoeSize;Integer) { trigger OnValidate(); ... } } procedure HasShoeSize() ... trigger OnBeforeInsert(); ... }`; "Only tables with the Extensible Property set to true can be extended"; system/virtual tables cannot be extended. — [Microsoft Learn, Table extension object](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-table-ext-object)
- Storage/perf: "In version 23, the data model for table extensions was changed. In this new model, data from all table extensions on a table are stored in the same companion table. This means that there will be at most one SQL join"; alternative data model "related table + FlowField on the base table" ("Doesn't affect performance of base table"). — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer)
- Keys in table extensions: from 2026 wave 2 (runtime 18) "table extension keys can mix both base table fields and extension fields"; `Unique` and `Clustered` not supported in extensions. — [Microsoft Learn, Table keys](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-table-keys)
- ObsoleteState: values `No`, `Pending`, `Removed` (plus `Moved`, `PendingMove`); "the AL compiler … will return warnings for references to elements marked as Pending and errors for references to elements marked as Removed"; for elements other than tables/fields `Removed` is a compile error because they can simply be deleted. — [Microsoft Learn, ObsoleteState property](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/properties/devenv-obsoletestate-property)
- Upgrade codeunits: `codeunit ... { Subtype=Upgrade; trigger OnCheckPreconditionsPerCompany() ... trigger OnUpgradePerCompany() ... trigger OnValidateUpgradePerCompany() ... }`; "If there are no data changes between the extension versions, you don't need to write upgrade code"; upgrade tags (`UpgradeTag.HasUpgradeTag/SetUpgradeTag`) prevent double execution; schema sync is done by `Sync-NAVApp` "synchronizes the database with any table schema changes in the extension". — [Microsoft Learn, Upgrading extensions](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-upgrading-extensions)
- `TableType = Temporary` tables have the "advantage … that the table schema isn't synchronized with the database. So it doesn't have restrictions on breaking schema changes". — [Microsoft Learn, Temporary tables](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-temporary-tables)

### Inferences
- `enum ... implements Interface` with per-value implementation is a compact declarative strategy pattern; for ObjectFlow status types this suggests a [BIG]-ish idea: let a status type (or any enum) bind each value to a service implementation, generating the dispatch.
- Extensibility (`Extensible = true`, enumextension, tableextension) is a [BIG] concept family but addresses an ISV ecosystem problem MoWare may not have; `ObsoleteState` + compiler warnings/errors is a [SMALL] but immediately useful idea (deprecation as a language property checked by the DSL), and the additive-only schema rules plus upgrade codeunits show one way to add schema migration to ManMap without a migration-script DSL.

### Gaps
- No criticism sources found specifically about enum/interface or table-extension design beyond Microsoft's own performance notes.

## Key question 6: Business Central AL – events (integration/business/trigger/isolated/external) and subscribers

### Takeaway
AL events are publisher methods with empty bodies, raised explicitly (integration/business events) or implicitly by the runtime (table/page trigger events), and subscribed to with an attribute; they are BC's main extensibility mechanism (including the `IsHandled` override idiom), with "isolated" events running each subscriber in its own transaction and "external business events" notifying external systems only after commit.

### Cited Findings
- Event types: BusinessEvent ("a formal contract that carries an implicit promise not to change in future releases"), IntegrationEvent (no such promise, may expose implementation details), InternalEvent, Global (predefined, e.g. OnBeforeCompanyOpen), Trigger events ("published by the runtime and they can't be raised programmatically"). — [Microsoft Learn, Event types](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-event-types)
- Database trigger event subscriber signature: `[EventSubscriber(ObjectType::Table, Database::<Table Name>, 'OnBeforeModifyEvent', '', <SkipOnMissingLicense>, <SkipOnMissingPermission>)] procedure MyProcedure(var Rec: Record; var xRec: Record; RunTrigger: Boolean)`; `OnBeforeValidateEvent`/`OnAfterValidateEvent` carry `'<Field Name>'` and `CurrFieldNo`. — [Microsoft Learn, Event types](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-event-types)
- "An event publisher method is composed of a signature only and doesn't execute any code"; "Business and integration type events must be explicitly published and raised … trigger events … are published and raised implicitly by the system at runtime"; "a publisher has no knowledge of subscribers". — [Microsoft Learn, Events in AL](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-events-in-al)
- Isolated events: "An isolated event ensures the event publisher continues its code execution after calling an event. If an event subscriber's code causes an error, its transaction and associated table changes will be rolled back"; implemented "by separating each event subscriber into its own transaction"; "write transactions should explicitly be committed before invoking an isolated event. Otherwise, the isolated event will be invoked like a normal event"; syntax `[InternalEvent(false, true)]` (second arg = Isolated); only `TableType: Normal` record changes are rolled back. — [Microsoft Learn, Isolated events](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-events-isolated)
- External business events (preview): `[ExternalBusinessEvent('salesorderposted', 'Sales order posted', 'Triggered when sales order has been posted', EventCategory::"Sales")] procedure SalesOrderPosted(salesOrderId: Guid; customerName: Text; orderNumber: Text) begin end;` raised from an ordinary subscriber; "Business Events notifications are sent to external systems only after the current transaction is committed to the database … If the transaction is rolled back … the notification is never sent." Limitations: no translation/versioning; subscriptions are per all accessible companies. — [Microsoft Learn, Business events on Business Central (preview)](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/business-events-overview)
- Performance cost of events: "Table events change the behavior of SQL optimizations … The Business Central Server will issue SQL update/delete statements row in a for loop rather than one SQL statement. They impact ModifyAll and DeleteAll methods that normally do bulk SQL operations to be forced to do single row operations." Also: "Codeunit size of the subscriber matters", "Use single instance codeunits for subscribers, if possible", and sign-in events (OnCompanyOpen) delay every session. — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer)
- IsHandled idiom: "the IsHandled parameter is a Boolean passed by reference, and setting it to true during subscription tells Business Central not to run the next piece of code". — [Folio3, Subscribing to events](https://dynamics.folio3.com/blog/subscribing-to-events-in-business-central-using-a-l/) (third-party, search excerpt)
- Workflow engine: a workflow step "consists of a workflow event, moderated by event conditions, and a workflow response, customized by response options"; adding one requires a codeunit that registers the event code via `WorkflowEventHandling.AddEventToLibrary(MyWorkflowEventCode(), Database::"Purchase Header", 'My workflow event description', 0, false)`, a subscriber calling `WorkflowManagement.HandleEvent(MyWorkflowEventCode, PurchaseHeader)`, response registration via `AddResponseToLibrary`, an `OnExecuteWorkflowResponse` subscriber, and event/response-combination and table-relation registrations; during upgrade "the libraries of workflow events, responses, and table relations are removed and then recreated". — [Microsoft Learn, Walkthrough: workflow events and responses](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-walkthrough-workflow-events-responses)

### Inferences
- MoWare has no domain events. The BC material distinguishes three things worth separating in an ObjectFlow idea: (1) in-process extension hooks (integration events, trigger events) — useful only if MoWare needs third-party extension, so [BIG] but possibly out of scope; (2) post-commit notifications (external business events, RAP business events) — [BIG], and both platforms agree they must fire only after commit; (3) subscriber isolation (own transaction per subscriber) — a [SMALL] option on an event declaration.
- The BC workflow engine is a configuration-time event→condition→response machine assembled entirely from runtime tables and ~8 registration subscribers; it is a cautionary example of what happens when a state/process concept is *not* in the language.

### Gaps
- No blog/forum source found that explicitly criticises the `IsHandled` pattern or subscriber "spaghetti"; the only critical material is Microsoft's own performance guidance.

## Key question 7: Business Central AL – record-level permissions, number series, temporary tables, posting routines, system fields, locking

### Takeaway
BC's remaining declarative/persistence mechanisms are mostly *platform conventions plus system fields*: security filters on permission sets with a per-record `SecurityFiltering` mode, number series as a configurable library (plus SQL `NumberSequence`), in-memory temporary tables, automatic SystemId/audit/rowversion fields, and the journal→posting-codeunit→immutable ledger entry pattern that structures every transaction.

### Cited Findings
- Security filters: set on permission sets per table, e.g. field `Salesperson Code` filter `AH`; "Record level security filters don't support wildcard characters"; max 200 characters; multiple permission sets combine "so that the least restrictive filter is used". Developer side: `SecurityFiltering` = Filtered ("as if records outside the security filters … don't exist"), Validated (error when touching a record outside; "decreases performance … must go through every record"; single-field filters only), Ignored (bypass — "the administrator … isn't informed"), Disallowed (error if any filter is set). Defaults: explicit record variables Validated, queries and page records Filtered. FlowFields are computed over the filtered set. — [Microsoft Learn, Using security filters](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/security/security-filters)
- Temporary tables: "A temporary table data isn't stored in the database. It's only held in memory until the table is closed. The write transaction principle … doesn't apply"; three forms (`TableType = Temporary`, `Record "X" temporary` variable, `SourceTableTemporary`); "Temporary tables don't require the user to have permissions on the underlying table"; typical use as posting buffers (`TempInvoicePostBuffer`). — [Microsoft Learn, Temporary tables](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-temporary-tables)
- Number series: "Microsoft deprecated the NoSeriesManagement codeunit" in v24 for `codeunit "No. Series"`; OnInsert pattern: `if "No." = '' then begin MySetup.Get(); MySetup.TestField("Document Nos."); "No. Series" := MySetup."Document Nos."; if NoSeries.AreRelated(...) then ...; "No." := NoSeries.GetNextNo("No. Series"); end;`; the engine supports date-driven structures and "control if any gaps in a series are permitted" (some jurisdictions forbid gaps). — [alguidelines.dev, No. Series pattern](https://alguidelines.dev/docs/patterns/no-series/) (community guidelines site)
- "No. Series - Batch" batches `GetNextNo` requests until `SaveState()`. — [yzhums.com](https://yzhums.com/51184/) (community blog, search excerpt)
- Non-blocking alternative: "If you need a fast, non-blocking number sequence that can be used from AL, refer to the number sequence object type. Use a number sequence object if you: Don't want to use a number series; Can accept holes in the number range." — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer)
- System fields: `SystemId` (GUID, immutable, always a unique secondary key, usable in TableRelation and as OData key); data audit fields `SystemCreatedAt/By`, `SystemModifiedAt/By` populated by the platform "After all OnBeforeInsert and OnBeforeModify triggers … After the OnInsert and OnModify triggers … Before all OnAfterInsert and OnAfterModify triggers"; "You can assign the values, but the values written to the database are always provided by the platform"; `SystemRowVersion` exposes the SQL rowversion read-only; from runtime 18 additional FlowFields `SystemCreatedByUserName` etc. — [Microsoft Learn, Table system fields](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-table-system-fields)
- Locking: tri-state locking (v23+) — reads after writes use READCOMMITTED/shared locks instead of UPDLOCK; "Explicitly using the LockTable method in code maintains the same behavior, disabling optimistic reads"; always on from v26. — [Microsoft Learn, Tri-state locking](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-tri-state-locking)
- `ReadIsolation` (runtime 11) sets isolation per record instance (Default, ReadCommitted, ReadUncommitted, RepeatableRead); `LockTable` applies `UPDLOCK` to subsequent reads of that table until commit — "defer the Record.LockTable call as late as possible". — [Microsoft Learn, Performance for AL developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer); [Microsoft Learn, Control database locking behavior (release plan)](https://learn.microsoft.com/en-us/dynamics365/release-plan/2023wave1/smb/dynamics365-business-central/control-database-locking-behavior) (search excerpt)
- Posting pattern: Codeunit 12 "Gen. Jnl.-Post Line … is the only place to insert general ledger, VAT, and customer and vendor ledger entries"; it had grown to "approximately 7,600 code lines" with "extensive use of global variables" and "long procedures … with high cyclomatic complexity"; the redesign introduced "a Posting Engine Framework … to manage the start and finish of transactions and to isolate the creation [of] general ledger and VAT entries". — [Microsoft Learn, General Journal Post Line overview](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-general-journal-post-line-overview)
- Posting engine routines: `StartPosting` "Initializes posting buffer TempGLEntryBuf, locks G/L Entry and VAT Entry tables, and initializes … G/L Register"; `ContinuePosting`; `FinishPosting` "Completes posting by inserting G/L entries from temporary buffer into database table … Checks for inconsistencies"; `InsertGLEntry` is "The only function that inserts G/L entry into global TempGLEntryBuf table". Interface: `RunWithCheck`/`RunWithoutCheck` → `Code`. — [Microsoft Learn, Posting engine structure](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-posting-engine-structure); [Posting interface structure](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-posting-interface-structure)
- Data process model: journals/documents flow into ledger entries; "Document History (line) table … doesn't check whether the conditions for the deletion are met because users can never delete a document history line directly". — [Microsoft Learn training, Use typical data triggers](https://learn.microsoft.com/en-us/training/modules/implement-data-process-model-business-central/3-typical-data-triggers); module index [Implement the data process model](https://learn.microsoft.com/en-us/training/modules/implement-data-process-model-business-central/)
- Exam-prep description of Check → Post Line → Post-Batch layering (Codeunit 11 validation, Codeunit 12 ledger creation). — [open-exam-prep MB-820 11.3](https://open-exam-prep.com/study-guides/mb-820/design-patterns-data-process-model/11-3-data-process-model-posting-routines) (third-party study guide, search excerpt)

- NumberSequence (reference): "Business Central number sequences are built on SQL Server sequences, which means that they are not associated with any tables"; "Numbers are used sequentially, but numbers can be skipped … gaps … can occur when transactions are rolled back or numbers are allocated but not used"; by contrast number series "are specially designed for scenarios where you have to use a continuous numbering system on transactional records … when a number is requested by a transaction, the No Series Line table in the database is locked until the transaction completes"; the No. Series option "Allow Gaps in Nos." "actually uses number sequences in the underlying code". API: `NumberSequence.Insert('MyCompanySequence', 0, 1, true); number := NumberSequence.Next('MySequence',true);` (`Current` "is retrieved out of transaction"). — [Microsoft Learn, Number sequences](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-number-sequences); [NumberSequence data type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/methods-auto/numbersequence/numbersequence-data-type)
- Permission set object (v18+): `permissionset 50134 "Sales Person" { Assignable = true; Caption = 'Sales Person'; Permissions = tabledata Customer = RIMD, tabledata "Payment Terms" = RMD, tabledata Currency = RM, ...; }`, composition via `IncludedPermissionSets`/`ExcludedPermissionSets`, object permissions such as `codeunit SomeCode = x`; "If a permission set is extended through AL, the extension makes additive changes to the permission set … an extension can provide elevated privileges"; a VS Code command generates the permission file for all objects of a project. — [Microsoft Learn, Permission set object](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-permissionset-object)

### Inferences
- Row-level security as a declared filter on a permission set plus a per-query *mode* (Filtered/Validated/Ignored) is a [BIG] idea for ManMap repositories: a repository/query could declare `securityFiltering = filtered|ignored`, and the generator would AND a configured predicate into every query.
- BC's audit fields and `SystemRowVersion` confirm ManMap's audit/TCN design; the notable [SMALL] refinement is that the platform *overrides* any user-assigned audit values and that creation fields are immutable.
- The posting pattern (journal lines → check → post → immutable ledger entries + register, all inside one transaction with explicit table locks) is a [BIG] architectural idea for ObjectFlow commands: a command kind that produces append-only entries and forbids modify/delete on them (ledger tables have no OnModify logic by design).
- Number series as a configurable, gap-controlled, date-dependent series vs. SQL sequences that are fast but gap-prone is a [SMALL] but concrete library/option idea (RAP's early/late numbering is the same concern at the language level).

### Gaps
- NumberSequence and permissionset pages are now cited. `InherentPermissions`/`InherentEntitlements` attributes were not fetched.
- No primary page on the "No. Series" codeunit API itself (System Application) was fetched; its usage rests on alguidelines.dev and a community blog.

## Key question 8: Both platforms – state transitions, cross-record consistency, history/change log, background jobs

### Takeaway
Neither platform has a declarative state machine: RAP derives permitted operations from status via dynamic feature control and encodes transitions in actions; BC uses a Status enum plus Release/Reopen codeunits and a table-driven workflow engine. Cross-record consistency is enforced by save-phase validations (RAP) or OnDelete/OnValidate code and `LockTable` (BC); history is a configurable change log (BC) or custom (RAP); background work is bgPF/application jobs/business events (RAP) and Task Scheduler/Job Queue (BC), both strictly post-commit.

### Cited Findings
**State transitions**
- RAP: status-dependent enabling of `update`, `delete`, `Edit`, `deductDiscount`, `acceptTravel`, `rejectTravel` is coded in `FOR INSTANCE FEATURES` by comparing `OverallStatus` (`fc-o-disabled`/`fc-o-enabled`); the transition itself is an action (`acceptTravel`). — [SAP tutorial RAP100 dynamic feature control](https://developers.sap.com/tutorials/abap-environment-rap100-dynamic-feature-control.html)
- BC: document Status values Open ("You can make changes"), Released ("you can't make changes to lines of type Item and Fixed Asset … you can reopen a released document"), Pending Approval, Pending Prepayment; "If you want to post a single open order … without releasing it first, Business Central will automatically release the document when you post it." — [Microsoft Learn, Status field on documents](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-document-status)
- BC document line OnInsert "Makes sure that the status can accept new lines if the document supports different statuses." — [Microsoft Learn training, Use typical data triggers](https://learn.microsoft.com/en-us/training/modules/implement-data-process-model-business-central/3-typical-data-triggers)
- BC approval/state via the workflow engine (event + conditions → response), see Key question 6. — [Microsoft Learn, Walkthrough: workflow events and responses](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-walkthrough-workflow-events-responses)

**Cross-record consistency**

**Background jobs**
- RAP/ABAP Cloud: "Currently we have three different approaches" — Background Processing Framework (bgPF), application jobs, and eventing; bgPF is built on bgRFC, "serializes the background operation in the synchronous session, and the call is queued for execution after a commit"; referenced objects must be serializable; first shipped in release 2308 (BTP ABAP environment / S/4HANA Cloud public edition), also available on-premise from 2023 releases. — [SAP blog, Asynchronous code execution using ABAP Cloud](https://community.sap.com/t5/enterprise-resource-planning-blogs-by-sap/asynchronous-code-execution-using-abap-cloud/ba-p/13572520); [SAP blog, Introducing the Background Processing Framework](https://community.sap.com/t5/technology-blogs-by-sap/introducing-the-background-processing-framework/ba-p/13579056) (search excerpts)
- RAP business events are "a way to notify a consumer asynchronously that a RAP business object has changed". — [SAP Community RAP topic page](https://pages.community.sap.com/topics/abap/rap) (search excerpt)
- BC: Job queue = "an abstraction that uses the task scheduler … to enable end users to view, create, or modify jobs"; a codeunit run by the job queue must declare `trigger OnRun()`, may take `TableNo = "Job Queue Entry"` to read `Rec."Parameter String"`; failure path runs the "Job Queue Error Handler" codeunit in a new background session, stores errors via Error Message Management, retries recurring jobs up to "Maximum No. of Attempts"; "The session runs using the same user/credentials … that sets the job to ready state"; UI calls throw `NavNCLCallbackNotAllowedException` — use `if GuiAllowed() then`. Characteristics table: Task (queued, runs once, any server, survives restarts, no logging) vs Job queue (scheduled, recurrence, logging, admin UI). — [Microsoft Learn, Job queue](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-job-queue)
- BC async options: Page Background Task (read-only, cancellable, bound to a page), `StartSession`, `TaskScheduler.CreateTask`, Job queue; online operational limits apply. — [Microsoft Learn, Async processing overview](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-async-overview)

- Draft lock lifetime (official): exclusive lock on the active instance while a draft exists, "not bound to the ABAP session", default maximum lifetime "15 minutes"; afterwards the draft is unprotected (optimistic phase), a second draft "implicitly deletes the first one", drafts are auto-removed after "28 days" of inactivity; the total ETag detects an outdated draft. — [SAP Learning, Understanding the Draft Concept](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-the-draft-concept)
- Classic RAP lock lifetime: "The lock expires once the lock is actively removed after the successful transaction" or when the ABAP session times out; locks are session-bound, OData is stateless, hence ETags. — [SAP Learning, Understanding Concurrency Control](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-concurrency-control)
- bgPF (SAP blog, search excerpt only; page returns 403): a developer "first creates a class implementing either the transactional or the non-transactional bgPF single-operation interface"; the calling session serializes the operation, which "is queued and then executed after a COMMIT WORK"; on-premise setup needs an inbound bgRFC destination named BGPF. — [SAP blog, Introducing the Background Processing Framework](https://answers.sap.com/t5/technology-blogs-by-sap/introducing-the-background-processing-framework/ba-p/13579056); [SAP blog, Asynchronous code execution using ABAP Cloud](https://groups.community.sap.com/t5/enterprise-resource-planning-blogs-by-sap/asynchronous-code-execution-using-abap-cloud/ba-p/13572520)
- History in RAP: no declarative change log; change documents are written by hand in `save_modified` (additional save) or in the unmanaged create/update/delete methods. — [SAP Community Q&A](https://community.sap.com/t5/technology-q-a/sap-btp-abap-rap-managed-service-change-documents/qaq-p/12526738) (search excerpt)

### Inferences
- Both platforms converge on the same decomposition for "process control": (a) status-derived permissions (RAP feature control; BC Released locks item lines), (b) explicit transition operations (RAP actions; BC Release/Reopen codeunits), (c) checks at commit (RAP validations; BC posting Check codeunit). A declarative state machine for ObjectFlow would be genuinely novel relative to both — [BIG] — and could generate (a) and the skeleton of (b).
- BC's change log is configuration, not code, and is deliberately kept off transactional tables; for ManMap a [SMALL] option "`changeLog = fields(...)`" generating old/new-value rows per mapping is the realistic equivalent, with the same caveat about volume.
- Background work: both platforms insist on *after commit* scheduling and on serializable payloads; a [SMALL]-to-[BIG] ObjectFlow idea is a "deferred command" scheduled from within a command and persisted at check-in.

### Gaps
- No primary SAP Help page or fetchable SAP blog on bgPF or application jobs could be read (community.sap.com/answers.sap.com return 403; a third-party post at blog.fediverse.dedyn.io did not resolve); all RAP background-processing findings are from SAP blog search excerpts. The bgPF interface/class names (`if_bgmc_op_single`, `cl_bgmc_process_factory`) were not verified.
- No source quantifies change-log overhead; Microsoft only warns qualitatively.

## Key question 9: Criticism and known pain points (both platforms)

### Takeaway
Criticism of RAP centres on learning-curve/maturity, strict-mode phase rules, determination/validation timing bugs, draft complexity and the managed/unmanaged decision; criticism of BC centres on performance pitfalls of implicit mechanisms (FlowFields, SIFT maintenance, events disabling bulk SQL, Validated security filtering) and the monolithic posting codeunits.

### Cited Findings
**RAP**
- "many ABAP developers find the idea of generated behavior code 'quite scary'"; whitelisting of released APIs compared to a "horror scenario"; "a data model has no business knowing how its data is going to be interacted with" (UI annotations in CDS); the business object concept "will no doubt get radical changes in future releases"; BOPF in "maintenance mode". — [SAP Press architecture article](https://blog.sap-press.com/exploring-the-architecture-of-the-abap-restful-application-programming-model) (2020, updated 2025)
- Community: "RAP and whole ABAP PaaS seems to be at this moment not mature enough for custom app development"; wish for "more granular options to have custom implementation only when necessary (e.g. custom delete handler)". — [SAP Community Q&A, RAP managed vs unmanaged](https://community.sap.com/t5/technology-q-a/rap-managed-vs-unmanaged/qaq-p/12452273) (search excerpt, undated)
- Brownfield: "existing BAPI logic, custom lock objects, complex validation chains made managed RAP a poor fit"; "trying to force it caused more pain than simply going unmanaged from day one". — [aixsap ?p=772](https://aixsap.com/?p=772) (practitioner blog, search excerpt)
- Timing bugs: determinations vs validations "mixing these up causes subtle bugs"; "the real complexity isn't in the boilerplate — it's in encoding your business rules correctly". — [aixsap ?p=873](https://aixsap.com/?p=873); [dev.to](https://dev.to/oktayates/abap-rap-deep-dive-part-2-implementing-business-logic-validations-and-determinations-in-sap-1mi9) (practitioner blogs)

### Inferences
- The recurring BC lesson is that *implicit* work (auto-calculated FlowFields, SIFT view maintenance, row-by-row triggers because of events) is what bites; ManMap's explicit style (no lazy loading, explicit save) is validated — new declarative aggregates should stay explicit at the call site or at least be visible in the DSL.
- The recurring RAP lesson is that phases need tooling: SAP added `strict(2)` mode precisely to turn phase violations into checks. Checker rules in ObjectFlow (where a rule may read/write, when events may fire) are a cheap [SMALL] win.

### Gaps
- No systematic survey or quantitative data on developer dissatisfaction for either platform; all criticism is anecdotal (SAP Press author, community threads, Microsoft's own performance notes).
- No 2024–2025 forum material specifically about unmanaged draft problems was found.

### Inferences
- The strongest overlaps between the two platforms, and therefore the safest "big ideas", are: (1) rules declared *with trigger conditions and phase* (RAP determinations/validations ≙ BC OnValidate/OnInsert but with a save phase); (2) status-derived permissions (RAP feature control ≙ BC Released status); (3) post-commit events (RAP business events ≙ BC external business events / isolated events); (4) declared aggregates/read models (BC FlowFields ≙ CDS projections). The platform-specific big ideas with no counterpart are RAP draft (persisted UoW) and BC security filters, posting pattern and schema obsoletion.
- Checker-rule candidates (cheap, SMALL) extracted from platform warnings: phase violations (DB write before check-in; event raised before commit), determination cycles over `affects`/field triggers, aggregates referenced without an index hint, deprecated (`ObsoleteState=Pending`) element references, and reads of aggregate fields that were never calculated (BC's "always zero" trap).
