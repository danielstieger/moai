# Java persistence and read-model ecosystem: mechanisms a relational-mapping DSL (ManMap) could adopt

Scope note for the report writer: ManMap today has entity/field/reference/embedded/list mappings, typed repository methods (READONLY/CHECKOUT/CHECKIN/DELETE), mapped queries with where/sortBy/limit/size and refJoin/listJoin, explicit `save with`/`delete with` (no cascade), custom SQL blocks with bound parameters and row mappers into DTOs, AUTOID/OPTIMISTIC_LOCK (TCN)/audit columns/schema hints/ADDITIONAL_TABLE_NAME/BATCH. Missing: lazy loading, migration, pagination, history, soft delete, multi-tenancy. Targets Oracle/MySQL/MariaDB; schema generated from mappings in MPS. Each mechanism below is tagged **[BIG]** or **[small]** relative to that baseline. Several hosts (vladmihalcea.com, blog.jooq.org, red-gate.com, liquibase.com) failed intermittently with DNS errors during research; where a retry succeeded the source is cited, where it did not the item is in Gaps.

## Key Question 1: Typed query construction (jOOQ, Spring Data Specifications, Querydsl) versus hand-assembled SQL strings

### Takeaway
jOOQ's value over string SQL is compile-time checking of the whole statement (tables, columns, types, arity of bind values), plus synthetic clauses that are emulated per dialect (MULTISET, implicit path joins, SEEK, upsert). Specifications/Querydsl offer only type-safe *predicates* composed over an ORM metamodel; Querydsl itself is now a community fork maintained on a best-effort basis.

### Cited Findings

**jOOQ MULTISET (nested collections in one query) [BIG]**
- Declares: a value constructor "collecting the results of a non scalar subquery into a single nested collection value"; example `multiset(select(BOOK.ID, BOOK.TITLE).from(BOOK))` typed as a nested `Result` inside the outer record. — [jOOQ manual: MULTISET](https://www.jooq.org/doc/latest/manual/sql-building/column-expressions/multiset-value-constructor/)
- Runtime: "hardly any dialect supports the MULTISET constructor natively"; jOOQ emulates with JSON/JSONB (e.g. PostgreSQL `jsonb_agg`), XML (DB2, SQL Server, Teradata), native on Oracle and Informix; `Settings.emulateMultiset` selects DEFAULT/XML/JSON/JSONB/NATIVE. MariaDB and MySQL are listed as emulated (JSON); Oracle native. — [jOOQ manual: MULTISET](https://www.jooq.org/doc/latest/manual/sql-building/column-expressions/multiset-value-constructor/)
- Limitations: element ordinals undefined (ordering best effort via ORDER BY); unsupported on ASE, Access, ClickHouse, Firebird, HSQLDB, Redshift, Vertica etc. (renders `/* UNSUPPORTED */`). — [jOOQ manual: MULTISET](https://www.jooq.org/doc/latest/manual/sql-building/column-expressions/multiset-value-constructor/)
- Type-safe mapping of nested results: `Records.mapping(Type::new)` inside `convertFrom(r -> r.map(...))` gives a "Nominally typed result, all type checked!"; changing the projection produces a compile-time error; the reflective `fetchInto(Author.class)` alternative is "Nominally typed result, but not strongly type checked." — [jOOQ manual: ad-hoc converters](https://www.jooq.org/doc/latest/manual/sql-execution/fetching/ad-hoc-converter/)
- DSL note: one declared "read model" query that yields a parent with nested child lists in a single round trip instead of refJoin/listJoin or N+1 — on Oracle native, on MariaDB/MySQL via JSON_ARRAYAGG emulation.

**jOOQ implicit path joins [BIG for a mapping DSL]**
- Declares: navigation along foreign keys through generated methods, e.g. `BOOK.author().FIRST_NAME`, without writing the JOIN; to-one since 3.11, to-many since 3.19. — [jOOQ manual: implicit join](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/implicit-join/)
- Runtime: SQL "nearly identical" to hand-written, "there is no performance penalty to this syntax"; default INNER JOIN for non-nullable to-one parent, LEFT JOIN for nullable parent and for to-many paths; override via `Settings.renderImplicitJoinType` / `renderImplicitJoinToManyType`. Paths with a common prefix share the join. — [jOOQ manual: implicit join](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/implicit-join/)
- Limitations: "Implicit JOINs can currently only be used to access columns, not to produce joins"; joins are appended after the statement is built, so VisitListeners don't see them. — [jOOQ manual: implicit join](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/implicit-join/)
- DSL note: ManMap already knows the FK graph from reference mappings; where-filters and projections could use dotted paths (`order.customer.name`) and have the generator derive joins, with nullability deciding INNER vs LEFT.

**jOOQ SEEK clause (keyset pagination) — see KQ4.** Also "cannot combine the SEEK clause with the OFFSET clause." — [jOOQ manual: SEEK](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/seek-clause/)

**jOOQ batch API [small; ManMap has BATCH]**
- Two modes: several different statements in one batch, or one statement with many bind rows via `create.batch(insert...).bind(...).bind(...)`; caveat: dummy bind values must be supplied for the template and later `bind()` calls have "no type safety provided by jOOQ". — [jOOQ manual: batch execution](https://www.jooq.org/doc/latest/manual/sql-execution/batch-execution/)

**Spring Data JPA Specifications [small/medium]**
- Declares: `Specification<T>.toPredicate(Root<T>, CriteriaQuery<?>, CriteriaBuilder)`; since 4.0 a query-type-agnostic `PredicateSpecification<T>.toPredicate(From<?,T>, CriteriaBuilder)`; composition with `.and()/.or()`; `UpdateSpecification`/`DeleteSpecification` bind the same predicates to `CriteriaUpdate`/`CriteriaDelete`. "Specifications become most valuable when composed". — [Spring Data JPA: Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html)
- Fluent API: `findBy(spec, q -> q.as(Projection.class).page(...))` with intermediates `sortBy, limit, as, project` and terminals `first, one, all, page, slice, scroll, stream, count, exists`. — [Spring Data JPA: Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html)
- Limitation: classic `Specification` "is tied a particular query type (select, update, delete) as per Criteria API restrictions". — [Spring Data JPA: Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html)
- DSL note: a named, reusable, composable *filter fragment* concept (predicate declared once, combined with and/or in several repository methods, also usable in bulk update/delete).

**Spring Data Query by Example [small]**
- Probe object + `ExampleMatcher` (string matching EXACT/STARTING/ENDING/CONTAINING, ignoreCase, ignore paths, include nulls, `matchingAny`); limitations: "No support for nested or grouped property constraints", "No support for matching collections or maps", "Exact matching for other property types", "Regex-matching is not supported by JPA". — [Spring Data JPA: Query by Example](https://docs.spring.io/spring-data/jpa/reference/repositories/query-by-example.html)
- DSL note: a generic "filter by template entity" repository method is cheap to generate; useful for search masks, but intentionally shallow.

**Querydsl [small, declining]**
- "Querydsl is a framework that enables the construction of statically typed SQL-like queries through its fluent API"; Q-classes generated by an annotation processor; `QuerydslPredicateExecutor`; web binding from request parameters with `@QuerydslPredicate`. — [Spring Data JPA: core extensions](https://docs.spring.io/spring-data/jpa/reference/repositories/core-extensions.html)
- Status: "Querydsl maintenance has slowed down to a point where the community has forked the project under OpenFeign ... Spring Data supports the fork on a best-effort basis." — [Spring Data JPA: core extensions](https://docs.spring.io/spring-data/jpa/reference/repositories/core-extensions.html); a Spring Data issue proposing to switch to the fork was declined and noted the original's last release as July 2021 — [spring-data-jpa#3335](https://github.com/spring-projects/spring-data-jpa/issues/3335)

**MyBatis dynamic SQL (XML tags) [small; comparable to ManMap's control-flow SQL blocks]**
- Elements `if`, `choose/when/otherwise`, `trim/where/set`, `foreach`, `bind`, `_databaseId` for vendor branches; `where` emits WHERE only if content exists and strips leading AND/OR; the docs themselves admit "Dynamic SQL can be downright painful to deal with". — [MyBatis 3: Dynamic SQL](https://mybatis.org/mybatis-3/dynamic-sql.html)
- MyBatis Dynamic SQL (Java library): "a typesafe SQL templating library"; conditions carry a filter: "if a condition's 'filter' method is not satisfied, then the condition will not be rendered"; `isEqualToWhenPresent(x)` renders only when non-null; "If all conditions fail to render, then the entire where clause will be dropped" and by default `NonRenderingWhereClauseException` is thrown to protect against updating all rows. — [MyBatis Dynamic SQL: conditions](https://mybatis.org/mybatis-dynamic-sql/docs/conditions.html), [introduction](https://mybatis.org/mybatis-dynamic-sql/docs/introduction.html)
- DSL note: "optional condition" semantics (a where-term that disappears when its parameter is null, with a safety rule against an empty WHERE) is a small, high-value addition to ManMap's where filter and to its custom SQL blocks.

### Inferences
- The gain of typed query DSLs over strings is less about expressiveness than about *checked structure*: ManMap already has a model of tables/columns, so the missing piece is checking projections, join paths and bind arity in the editor — which MPS can do natively; the jOOQ features worth copying are the synthetic clauses (MULTISET, path joins, SEEK, upsert) because they are each a small declaration with a large, dialect-specific SQL expansion.
- Spring Data's fluent `findBy(spec, q -> ...)` shows a useful separation: the *filter* (spec), the *shape* (projection class), and the *window* (page/slice/scroll) are three orthogonal parameters of one query; ManMap's mapped query could adopt the same three-axis structure.

### Gaps
- jOOQ derived tables and DAO/UpdatableRecord APIs were not fetched (judged low marginal value); not cited.
- The jOOQ 3.19 to-many path join blog post and current jOOQ version page were not fetched; version claims come from the manual pages only.

## Key Question 2: Read models (Blaze-Persistence Entity Views, Spring Data projections, Hibernate @Subselect, jOOQ MULTISET)

### Takeaway
All four approaches declare a *shape* separately from the entity mapping and let the engine derive the SELECT (and joins) from the shape; Blaze-Persistence goes furthest with nested subviews, per-collection limits, keyset pagination and updatable views with declared flush/cascade semantics.

### Cited Findings

**Blaze-Persistence Entity Views [BIG]**
- Declares: "entity views are defined as interfaces or abstract classes mostly containing just getter definitions"; `@EntityView(Cat.class) interface CatNameView { @IdMapping Long getId(); @Mapping("name") String getCatName(); }`; without `@Mapping` "a default mapping to the same named entity attribute will be created"; `@Mapping` accepts expressions such as `SIZE(kittens)`; subviews when the getter type is itself an entity view (default LEFT join); collections `Set<SimpleCatView>` or `@Mapping("kittens.name") Set<String>`; `@Limit(limit="5", order={"age DESC"})` fetches top-N per parent. — [Blaze-Persistence Entity View manual](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- Runtime: applied to a criteria query `evm.applySetting(EntityViewSetting.create(CatNameView.class), cb)`; filters via `@AttributeFilter(ContainsFilter.class)` and `setting.addAttributeFilter("name","Kitty")`; pagination `EntityViewSetting.create(View.class, firstResult, maxResults)` returning `PagedList`. — [Blaze-Persistence Entity View manual](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- Keyset pagination: "Supplying a keyset page allows the runtime to choose keyset pagination instead of offset pagination"; `setting.withKeysetPage(previousKeysetPage)`; `list.getKeysetPage()`; for stateless REST the KeysetPage is serialized to the client. — [Blaze-Persistence Entity View manual (offset 100000)](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- Updatable views: `@UpdatableEntityView(mode=PARTIAL|LAZY|FULL, strategy=QUERY|ENTITY)`; PARTIAL "will only flush values of actually changed attributes"; QUERY "will flush changes by executing JPQL DML statements"; `@CreatableEntityView` validated "against the backing model regarding it's persistability"; cascade controlled by `@UpdatableMapping(cascade=...)`: "Updates done to mutable values of an attribute are only flushed if the CascadeType.UPDATE is enabled"; orphan removal "also implies delete cascading"; mapping must match the entity's cascade settings or it is an error; `lockMode` AUTO/OPTIMISTIC/PESSIMISTIC_READ/PESSIMISTIC_WRITE/NONE where AUTO "Uses the version field of the entity type". — [Blaze-Persistence Entity View manual (offsets 100000, 200000)](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- Spring Data integration: `EntityViewRepository<View, Id>`, `KeysetAwarePage<T> findAll(Pageable)`, "the Pageable should be an instance of KeysetPageable if keyset pagination should be used", last sort field must be unique. GraphQL integration builds settings from the selection set so "unrequested fields and their joins are skipped". — [Blaze-Persistence Entity View manual (offset 200000)](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- Limitations: mapping managed entities directly "defeats the purpose of entity views and can lead to lazy loading issues"; flat views with JOIN fetch cannot hold collections in certain positions; architecture overview says updatable views "are still in flux"; keyset over REST needs "custom implementations of the KeysetPage and Keyset interfaces". — [Blaze-Persistence Entity View manual](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- DSL note: a declared "View" concept in ManMap (interface-like shape over an EntityMapping, with subviews, collection limits, filters) from which the generator derives SELECT/joins; updatable views show how to declare partial write-back with explicit cascade and lock mode per view — i.e. CHECKOUT/CHECKIN of a *shape* rather than a whole entity.

**Spring Data interface/DTO projections [small/medium]**
- Interface projections: "The query execution engine creates proxy instances of that interface at runtime"; closed projections allow "Spring Data can optimize the query execution, because we know about all the attributes"; open projections (`@Value("#{target.firstname + ' ' + target.lastname}")`) disable optimization; DTO/record projections: "no proxying happens and no nested projections can be applied"; dynamic projections via `Class<T>` parameter; nested interface projections are allowed but for derived queries "Any nested properties resolving to joins select the entire nested property causing the full join to materialize." — [Spring Data JPA: Projections](https://docs.spring.io/spring-data/jpa/reference/repositories/projections.html)
- DSL note: ManMap already has no-key mappers into DTOs for custom SQL; the missing step is deriving the column list and joins *from* the DTO/view shape for mapped queries (closed projection), and allowing one mapped query to be executed with several shapes (dynamic projection).

**Hibernate @Subselect / @Immutable [small]**
- Javadoc: an immutable, read-only entity "mapped to a given SQL select expression", presented as an alternative to a database view mapped with `@Table`; pair with `@Synchronize("details")` so Hibernate flushes pending changes to the underlying tables before querying. — [Hibernate javadoc: @Subselect](https://docs.hibernate.org/orm/7.4/javadocs/org/hibernate/annotations/Subselect.html)
- Practitioner guidance: annotate `@Immutable`, omit setters; the subselect must be a constant SQL text (no parameters), so a DTO projection or view is usually preferable. — [Thorben Janssen: map an entity to a query](https://thorben-janssen.com/hibernate-tips-how-to-map-an-entity-to-a-query/), [Vlad Mihalcea: map entity to view or SQL query](https://vladmihalcea.com/map-jpa-entity-to-view-or-sql-query-with-hibernate)
- DSL note: an EntityMapping whose "table" is a SQL select (or a generated DB view) — read-only mapping, with a declared list of base tables for flush ordering/cache invalidation.

**jOOQ MULTISET for nested DTO graphs** — see KQ1; one SQL statement, JSON/XML emulated on MariaDB/MySQL, native on Oracle. — [jOOQ manual: MULTISET](https://www.jooq.org/doc/latest/manual/sql-building/column-expressions/multiset-value-constructor/)

### Inferences
- Read-model declarations are the single most reused idea across jOOQ, Spring Data and Blaze: the shape drives the SELECT. For ManMap this would turn READONLY repository methods into "load View V where ..." with the join set derived rather than hand-declared with refJoin/listJoin.
- Blaze's `@Limit` per collection and GraphQL "fetch only selected fields" are the two features that go beyond simple projections and are hard to hand-write in SQL (window functions / lateral joins per parent).

### Gaps
- Blaze-Persistence's `@EntityViewInheritance`, flush-mode interaction with optimistic locking, and the final ~50k characters of its manual were not read.
- No independent benchmark comparing MULTISET-JSON emulation vs. multiple selects on MariaDB was found.

## Key Question 3: Loading strategy (JPA entity graphs, Hibernate batch/subselect fetching, fetch profiles, Jmix fetch plans)

### Takeaway
The ecosystem converged on *declaring the graph to load per use case* (entity graph, fetch profile, fetch plan) and on treating lazy loading as a fallback that causes N+1; Jmix's "partial entity throws on unfetched attribute" is the closest existing analogue to ManMap's "unloaded reference throws".

### Cited Findings

**JPA entity graphs [medium]**
- `var graph = session.createEntityGraph(Book.class); graph.addSubgraph(Book_.publisher); session.byId(Book.class).withFetchGraph(graph).load(id)` adds a `left outer join`; a fetch graph loads exactly the listed associations, a load graph adds them to EAGER-mapped ones; Hibernate's guide calls the JPA API "untypesafe and unnecessarily verbose" and named graphs via annotations "so verbose that it's just not worth using". — [Hibernate 6.6 Introduction (offset 100000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- DSL note: a per-repository-method "load graph" declaration (which references/lists to populate) is natural in ManMap, where the graph is already explicit via refJoin/listJoin; naming and reusing graphs is the increment.

**Hibernate batch and subselect fetching [small]**
- Batch fetching "fetches associated rows in batches of primary keys" via `hibernate.default_batch_fetch_size`, `@BatchSize(size=20)` or `setFetchBatchSize()`; subselect fetching re-runs the original query as a subselect via `@Fetch(SUBSELECT)` or `hibernate.use_subselect_fetch`; "While batch fetching might mitigate problems involving N+1 selects, it won't solve them." Join fetching is preferred. — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- DSL note: ManMap's listJoin could gain a strategy switch (JOIN vs. batched IN-list vs. subselect) chosen per method; the IN-list variant avoids row multiplication on wide parents.

**Hibernate fetch profiles [small]**
- `@FetchProfile(name="EagerBook")` on a class plus `@FetchProfileOverride(profile=..., mode=JOIN|SUBSELECT)` on associations; enabled per session `session.enableFetchProfile(...)`; "a fetch profile—unlike an entity graph—isn't 'rooted' at any particular entity"; "The one and only advantage unique to fetch profiles is that they let us very selectively request subselect fetching." — [Hibernate 6.6 Introduction (offset 300000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)

**Jmix fetch plans [BIG as a design reference]**
- A fetch plan defines "what object graph should be eagerly loaded from the database in a particular operation"; declared inline in XML screen descriptors, via `fetchPlans.builder(Order.class)`, or in a shared `fetch-plans.xml` registry retrieved by name; built-ins `_local` (non-reference attributes), `_instance_name`, `_base` (local + instance name + embedded); `extends` composes plans; nested `fetchPlan` on properties controls depth. — [Jmix: Fetching data](https://docs.jmix.io/jmix/data-access/fetching.html)
- Partial entities: attributes omitted from the plan are left empty and "Cannot get unfetched attribute [foo] from detached object" is thrown on access; "We recommend using partial fetch plans sparingly"; id and version are always loaded; lazy loading exists but "can cause N+1 queries". — [Jmix: Fetching data](https://docs.jmix.io/jmix/data-access/fetching.html)
- DSL note: named, inheritable fetch plans attached to repository methods; ManMap's "unloaded reference throws" is exactly Jmix's partial-entity contract, so the two ideas compose without lazy loading.

**N+1 and Open Session in View critique (why explicit plans)**
- N+1: "`@ManyToOne` and `@OneToOne` associations use `FetchType.EAGER` by default", each extra query is fast so slow-query logs miss it; fix with `JOIN FETCH` or joins in native SQL; detect N+1 in tests. — [Vlad Mihalcea: N+1 query problem](https://vladmihalcea.com/n-plus-1-query-problem/)
- OSIV: "every additional statement issued from the UI rendering phase is executed in auto-commit mode"; "The UI layer is limited to navigating associations which can, in turn, trigger N+1 query problems"; "the database connection is held throughout the UI rendering phase"; recommended alternative: "A DTO projection forces the application developer to fetch just the required data set"; "The Open Session in View is a solution to a problem that should not exist in the first place." — [Vlad Mihalcea: OSIV anti-pattern](https://vladmihalcea.com/the-open-session-in-view-anti-pattern/)

### Inferences
- ManMap's no-lazy-loading stance is vindicated by the OSIV/N+1 critique; what is missing is the *vocabulary* to say per use case which graph to load (named plan + strategy per edge), which both Hibernate and Jmix provide in some form.
- Batch fetching by IN-list is the only alternative to joins that does not require lazy proxies, so it is the right second strategy for a DSL without a persistence context.

### Gaps
- Hibernate second-level cache: only summarized (opt-in `@Cache(usage=READ_WRITE)`, external provider required, query cache "only rarely an efficient thing to do") — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html); no deeper coverage because a cache needs a session/identity map that ManMap lacks.
- Jmix annotation-based fetch plan declaration not covered by the fetched page.

## Key Question 4: Pagination, keyset pagination, counting, slice vs page

### Takeaway
Three result-window types are standard: Page (data + count query), Slice (size+1 fetch, no count), Window/keyset (seek predicate on sort keys + PK, no OFFSET). Keyset needs non-null sort keys, a matching index and sort keys present in the projection; it cannot jump to page N.

### Cited Findings

**Spring Data Page / Slice / List / Limit [small]**
- `Page<User> findByLastname(String, Pageable)`: "A Page knows about the total number of elements and pages available. It does so by the infrastructure triggering a count query"; `Slice` "knows only about whether a next Slice is available"; `List` with `Pageable` issues no count query; Slice fetches `pageSize + 1` rows; `Limit` parameter and `Top`/`First` keywords "may not be mixed with a Limit parameter"; `Pageable` and `Sort` or `Pageable` and `Limit` cannot be combined. — [Spring Data JPA: query method details](https://docs.spring.io/spring-data/jpa/reference/repositories/query-methods-details.html)
- DSL note: ManMap has limit/size; adding a *result window* parameter type (page/slice/keyset) with generated count query or size+1 probe is a small generator change.

**Keyset scrolling (Spring Data Window) [medium]**
- Scrolling "consists of a stable sort, a scroll type (Offset- or Keyset-based scrolling) and result limiting"; `ScrollPosition` is exclusive; `WindowIterator` wraps the loop; keyset "rewrites the criteria clause to include all sort fields and the primary key so that the database can leverage potential indexes". — [Spring Data Commons: Scrolling](https://docs.spring.io/spring-data/commons/reference/repositories/scrolling.html)
- Requirements: "Keyset-Filtering requires the keyset properties (those used for sorting) to be non-nullable"; "works best when your database contains an index that matches the sort fields"; sort properties must be returned by the query and mapped in the entity/projection; uniqueness is ensured automatically by appending the primary key. — [Spring Data Commons: Scrolling](https://docs.spring.io/spring-data/commons/reference/repositories/scrolling.html)
- "Offset-based queries becomes inefficient when the offset is too large because the database still has to materialize the full result." — [Spring Data JPA: query method details](https://docs.spring.io/spring-data/jpa/reference/repositories/query-methods-details.html)

**jOOQ SEEK [medium]**
- `.orderBy(T.VALUE, T.ID).seek(lastValue, lastId).limit(5)` emits `WHERE (value, id) > (2, 533) ORDER BY value, id LIMIT 5`; jOOQ "emulates row value expression predicates for you, in those databases that do not support them"; "you cannot combine the SEEK clause with the OFFSET clause". — [jOOQ manual: SEEK](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/seek-clause/)
- Rationale: "the Seek Method does not skip records before an OFFSET, but it skips records until the last record previously fetched"; offset paging must read every skipped row while seek is "a simple range scan on an index"; "fetching higher page numbers is significantly faster"; mixed sort directions need the expanded `(a < x) OR (a = x AND b > y)` form; ties lose rows unless a unique column is in ORDER BY; NULLS FIRST/LAST complicate the predicate; page numbers lose meaning. — [jOOQ blog: seek method](https://blog.jooq.org/faster-sql-paging-with-jooq-using-the-seek-method/)

**Blaze-Persistence keyset** — runtime switches between offset and keyset based on supplied `KeysetPage`; Spring Data `KeysetAwarePage`/`KeysetPageable`; last sort field must be unique. — [Blaze-Persistence Entity View manual](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)

### Inferences
- For a DSL that generates SQL per dialect, keyset pagination is attractive: the generator knows the sort columns and PK, can refuse nullable sort columns at edit time, emit the expanded predicate for mixed directions (MySQL/MariaDB lack full row-value comparison semantics with indexes; Oracle lacks row-value `<` entirely), and emit a size+1 probe for "has next".
- Counting should be a separate, optional declaration (Page vs Slice), since the count query is the costly part.

### Gaps
- No official statement was found on how Spring Data handles backward keyset scrolling; the Commons page does not cover it.

## Key Question 5: Historisation (Envers, SQL:2011 system versioning in MariaDB, Oracle Flashback/Temporal Validity, bitemporal patterns)

### Takeaway
Two families exist: application-level audit tables (Envers: `_AUD` + REVINFO, two storage strategies, a query API over history) and database-level system versioning (MariaDB `WITH SYSTEM VERSIONING` + `FOR SYSTEM_TIME AS OF`; Oracle Flashback Query/Version Query/Flashback Time Travel). Both are transaction-time only; valid-time (application-time periods, Oracle Temporal Validity) is needed for bitemporal, which Fowler advises to avoid unless retroactive change is a real requirement.

### Cited Findings

**Hibernate Envers [BIG]**
- Declares: `@Audited` on the entity; "By default, Hibernate adds the '_AUD' suffix to the table name"; audit table holds PK, audited fields, REV and REVTYPE; "Envers uses the integer values 0, 1 and 2 to store that an entity was added, updated or deleted"; REVINFO stores "only the revision number as an integer and the creation timestamp as a long" by default; each transaction creates one revision; audit tables must exist ("Hibernate expects to find the aforementioned audit tables in your database, otherwise, Envers will fail"). — [Thorben Janssen: Envers getting started](https://thorben-janssen.com/hibernate-envers-getting-started/), [Vlad Mihalcea: audit log with Envers](https://vladmihalcea.com/the-best-way-to-implement-an-audit-log-using-hibernate-envers/)
- Query API: `AuditReaderFactory.get(em)`; `getRevisions(Class,id)`, `find(Class,id,revision)`, `find(Class,id,Date)` (largest REV at or before the date); `forRevisionsOfEntity(...)` returns all snapshots; `forEntitiesAtRevision(...)` loads the state at a revision. — [Thorben Janssen: Envers getting started](https://thorben-janssen.com/hibernate-envers-getting-started/), [Vlad Mihalcea: audit log with Envers](https://vladmihalcea.com/the-best-way-to-implement-an-audit-log-using-hibernate-envers/)
- Strategies: DefaultAuditStrategy — one audit row per change, but a point-in-time read uses a correlated `MAX(REV)` subquery, "definitely not very efficient" for large logs; ValidityAuditStrategy (`org.hibernate.envers.audit_strategy`) adds `REVEND` (null = current), costs an extra UPDATE per change, reads become a range condition — "Much better than using a correlated subquery!"; index REV and REVEND. On delete, all columns except the identifier are null (REVTYPE DEL). — [Vlad Mihalcea: audit log with Envers](https://vladmihalcea.com/the-best-way-to-implement-an-audit-log-using-hibernate-envers/); javadoc: "persisting audit information is slightly slower due to an extra update required" while "retrieval is considerably faster" — [Hibernate javadoc: ValidityAuditStrategy](https://docs.hibernate.org/orm/7.0/javadocs/org/hibernate/envers/strategy/internal/ValidityAuditStrategy.html)
- Known issue: ValidityAuditStrategy struggled with non-generated PKs when a row is deleted and re-inserted with the same key (HHH-6209; resolution not confirmed). — [Hibernate JIRA HHH-6209](https://hibernate.atlassian.net/browse/HHH-6209)
- AuditReader (primary source, 6.6 javadoc): "Provides access to past versions of audited entities based on a global revision"; `find(Class, id, Number revision)` returns the entity at that revision or null; `find(Class, id, Date|LocalDateTime)` returns the version "from the latest revision created on or before the given time" and throws `RevisionDoesNotExistException` before the first revision; `getRevisions(Class, id)` "sorted in ascending order (so older revisions come first)"; `getRevisionNumberForDate(...)` "returns the number of the highest revision, which was created on or before the given date"; `createQuery()` yields an `AuditQueryCreator`; overloads with `includeDeletions` search deleted entities; returned entities "may be partially filled if not all properties are audited"; `getCrossTypeRevisionChangesReader()` needs `org.hibernate.envers.track_entities_changed_in_revision` or a custom revision entity. — [Hibernate 6.6 javadoc: AuditReader](https://docs.hibernate.org/orm/6.6/javadocs/org/hibernate/envers/AuditReader.html)
- Configuration properties (official docs, older version 4.2 — the property table is unchanged in later guides but was not re-verified for 6.6): `org.hibernate.envers.audit_strategy` defaults to `DefaultAuditStrategy` (stores only the revision at which an entity was modified) vs `ValidityAuditStrategy` (stores start and end revision); `audit_strategy_validity_end_rev_field_name` (default `REVEND`) and `audit_strategy_validity_store_revend_timestamp` apply only to the validity strategy; `store_data_at_delete` defaults to false — when true the entity data is written to the delete revision instead of only the id with null properties, "at the cost of storing the pre-deletion data twice". — [Hibernate 4.2 Developer Guide ch. 15 Envers](https://docs.hibernate.org/orm/4.2/devguide/en-US/html/ch15.html), [Envers 3.6 configuration reference](https://docs.hibernate.org/envers/3.6/reference/en-US/html/configuration.html)
- DSL note: an `AUDITED` option on an EntityMapping that generates the `_AUD` table (ManMap's ADDITIONAL_TABLE_NAME already generates a second table), a REVINFO table, the extra INSERT in CHECKIN/DELETE, and a repository method kind `AS OF revision/timestamp`; choose the validity (REV/REVEND) layout since reads dominate.

**MariaDB system-versioned tables (SQL:2011) [BIG — ManMap targets MariaDB]**
- Declares: `CREATE TABLE t (x INT) WITH SYSTEM VERSIONING;` (hidden `ROW_START`/`ROW_END`) or the full form with `GENERATED ALWAYS AS ROW START/END` + `PERIOD FOR SYSTEM_TIME`; `ALTER TABLE t ADD SYSTEM VERSIONING` / `DROP SYSTEM VERSIONING`; per-column `WITHOUT SYSTEM VERSIONING` excludes a column. — [MariaDB docs: System-versioned tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)
- Runtime: "A history row is created for every UPDATE statement that includes a versioned column in its SET list"; queries `FOR SYSTEM_TIME AS OF ...`, `BETWEEN ... AND ...` (inclusive), `FROM ... TO ...` (end exclusive), `ALL`; session/global `system_versioning_asof` applies an implicit AS OF to all queries (no effect on DML); InnoDB transaction-precise history with `BIGINT UNSIGNED` row columns and `AS OF TRANSACTION n`. — [MariaDB docs: System-versioned tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)
- Storage: `PARTITION BY SYSTEM_TIME` (by `LIMIT` rows or `INTERVAL`, `AUTO` since 10.9.1) separates history so current-data queries prune; `DELETE HISTORY FROM t BEFORE SYSTEM_TIME ...` needs the `DELETE HISTORY` privilege; `TRUNCATE` fails (error 4137). — [MariaDB docs: System-versioned tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)
- Limitations: "Tables that use system-versioning implicitly add the row_end column to the Primary Key" (replication duplicate-key risk; `secure_timestamp=YES` on replicas); `mariadb-dump` needs `-H/--dump-history` (10.11+) to include history; versioning clauses cannot be applied to generated columns; history in the same table "increases the size of the table" and slows scans; implicit-to-explicit row column conversion only from 11.7. — [MariaDB docs: System-versioned tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)
- Bitemporal: "Bitemporal tables are tables that use versioning both at the system and application-time period levels" (`PERIOD FOR application_time(date_1, date_2)` + `PERIOD FOR system_time` + `WITH SYSTEM VERSIONING`); `system_time` "cannot be used in DELETE FOR PORTION or UPDATE FOR PORTION statements". — [MariaDB docs: Bitemporal tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/bitemporal-tables)
- DSL note: a `SYSTEM_VERSIONED` option per EntityMapping that emits the clause in the generated DDL, plus a query modifier `as of <timestamp>` on READONLY methods — history for free on MariaDB with no extra write statements; the application still cannot see *who* changed a row unless MODIFIEDBY is a versioned column (it is, by default).

**Oracle Flashback / Flashback Time Travel / Temporal Validity [medium]**
- Flashback Query: "retrieves data as it existed at an earlier time ... through a time stamp or System Change Number (SCN)"; `SELECT * FROM employees AS OF TIMESTAMP ...`; a timestamp "might be up to 3 seconds earlier than the time you specify". — [Oracle 23ai: Flashback Technology](https://docs.oracle.com/en/database/oracle/oracle-database/23/adfns/flashback.html)
- Flashback Version Query: `VERSIONS BETWEEN {SCN|TIMESTAMP} start AND end` with pseudocolumns `VERSIONS_STARTSCN/STARTTIME`, `VERSIONS_ENDSCN/ENDTIME`, `VERSIONS_XID`, `VERSIONS_OPERATION` (I/D/U); "A row version is created whenever a COMMIT statement is executed." — [Oracle 23ai: Flashback Technology](https://docs.oracle.com/en/database/oracle/oracle-database/23/adfns/flashback.html)
- Flashback Time Travel (formerly Data Archive): `CREATE FLASHBACK ARCHIVE fla2 TABLESPACE tbs2 RETENTION 2 YEAR; ALTER TABLE employee FLASHBACK ARCHIVE;` "By default, Flashback Archive is not enabled for any table"; `BLOCKCHAIN FLASHBACK ARCHIVE` for tamper-evident history; restrictions: "Adding or enabling a Constraint (including Foreign Key Constraint) on a table that has been enabled for Flashback Archive fails with ORA-55610", limited DDL, reserved column names `STARTSCN, ENDSCN, RID, XID, OP, OPERATION`, wait up to 5 minutes before flashback-querying a newly enabled table; plain Flashback Query (undo-based) becomes invalid after structure-changing DDL (ORA-01466). — [Oracle 23ai: Flashback Technology](https://docs.oracle.com/en/database/oracle/oracle-database/23/adfns/flashback.html)
- Temporal Validity (valid time): `PERIOD FOR valid_period (start_date, end_date)` in CREATE/ALTER TABLE, or `ADD PERIOD FOR p` with "system generated hidden columns"; queries `AS OF PERIOD FOR p <date>` and `VERSIONS PERIOD FOR p BETWEEN a AND b`; combinable with `AS OF SCN` in one statement (bitemporal); implemented as a query rewrite into `IS NULL / <= / >` predicates ("the statement has been rewritten to a form we might have used prior to 12c"). — [ORACLE-BASE: Temporal Validity 12cR1](https://oracle-base.com/articles/12c/temporal-validity-12cr1) (secondary source; the official 23ai design-basics page returned 404 during research)
- DSL note: on Oracle the same `SYSTEM_VERSIONED` option would map to `FLASHBACK ARCHIVE`, but the FK restriction (ORA-55610) and licensing need checking; valid-time columns are an ordinary mapping with generated `AS OF PERIOD FOR` filters.

**Bitemporal pattern (Fowler) [design guidance]**
- Two dimensions: "actual" (valid) history and "record" (transaction) history; a lookup needs both dates, e.g. `salaryAt(actualDate, recordDate)`; record history is append-only; "Actual history is no longer append-only, we go back and make retroactive changes." Implementations: bitemporal rows with two date ranges (awkward, use a helper library) or bitemporal events with read models; "if events need to support bitemporal history, they need to be bitemporal themselves." Advice: it "does complicate a system quite significantly", so avoid it when possible by refusing retroactive changes or recording inputs alongside actions; educating users is "One of the hardest parts"; native temporal DB support is niche. — [Martin Fowler: Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)

### Inferences
- For ManMap's targets the cheapest history is database system versioning on MariaDB (DDL option + `AS OF` query modifier), while Oracle needs Flashback Archive with FK caveats; an Envers-style `_AUD` table is the only portable option across Oracle/MySQL/MariaDB (MySQL has no system versioning) and fits ManMap's explicit-save model (the generator adds one INSERT per CHECKIN/DELETE).
- Valid-time (application-time) is a modelling decision (two date columns + period semantics) rather than an infrastructure feature; it should stay optional and explicit, per Fowler.

### Gaps
- Oracle licensing/edition requirements for Flashback Time Travel were not found in the fetched page.
- The fetchable part of the Hibernate 6.6 user guide single page (472k chars) stops before the Envers chapter; Envers behaviour was therefore cited from the 6.6 AuditReader javadoc, the 4.2 developer guide property table and practitioner articles. `AuditQueryCreator` method semantics (forEntitiesAtRevision, forRevisionsOfEntity, forEntitiesModifiedAtRevision, relation traversal limits) and `global_with_modified_flag` remain uncited from a current primary source.
- The official Oracle 23ai "Temporal Validity Support" page could not be located by search (only 12c-era secondary sources and an Oracle CoreTec blog stating the feature is "available in every edition" since 12.1 — [blogs.oracle.com/coretec](https://blogs.oracle.com/coretec/?p=1002)); a 2015 Oracle forum post cites a documented restriction that temporal validity was not supported in a multitenant container database (CDB) — current status unverified — [Oracle Forums](https://forums.oracle.com/ords/apexds/post/temporal-validity-in-otn-developer-vm-7712).
- MariaDB `UPDATE/DELETE FOR PORTION OF` and `WITHOUT OVERLAPS` syntax details were on a page not fetched.

## Key Question 6: Soft delete, multi-tenancy, row-level filters, locking, cascade semantics and orphan removal

### Takeaway
Hibernate 6.4+ made soft delete and discriminator multi-tenancy declarative (`@SoftDelete`, `@TenantId`) with automatic filtering of *entity* queries but not native SQL; filters are session-scoped predicates that deliberately skip `find()` and `@ManyToOne`. Cascade/orphanRemoval are widely criticized when applied by default, which supports ManMap's explicit parent-then-children save.

### Cited Findings

**Hibernate @SoftDelete (6.4+) [medium]**
- Purpose: "perform a 'soft delete' where a column is updated to indicate that the row is no longer active"; "should be highly preferred" over filter/`@Where`/custom event hacks; three parts: strategy, indicator column, conversion. Strategies `ACTIVE` ("A true value in the database indicates that the row is active") and `DELETED` (default; "A true value in the database indicates that the row is deleted"); default columns `active`/`deleted`; converters `NumericBooleanConverter` (0/1), `YesNoConverter` (N/Y), `TrueFalseConverter` (F/T), resolved from column type when not specified; "an appropriate check constraint may be applied to the column". — [Hibernate 6.6 User Guide §3.12 Soft Delete](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html)
- Scope: entity hierarchies (indicator on the root table, "the soft delete applies to all inheritance types"), collection tables of `@ElementCollection` and `@ManyToMany` ("The soft delete applies to the collection table row"), package level; `@SoftDelete` on `@OneToMany` "will throw an exception"; soft-deletable targets of to-many associations are "handled transparently". Annotation is `@Incubating`, added in 6.4; "The converter should never return null." — [Hibernate 6.6 User Guide §3.12](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html), [Hibernate javadoc: @SoftDelete](https://docs.hibernate.org/orm/6.6/javadocs/org/hibernate/annotations/SoftDelete.html)
- Introduction guide: `@SoftDelete(columnName="deleted", converter=TrueFalseConverter.class)`; marks rows "with an SQL update rather than an SQL delete". — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- Query behaviour (secondary sources): on `remove()` Hibernate sets the indicator column and adds a predicate that hides soft-deleted rows from JPQL, Criteria and other generated statements; the default expects a boolean `deleted` column. — [Thorben Janssen: implement soft delete with Hibernate](https://thorben-janssen.com/implement-soft-delete-hibernate/). A Hibernate forum thread reports that the automatic filter cannot be bypassed through Hibernate APIs (described there as intended) and that native SQL is the way to read deleted rows back — reported as a maintainer answer, not verified against the user guide. — [Hibernate Discourse: retrieve all records with @SoftDelete](https://discourse.hibernate.org/t/when-an-entity-is-annotated-with-softdelete-how-to-retrieve-all-the-records/9622)
- DSL note: a `SOFT_DELETE(column, strategy, converter)` option per EntityMapping: DELETE methods become UPDATEs, every generated SELECT gets the predicate, custom SQL blocks do not (mirror Hibernate: native SQL is the developer's job) — and a `DELETED_ALSO`/`ONLY_DELETED` query modifier for admin views.

**Hibernate @Filter / @FilterDef / @SQLRestriction [small]**
- "A filter is a named, globally-defined, parameterized restriction on the data that is visible in a given session"; `@FilterDef(name="ByRegion", parameters=@ParamDef(name="region", type=String.class), defaultCondition="region = :region")` at package level, `@Filter(name="ByRegion")` on entities, `session.enableFilter("ByRegion").setParameter(...)`; since 6.5 `autoEnabled=true` with a `Supplier` for parameters; limitations: not applied to `@ManyToOne` associations or `find()` "by design"; condition is native SQL and may not join other tables (subquery allowed); static conditions better expressed with `@SQLRestriction`. — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- DSL note: a named, parameterized "row restriction" attachable to EntityMappings and enabled per repository call (region, organisational unit, visibility) — the general form of soft-delete and tenant filters.

**Multi-tenancy [medium]**
- Three approaches: separate database per tenant, separate schema per tenant (both via `MultiTenantConnectionProvider`; `DataSourceBasedMultiTenantConnectionProviderImpl` as model), or shared tables with `@TenantId` column; tenant chosen with `sessionFactory.withOptions().tenantIdentifier(id).openSession()`, JPA hint `HibernateHints.HINT_TENANT_ID`, or `CurrentTenantIdentifierResolver` (`hibernate.tenant_identifier_resolver`); for the discriminator approach "our data is automatically filtered so that only rows tagged with the tenant id" and "Native SQL queries are not automatically filtered by tenant id; you'll have to do that part yourself." — [Hibernate 6.6 Introduction (offset 300000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- Hibernate 6.4 allows non-String tenant ids (HHH-14822). — [Hibernate ORM 6.4 release](https://in.relation.to/2023/11/23/orm-640-final/)
- Schema-per-tenant example (PostgreSQL): `MultiTenancyStrategy.SCHEMA`; "each database schema will have its own ConnectionProvider instance"; tenant resolved from a ThreadLocal; "very suitable for database systems that draw a clear distinction between a database catalog and a schema"; migration/provisioning per tenant not discussed. — [Vlad Mihalcea: schema-based multitenancy](https://vladmihalcea.com/hibernate-database-schema-multitenancy/)
- Related: `@PartitionKey` adds the partition column to generated UPDATE/DELETE predicates (`where id=? and tenantKey=?`) so the DB does not "look for the row in all partitions". — [Hibernate 6.6 User Guide §3.11 Partitioning](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html)
- DSL note: discriminator tenancy is a special case of the row-restriction above plus an automatically populated column on INSERT; schema/database tenancy is a connection-routing concern outside the mapping DSL but requires per-tenant schema migration (see KQ7).

**Locking [small; ManMap has TCN optimistic lock]**
- Optimistic: `@Version` assigned automatically; without a version column `@OptimisticLocking` can validate "ALL fields, or only the DIRTY fields"; "an OPTIMISTIC lock is always verified at the end of the transaction, even when the entity has not been modified." Pessimistic: `session.find(Book.class, isbn, LockMode.PESSIMISTIC_WRITE)` uses `for update`; JPA `LockModeType.READ` is a synonym for `OPTIMISTIC`, not Hibernate's `LockMode.READ`; pessimistic locks should not be held across user interactions. — [Hibernate 6.6 Introduction (offsets 0, 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- DSL note: a `FOR UPDATE [NOWAIT|SKIP LOCKED]` modifier on CHECKOUT methods is the pessimistic counterpart to the TCN check; dialect differences (Oracle `FOR UPDATE NOWAIT`, MariaDB `FOR UPDATE SKIP LOCKED` since 10.6) belong in the generator.

**Cascade and orphan removal [design guidance]**
- Hibernate: `@OneToMany(mappedBy=..., cascade={PERSIST,REMOVE,REFRESH}, orphanRemoval=true)`; `orphanRemoval=true` deletes a child removed from the parent's collection; cascading is "very rare for many-to-many associations". — [Hibernate 6.6 Introduction (offset 100000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- Critique: cascading is for parent-child only ("Cascading from Child to Parent is not very useful"); on many-to-many "We shouldn't default to CascadeType.ALL because the CascadeType.REMOVE might end-up deleting more than we're expecting"; cascaded REMOVE is often discovered only after an unexpected deletion; many-to-many cascading "produces many redundant SELECT and DELETE statements". — [Vlad Mihalcea: cascade types](https://vladmihalcea.com/a-beginners-guide-to-jpa-and-hibernate-cascade-types/)
- Blaze-Persistence requires updatable views to *declare* cascade/orphan removal explicitly and to match the entity's settings, otherwise it is an error. — [Blaze-Persistence Entity View manual (offset 200000)](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)
- StatelessSession as a non-cascading model: operations "do not cascade", no dirty checking, `upsert(book)` executes `merge into` immediately. — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)

### Inferences
- The mainstream has moved toward *declared, per-use-case* cascade (Blaze updatable views, Hibernate StatelessSession without cascade), which is close to ManMap's `save with`/`delete with`; the one convenience worth adding is a declared *composition* (parent owns list) from which the generator emits the parent-then-children statements and the orphan-delete (diff of key sets) — explicit, visible, non-transitive.
- Soft delete, tenancy and filters share one mechanism (an implicit predicate on generated SELECTs plus implicit column values on INSERT/UPDATE); a single "implicit row restriction" concept in ManMap covers all three.

### Gaps
- Hibernate user guide text on how `@SoftDelete` interacts with `@ManyToOne` references to soft-deleted rows and HQL bulk delete was not in the fetched excerpt; the "no API to include deleted rows, use native SQL" statement rests on a forum thread and a practitioner article only.
- The DATABASE vs DISCRIMINATOR trade-off discussion from a primary source (beyond the Introduction guide's three-option list) was not found; second-level-cache-per-tenant behaviour not cited.

## Key Question 7: Schema evolution (Liquibase, Flyway, hbm2ddl) and what a DSL-driven migration could look like

### Takeaway
Both mainstream tools version the schema as an ordered list of immutable change units tracked in a history table; Liquibase additionally offers model-vs-database diff (including a Hibernate/JPA model as the reference), while Flyway reserves undo, dry-run and auto-generated scripts for paid tiers. Hibernate's own `hbm2ddl update` is uniformly advised against for production.

### Cited Findings

**Liquibase [BIG for a model-driven DSL]**
- "With Liquibase, you use a text-based changelog file to sequentially list all changes made to your database"; "An individual unit of change in your changelog is called a Changeset", each with one Change Type; formats SQL/XML/YAML/JSON; changeset `id` + `author` + file path form the unique identifier; preconditions; rollback (`--rollback` in SQL format; XML/YAML/JSON "generate automatic rollback statements for some changes"); contexts/labels; `DATABASECHANGELOG` tracking table (plus `DATABASECHANGELOGHISTORY` since 4.27). — [Liquibase docs: Changelogs](https://docs.liquibase.com/concepts/changelogs/home.html)
- `diff-changelog` "displays the differences between two databases you are comparing" and generates "a changelog file containing deployable changesets to resolve most of these differences"; default diff types columns, foreignkeys, indexes, primarykeys, tables, uniqueconstraints, views; check constraints, functions, procedures, triggers "require Liquibase Secure"; "Liquibase does not currently check data type length"; some objects "cannot be represented automatically"; output "should be inspected for correctness and completeness before being deployed". — [Liquibase docs: diff-changelog](https://docs.liquibase.com/commands/inspection/diff-changelog.html)
- Hibernate extension "lets you use your Hibernate configuration as a comparison database for diff, diffChangeLog, and generateChangeLog"; branches for Hibernate 7.x (Liquibase 4.x and 5.x) and 6.x; "The extension version must match your Hibernate major version." — [liquibase-hibernate README](https://github.com/liquibase/liquibase-hibernate)
- Reference URL forms: `hibernate:classic:path/hibernate.cfg.xml`, `hibernate:ejb3:<persistenceUnit>`, `hibernate:spring:com.example.pkg1,com.example.pkg2?dialect=org.hibernate.dialect.MySQL5Dialect` (package scan requires `dialect`; Spring config file form requires `bean=`); URL parameters `dialect`, `hibernate.physical_naming_strategy`, `hibernate.implicit_naming_strategy` override config; workflow `liquibase --changeLogFile=changelog.xml --url=jdbc:... --referenceUrl=hibernate:classic:... diffChangeLog` appends to the changelog, review before `update`; generated changes are a "rough draft" and the wiki's own example shows that a renamed class yields a *new table* in the diff rather than a rename. — [liquibase-hibernate wiki](https://github.com/liquibase/liquibase-hibernate/wiki)
- DSL note: ManMap already generates the target schema from mappings; the model-as-reference diff is exactly what an MPS generator could do against (a) the previous model version (model-to-model diff, which knows renames) or (b) a live database snapshot — emitting a Liquibase/Flyway-compatible changeset for review.

**Flyway [medium]**
- Migrations are SQL (or Java/script) files "tracked in version control"; types versioned (regular and undo), repeatable, baseline; `migrate` compares disk vs applied and "is idempotent"; "An undo migration is responsible for undoing the effects of the versioned migration with the same version"; schema history table records what was applied, when, by whom; each migration runs in a single transaction by default; placeholders `${...}`; callbacks. — [Flyway docs: Migrations](https://documentation.red-gate.com/flyway/flyway-concepts/migrations)
- Naming `V<version>__<description>.sql`, `R__` repeatable (no version), `U<version>__` undo; applied scripts are checksummed so editing them fails validation (secondary sources; the official naming page returned 404). — [Harness: Flyway migrations file structure](https://developer.harness.io/database-devops/use-db-devops/changelogs-and-schema-changes/flyway/flyway-migrations-file-structure), [Flyway BaseJavaMigration source](https://java-browser.yawk.at/org.flywaydb/flyway-core/6.4.0/org/flywaydb/core/api/migration/BaseJavaMigration.java)
- Editions: Community has migrate/baseline/info/validate/clean/repair, versioned/repeatable/baseline/Java migrations; Teams adds "Undo migrations", "Dry Run Script", "Maintaining a Schema Model", "Schema change diff viewer", "Static data versioning"; Enterprise adds "Generate versioned scripts", "Generate undo scripts", "Auto-generate migration scripts via CLI", "Drift detection", "Schema comparison tool". — [Redgate: Flyway feature summary](https://documentation.red-gate.com/fd/feature-summary-165740620.html)

**Hibernate hbm2ddl [critique]**
- Options `none, create-only, drop, create, create-drop, validate, update`; `create`/`create-drop` "are not suitable for an end-user project"; `update` "is to be avoided"; "better off handling the schema migrations with a tool like Flyway"; use hbm2ddl only to extract an initial script to review manually. — [Vlad Mihalcea: hbm2ddl.auto](https://vladmihalcea.com/hibernate-hbm2ddl-auto-schema/)
- Hibernate's own guide: indexes are usually owned by a DBA, so keeping index DDL in a script may be preferable to `@Index`; `javax.persistence.schema-generation.create-script-source` runs a DDL script. — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- Envers practitioners likewise: "you shouldn't deploy it to production without reviewing and improving" generated audit DDL. — [Thorben Janssen: Envers getting started](https://thorben-janssen.com/hibernate-envers-getting-started/)
- System-versioned tables constrain migration: MariaDB `ALTER TABLE` on versioned tables is governed by `system_versioning_alter_history` (KEEP), Oracle Flashback Archive forbids adding FK constraints (ORA-55610). — [MariaDB docs: System-versioned tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables), [Oracle 23ai: Flashback Technology](https://docs.oracle.com/en/database/oracle/oracle-database/23/adfns/flashback.html)

### Inferences
- A DSL-driven migration has one structural advantage over DB-diff tools: the model history (MPS model versions / VCS) knows *intent* (rename vs drop+add, type widening, split of an embedded value object), which diff-changelog explicitly cannot infer. The realistic design is: generator emits a reviewed changeset (Liquibase XML or Flyway SQL per dialect) from a model diff, tracked by the standard history table, never applied automatically — consistent with every source above.
- Multi-tenancy by schema multiplies migrations per tenant; discriminator tenancy avoids that, which is a reason to prefer the row-restriction approach in a DSL that also generates schema.

### Gaps
- Official Flyway naming-convention page (red-gate.com) was 404 on two attempts and a second search returned only third-party guides; naming rules (`V<version>__<description>.sql`, `R__`, `U<version>__`, monotonic unique versions, immutability) are from secondary sources — [Harness: Flyway migrations file structure](https://developer.harness.io/docs/database-devops/concepts/flyway-migrations-file-structure).
- Liquibase changelog "limitations" page was not retrievable; Hibernate-extension URL formats were obtained from the project wiki (cited above).

## Key Question 8: Batch/bulk operations (JDBC batching, bulk update/delete, upsert/merge per database)

### Takeaway
JDBC batching is a transport optimization that helps only for many statements against the same table; set-based UPDATE/DELETE statements and upsert (MERGE / ON DUPLICATE KEY / ON CONFLICT) are the stronger tools, and jOOQ shows how one declaration maps to each dialect's syntax.

### Cited Findings
- Hibernate JDBC batching via `hibernate.jdbc.batch_size` or `setJdbcBatchSize()`: "Batching only helps in cases where a program executes many inserts, updates, or deletes" against the same table in one transaction; HQL `update`/`delete` statements are "even better" than batched DML. — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- `StatelessSession.upsert(entity)` emits SQL `merge into`; operations execute immediately without cascade or dirty checking. — [Hibernate 6.6 Introduction (offset 200000)](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
- Spring Data `UpdateSpecification`/`DeleteSpecification` compose the same predicates into `CriteriaUpdate`/`CriteriaDelete` bulk statements: `UpdateSpecification.update((root, update, cb) -> update.set("lastname", x)).where(hasFirstname(a).and(hasLastname(b)))`. — [Spring Data JPA: Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html)
- jOOQ upsert: `insertInto(AUTHOR, ID, LAST_NAME).values(3,"Koontz").onDuplicateKeyUpdate().set(AUTHOR.LAST_NAME,"Koontz")` — native `ON DUPLICATE KEY UPDATE` on MySQL/MariaDB/Aurora MySQL/MemSQL, `ON CONFLICT (...) DO UPDATE` on PostgreSQL/SQLite/CockroachDB/DuckDB, "Emulated with MERGE" (USING subquery, WHEN MATCHED THEN UPDATE / WHEN NOT MATCHED THEN INSERT) on Oracle, SQL Server, DB2, H2, HSQLDB, Hana, Firebird, Snowflake, Teradata; unsupported on ASE, Access, BigQuery, ClickHouse, Trino etc. — [jOOQ manual: INSERT .. ON DUPLICATE KEY](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/insert-statement/insert-on-duplicate-key/)
- jOOQ MERGE: "one of the most advanced standardised SQL features", target + `USING` source, `ON` match, `whenMatchedThenUpdate()`, `whenNotMatchedThenInsert(...)`, think of it as a RIGHT JOIN; some dialects support `BY SOURCE` to update/delete target rows with no source match. — [jOOQ manual: MERGE](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/merge-statement/)
- jOOQ batch: single statement with many `bind()` rows, or several statements; later `bind()` calls have "no type safety provided by jOOQ". — [jOOQ manual: batch execution](https://www.jooq.org/doc/latest/manual/sql-execution/batch-execution/)
- MyBatis Dynamic SQL safety rule for bulk statements: dropping an all-optional WHERE "could end up impacting all rows in a table", hence `NonRenderingWhereClauseException` by default. — [MyBatis Dynamic SQL: conditions](https://mybatis.org/mybatis-dynamic-sql/docs/conditions.html)
- MariaDB system versioning interacts with bulk DML: a history row is created per UPDATE touching a versioned column; `TRUNCATE` is refused on versioned tables. — [MariaDB docs: System-versioned tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)

### Inferences
- For ManMap: (1) a repository method kind `UPDATE where ... set ...` / `DELETE where ...` (set-based, mapped fields, bound parameters, with the "no empty WHERE" guard) is small and high-value; (2) an `UPSERT` save variant per EntityMapping maps to `INSERT ... ON DUPLICATE KEY UPDATE` on MySQL/MariaDB and `MERGE INTO ... USING (SELECT ? ... FROM dual)` on Oracle, exactly as jOOQ emulates — but it bypasses the TCN optimistic-lock check, so it should be an explicit, separate method type.
- JDBC batching (already BATCH in ManMap) is complementary, not a substitute; the sources rank set-based statements above it.

### Gaps
- No primary source was fetched for Oracle-specific `MERGE` restrictions (e.g., cannot update the join column) or MariaDB `INSERT ... RETURNING` with upsert; dialect details beyond jOOQ's table are not cited.
- Generated-key retrieval in JDBC batches (jOOQ limitation page) was not fetched.

## Inventory summary: big vs small for a ManMap-like DSL

**[BIG]**
1. Declared read models / views with derived SELECT and joins, nested subviews, per-collection limits (Blaze Entity Views; Spring closed projections; jOOQ MULTISET + Records.mapping). Sources: [Blaze manual](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html), [jOOQ MULTISET](https://www.jooq.org/doc/latest/manual/sql-building/column-expressions/multiset-value-constructor/), [Spring projections](https://docs.spring.io/spring-data/jpa/reference/repositories/projections.html)
2. Path expressions over the FK graph with derived joins (jOOQ implicit joins). Source: [jOOQ implicit join](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/implicit-join/)
3. Named fetch plans per use case with partial-entity semantics (Jmix; Hibernate entity graphs/fetch profiles). Sources: [Jmix fetching](https://docs.jmix.io/jmix/data-access/fetching.html), [Hibernate Introduction](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
4. Historisation: MariaDB system versioning as a DDL option + `AS OF` query modifier; Envers-style `_AUD` tables (validity layout) as the portable fallback; Oracle Flashback Archive with caveats. Sources: [MariaDB](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables), [Vlad Mihalcea Envers](https://vladmihalcea.com/the-best-way-to-implement-an-audit-log-using-hibernate-envers/), [Oracle Flashback](https://docs.oracle.com/en/database/oracle/oracle-database/23/adfns/flashback.html)
5. Model-driven migration: generate reviewed Liquibase/Flyway changesets from a model diff, tracked in the standard history table. Sources: [Liquibase changelogs](https://docs.liquibase.com/concepts/changelogs/home.html), [diff-changelog](https://docs.liquibase.com/commands/inspection/diff-changelog.html), [liquibase-hibernate](https://github.com/liquibase/liquibase-hibernate), [Flyway migrations](https://documentation.red-gate.com/flyway/flyway-concepts/migrations)

**[medium]**
6. Keyset pagination with Page/Slice/Window result kinds and edit-time rules (non-null sort keys, PK appended, no OFFSET). Sources: [Spring scrolling](https://docs.spring.io/spring-data/commons/reference/repositories/scrolling.html), [jOOQ SEEK](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/select-statement/seek-clause/)
7. Implicit row restriction covering soft delete, discriminator tenancy and named filters, with native SQL deliberately excluded. Sources: [Hibernate User Guide §3.12](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html), [Hibernate Introduction](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
8. Set-based UPDATE/DELETE methods and UPSERT (MERGE / ON DUPLICATE KEY) per dialect. Sources: [jOOQ upsert](https://www.jooq.org/doc/latest/manual/sql-building/sql-statements/insert-statement/insert-on-duplicate-key/), [Spring UpdateSpecification](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html)
9. Declared composition (owned list) generating parent-then-children save and key-diff orphan delete — explicit, non-transitive, in line with the cascade critique. Sources: [Vlad Mihalcea cascade](https://vladmihalcea.com/a-beginners-guide-to-jpa-and-hibernate-cascade-types/), [Blaze updatable mappings](https://persistence.blazebit.com/documentation/entity-view/manual/en_US/index.html)

**[small]**
10. Optional where-terms (render only when parameter present, empty-WHERE guard). Source: [MyBatis Dynamic SQL conditions](https://mybatis.org/mybatis-dynamic-sql/docs/conditions.html)
11. Reusable, composable filter fragments (Specifications). Source: [Spring Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html)
12. Query-by-example method on repositories. Source: [Spring QBE](https://docs.spring.io/spring-data/jpa/reference/repositories/query-by-example.html)
13. Pessimistic `FOR UPDATE [NOWAIT|SKIP LOCKED]` modifier on CHECKOUT. Source: [Hibernate Introduction](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
14. Batched IN-list / subselect strategy for list loading as alternative to JOIN. Source: [Hibernate Introduction](https://docs.hibernate.org/orm/6.6/introduction/html_single/Hibernate_Introduction.html)
15. Read-only mapping onto a SQL select / DB view with declared base tables (@Subselect). Source: [Hibernate @Subselect javadoc](https://docs.hibernate.org/orm/7.4/javadocs/org/hibernate/annotations/Subselect.html)
16. Auditing already covered by ManMap (CREATEDAT/BY etc.); Spring's only extra is the pluggable `AuditorAware`/`DateTimeProvider` indirection. Source: [Spring Data auditing](https://docs.spring.io/spring-data/jpa/reference/auditing.html)
17. Partition-key predicate on UPDATE/DELETE (`@PartitionKey`). Source: [Hibernate User Guide §3.11](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html)
