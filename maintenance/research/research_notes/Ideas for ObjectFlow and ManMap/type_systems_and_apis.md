## A1. Nullable types and Option: how they change API design, and migration pitfalls

### Takeaway
Kotlin (nullable `T?`), Rust (`Option<T>`) and Java-via-JSpecify all make absence a *type-level* fact so the compiler forces handling; the migration pitfall is always the boundary with code that has "unspecified nullness" (Java platform types, un-annotated code, generics), and Java's own `Optional` is deliberately a return-type device only, not a field/property type.

### Cited Findings

**Kotlin nullable types [BIG]**
- Declares: a type is non-nullable unless suffixed with `?`; `String` cannot hold null, `String?` can. Example: `var b: String? = "abc"; b = null // OK`; `val l = b.length` is a compile error ("Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver"). — [Kotlin null safety](https://kotlinlang.org/docs/null-safety.html)
- Operators: safe call `?.` (returns null and short-circuits chains, `bob?.department?.head?.name`), elvis `?:` (right side evaluated only on null; may be `throw`/`return`), `!!` (throws NPE if null), smart casts after a null check narrow `T?` to `T` within scope, provided the variable cannot change between check and use. — [Kotlin null safety](https://kotlinlang.org/docs/null-safety.html)
- Guarantee: the docs state that the only possible NPE causes in Kotlin are an explicit `throw NullPointerException()`, use of `!!`, initialization inconsistencies (leaking `this`, superclass constructor calling an open member), and Java interoperation. Accessing an uninitialized `lateinit` property throws `UninitializedPropertyAccessException`, not NPE. — [Kotlin null safety](https://kotlinlang.org/docs/null-safety.html)
- Pitfall (migration): the page lists Java-interop NPE causes: accessing a member of a null reference of a *platform type*, and generics nullability mismatches, e.g. Java code adding null into a Kotlin `MutableList<String>` that would need to be `MutableList<String?>`. — [Kotlin null safety](https://kotlinlang.org/docs/null-safety.html)

**Rust `Option<T>` [BIG]**
- Declares: Rust has no null; absence is `enum Option<T> { None, Some(T) }` in the prelude. The book quotes Tony Hoare's 2009 talk calling null his "billion-dollar mistake". — [Rust book ch06-01](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)
- Guarantee: `Option<T>` and `T` are different types, so `let sum = x + y` with `y: Option<i8>` fails (`error[E0277]: cannot add Option<i8> to i8`); a value must be unwrapped (typically by `match`) before use, and "values whose type isn't Option<T> can be assumed to be non-null". — [Rust book ch06-01](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)
- Payload per variant: the same chapter shows `enum IpAddr { V4(u8,u8,u8,u8), V6(String) }`, i.e. variants carrying different data, replacing a struct with a separate `kind` field. — [Rust book ch06-01](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)

**Java `Optional` [small]**
- Oracle's API Note: "`Optional` is primarily intended for use as a method return type where there is a clear need to represent 'no result,' and where using `null` is likely to cause errors. A variable whose type is `Optional` should never itself be `null`". It is a value-based class (instances must not be used for synchronization). Key methods: `orElse`, `orElseThrow()` (since 10), `map`, `ifPresentOrElse` (since 9). — [Optional Javadoc, JDK 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Optional.html)
- Kotlin's standard library recommends null-returning variants over throwing ones for expected absence: `getOrNull()`, `firstOrNull()`, `toIntOrNull()`. — [Kotlin exceptions](https://kotlinlang.org/docs/exceptions.html)
- Criticism of `Optional` (Michael Ernst): "`Optional` does not make your code more correct or robust"; an `Optional` variable can itself be null; `get()` on an empty value "transforms a `NullPointerException` into a `NoSuchElementException`, which still crashes your program"; extra object, indirection and serialization issues; verbosity in type names and access. His alternative: ordinary references with `@Nullable` annotations plus a static checker (Nullness Checker, NullAway, Infer) for compile-time guarantees at no runtime cost. — [Ernst, Nothing is better than the Optional type](https://homes.cs.washington.edu/~mernst/advice/nothing-is-better-than-optional.html)
- Java's own `Optional` is listed by JEP 401 as an example of a (future) value class alongside `Integer` and `LocalDate` (preview in JDK 28), i.e. identity-free; see A4/A6. — [JEP 401](https://openjdk.org/jeps/401)

**JSpecify nullness annotations for Java [BIG for generated Java code]**
- Declares: `@Nullable` and `@NonNull` are *type-use* annotations; `@NonNull String` is a subtype of `@Nullable String`. `@NullMarked` on a module/package/class/method makes unannotated types `@NonNull` within scope (exceptions: local variables, type variables); `@NullUnmarked` undoes it for incremental adoption. Outside a `@NullMarked` scope types have *unspecified nullness*, which tools cannot guarantee across. Generics: a type variable needs a `@Nullable` bound (`<E extends @Nullable Object>`) to accept nullable arguments. — [JSpecify user guide](https://jspecify.dev/docs/user-guide/)
- Status: JSpecify 1.0.0 released 17 July 2024 on Maven Central with exactly four annotations; the authors say they "will never make backwards-incompatible changes to them". Adoption advice depends on "how ready your nullness analyzer is to support JSpecify, and whether you or your users also use Kotlin". — [JSpecify 1.0.0 release post](https://jspecify.dev/blog/release-1.0.0/)

**GraphQL and OpenAPI nullability as contract facts** (details in B1)
- GraphQL: "Types are assumed to be nullable and singular by default"; `!` makes a type non-null; list nullability is per level: `[String]`, `[String!]`, `[String]!`, `[String!]!`. — [graphql.org/learn/schema](https://graphql.org/learn/schema/)
- OpenAPI 3.1 removed the 3.0 `nullable: true` keyword in favor of JSON Schema type arrays `type: [string, "null"]`. — [OpenAPI 3.0 to 3.1 migration](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0)

### Inferences
- For OF: today "no value is null, except strings" is a convention, not a declared fact. The Kotlin/JSpecify lesson is that nullability is only useful when it is **per property and visible in the type**: a `mandatory`/`optional` (or `T?`) marker on entity/VO/DTO properties would let generated code carry `@NullMarked`/`@Nullable` (JSpecify), let the `:eq:`/`:ne:` null-safe operators become unnecessary on non-nullable properties, and let serdes, ManMap (`NOT NULL`) and any API contract derive `required`/`!`/`type: [.., "null"]` from one declaration. [BIG]
- Migration pitfall for OF, mirrored from Kotlin's platform types: existing models and runtime library code have "unspecified nullness"; a `@NullUnmarked`-like default per model/module and an explicit opt-in is the proven adoption path rather than a flag day.
- Java `Optional` is a return-type device per Oracle; using it as a property type in generated entities/DTOs would contradict the JDK's own guidance and complicate serdes. A nullable marker plus JSpecify annotations fits generated Java better than `Optional` fields. [small]
- OF's rule "a yes/no is a status" already avoids the classic "three-valued Boolean" (true/false/null) ambiguity; a nullability marker should keep that rule rather than reintroduce nullable booleans.

### Gaps
- Brian Goetz's often-cited Stack Overflow answer on `Optional` remains unfetched (stackoverflow.com and blogs.oracle.com are blocked for this tool, 403); the Javadoc API Note carries the same "return type for no result" guidance and Ernst's essay supplies the criticism side, so the substance is covered.
- Kotlin docs do not define "platform type" on the null-safety page itself (they link to the Java interop page, not fetched).

## A2. Result/Either types versus exceptions for expected failures

### Takeaway
Rust's position is the clearest: `Result` is the default for failures the caller can expect and handle, `panic!` for broken invariants/caller bugs; Kotlin dropped checked exceptions entirely and offers `Result`/`runCatching` plus null-returning variants; GraphQL encodes failures as *partial results plus an errors list*, not as exceptions.

### Cited Findings

**Rust `Result<T,E>` and `?` [BIG]**
- Declares: `enum Result<T, E> { Ok(T), Err(E) }`. The `?` operator unwraps `Ok` or returns early with `Err(e)` after passing it through `From::from` so error types convert automatically; `?` also works on `Option` (returns `None` early) but the two cannot be mixed without `ok()`/`ok_or()`. `?` is only usable in functions whose return type is `Result`/`Option` (e.g. `fn main() -> Result<(), Box<dyn Error>>`). — [Rust book ch09-02](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html)
- When to use which: "returning `Result` is a good default choice when you're defining a function that might fail"; "when failure is expected, it's more appropriate to return a `Result` than to make a `panic!` call" (examples: malformed input, rate-limited HTTP response); "Panicking when the contract is violated makes sense because a contract violation always indicates a caller-side bug". `unwrap`/`expect` acceptable in prototypes/tests or where inspection proves `Err` impossible, with `expect` documenting why. — [Rust book ch09-03](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)

**Kotlin: unchecked exceptions only, `kotlin.Result` [small]**
- All exceptions are unchecked; `@Throws` exists only for Java callers. Precondition helpers `require` (IllegalArgumentException), `check` (IllegalStateException), `error(...)`. `Nothing` is the bottom type, so `person.name ?: fail("Name required")` yields `String`, not `String?`. — [Kotlin exceptions](https://kotlinlang.org/docs/exceptions.html)
- `kotlin.Result<out T>` is a `@JvmInline value class` discriminated union of a success value or a `Throwable`, since Kotlin 1.3, with `getOrNull`, `exceptionOrNull`, `getOrElse`, `getOrThrow`, `fold`, `map`, `mapCatching`, `recover`, `onSuccess`/`onFailure`. — [kotlin.Result API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/-result/)
- History (secondary sources): from Kotlin 1.3 to 1.4 declaring a function returning `Result<T>` was a compile error unless `-Xallow-result-return-type` was set; the restriction was lifted in Kotlin 1.5 (May 2021) via a KEEP change. — [Kotlin Slack archive thread](https://slack-chats.kotlinlang.org/t/450970/so-the-release-of-kotlin-1-5-finally-unlocks-the-use-of-resu); [zenn.dev note](https://zenn.dev/fusuma/scraps/c7369d0ec300c3)

**Scala 3 / Iron: `Either` for validation [small]**
- Iron's `refineEither` returns `Either[String, Refined]`, composing in a `for` comprehension (`n <- name.refineEither[Alphanumeric]; a <- age.refineEither[Greater[0]]`), and `refineValidation` (Cats/ZIO modules) *accumulates* all errors instead of stopping at the first. — [Iron refinement methods](https://iltotore.github.io/iron/docs/reference/refinement.html)

**GraphQL: errors as data alongside partial results [BIG as an API design idea]**
- Normative: "If the request raised any errors, the response map must contain an entry with key `errors`"; "A response may contain both a partial response as well as any field errors"; every error "must contain an entry with the key `message`", should have `locations`, must have `path` for field errors, may have `extensions`. If a field of Non-Null type resolves to null, "field errors are propagated to be handled by the parent field"; "If the parent field may be null then it resolves to null"; "only one error should be added to the errors list per field". — [GraphQL spec Oct 2021, 6.4.4 and 7.1](https://spec.graphql.org/October2021/)

**Salesforce: `addError()` on records and formula validation rules** (see B2) make a user-correctable error a *declared outcome* of a save, rolling back the operation in most cases. — [Trailhead Apex triggers](https://trailhead.salesforce.com/content/learn/modules/apex_triggers/apex_triggers_intro)

**Mendix: validation errors surface differently per caller** (see B3): in a form as a page message, in a microflow as a catchable error, elsewhere as a Java exception. — [Mendix validation rules](https://docs.mendix.com/refguide/validation-rules/)

### Inferences
- OF's split "preconditions throw user-correctable problems, guards throw technical ones" already matches Rust's expected-failure vs contract-violation line. The missing piece is making the *expected* failure part of the method's declared signature: a service/API method could declare `problems { NotEnoughStock, CustomerBlocked }` so generated code returns a `Result`-like type (or a JSpecify-annotated sealed outcome) and an API contract can list these as documented error responses (OpenAPI `4xx` + error schema, GraphQL `errors[].extensions.code`). [BIG]
- Error *accumulation* (Iron `refineValidation`, Mendix "all failing rule messages are recorded and shown", GraphQL multiple `errors`) is what UIs need; a single-throw precondition cannot deliver a per-field list. A "collect problems" mode for preconditions is a small DSL addition with large UI value. [small-to-medium]
- Kotlin's `Nothing`-typed `fail()` shows a trick for a DSL: a `problem ...` statement typed as bottom lets `x ?: problem(...)` narrow nullability.

### Gaps
- The Kotlin `Result` return-type history is now sourced only from community archives (Kotlin Slack, zenn.dev), not from JetBrains release notes.

## A3. Sealed hierarchies and exhaustive matching: status with payload per state

### Takeaway
Java 17+/21, Scala 3 and Rust all let a closed set of alternatives carry *different data per alternative* and have the compiler check that every alternative is handled; Java's version (sealed interfaces + records + `switch` patterns, `MatchException` at runtime) is directly relevant to generated code.

### Cited Findings

**Java sealed classes (JEP 409, JDK 17) [BIG]**
- Declares: `sealed` class/interface with `permits` (inferable when subclasses are in the same file); each permitted subclass must be exactly one of `final`, `sealed`, or `non-sealed`; permitted subclasses must be in the same module (same package if unnamed module) and directly extend the sealed type; anonymous/local classes not allowed; records fit well because they are implicitly final. — [JEP 409](https://openjdk.org/jeps/409)
- Guarantee: JVM records `PermittedSubclasses` attribute; unauthorized subclass causes `IncompatibleClassChangeError` at class definition; compiler rejects impossible casts/`instanceof`; reflection `Class.getPermittedSubclasses()`/`isSealed()`. "Combining sealed types (sums) with records (products) gives algebraic data types". Example: `sealed interface Expr permits ConstantExpr, PlusExpr, ...` with records and a `switch` needing no `default`. — [JEP 409](https://openjdk.org/jeps/409)

**Java pattern matching for `switch` (JEP 441, JDK 21) [BIG]**
- Switch expressions and pattern switch statements must be exhaustive; for sealed types the compiler uses `permits`; for enums the JEP advises omitting `default` so missing constants are flagged; if an exhaustive enum switch finds no match at runtime it throws `MatchException`. `case null` handles null explicitly (otherwise NPE as before); `default` does not match null, `case null, default` does. Guards via `when` only on pattern labels; dominance rules make unreachable labels a compile error; recommended order constants, guarded patterns, unguarded patterns. — [JEP 441](https://openjdk.org/jeps/441)

**Java record patterns (JEP 440, JDK 21) [small]**
- Deconstruction: `if (obj instanceof Point(int x, int y))` binds components via accessors; nested record patterns; null never matches a record pattern; exhaustiveness analysis considers component types and sealed hierarchies (a `switch` over `Pair<I>` exhaustive with `C`/`D` cases when `I` is sealed permitting only `C`, `D`); type arguments inferred for generic record patterns. — [JEP 440](https://openjdk.org/jeps/440)

**Scala 3 enums/ADTs and sealed traits [BIG]**
- `enum Option[+T]: case Some(x: T); case None` where parameterized cases are case classes; hybrid enums mix plain values and parameterized cases (`Red, Green, Blue, Mix(mix: Int)`); desugars to a `sealed abstract class` plus companion; GADTs refine the type parameter per case (`IntBox(n: Int) extends Box[Int]`). — [Scala 3 ADTs](https://docs.scala-lang.org/scala3/reference/enums/adts.html); [Scala 3 book: ADTs/GADTs](https://docs.scala-lang.org/scala3/book/types-adts-gadts.html)
- Exhaustivity: "the compiler checks that the cases of a match expression are exhaustive when the base type is sealed", warning "match may not be exhaustive" and naming a failing input; subtypes must be in the same file. Example `sealed trait Notification` with `Email(sender, title, body)`, `SMS(caller, message)`, `VoiceRecording(contactName, link)`. — [Scala tour: pattern matching](https://docs.scala-lang.org/tour/pattern-matching.html)

**Rust enums with payload**: see A1 (`IpAddr::V4(u8,u8,u8,u8)` vs `V6(String)`). — [Rust book ch06-01](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)

**F#: "making illegal states unrepresentable" [BIG idea, small syntax]**
- A `Contact` needing an email *or* postal address: both-required is too strict, both-optional too loose (allows neither). Replace with a union `EmailOnly | PostOnly | EmailAndPost`; the invalid "neither" cannot be constructed; updating requires an explicit match over all three cases; business-rule changes become compile-time breakage, which the author regards as good. Idea attributed to Yaron Minsky. — [F# for fun and profit: illegal states](https://fsharpforfunandprofit.com/posts/designing-with-types-making-illegal-states-unrepresentable/)

**GraphQL unions/interfaces and OpenAPI `oneOf`+`discriminator` as the wire form of sealed types** (see B1). — [graphql.org/learn/schema](https://graphql.org/learn/schema/); [Swagger: inheritance and polymorphism](https://swagger.io/docs/specification/v3_0/data-models/inheritance-and-polymorphism/)

### Inferences
- OF's `status` type with exhaustive `status switch` is already the "sum" half. The missing half is **payload per state**: e.g. `status Shipment { Planned; Shipped(carrier: Carrier, trackingNo: string); Delivered(at: DateTime, signedBy: string) }`. Generated Java would be a sealed interface + records (JDK 17/21), the switch gains deconstruction, and fields that are only meaningful in one state stop being nullable columns with implicit invariants. For ManMap this is the classic single-table question: one `status` column plus nullable per-state columns with a generated `CHECK`, or a per-state side table; both are mechanical given the declaration. [BIG]
- Even without payload, the JEP 441 rule "omit `default` so new constants are flagged" and `MatchException` at runtime are worth copying for OF's `status switch` codegen: generate no `default`, let javac fail when a status value is added and a switch is not updated.
- `case null` vs NPE in JEP 441 shows that null handling in a switch should be an explicit declaration; combined with a nullable marker (A1), OF's `status switch` on a non-nullable status needs no null arm, on a nullable one it must have one.

### Gaps
- The Scala 3 reference page on ADTs does not itself discuss exhaustivity; the Scala tour page (Scala 2/3 generic) was used for that statement.

## A4. Value classes, inline classes and units of measure for money and quantity

### Takeaway
Kotlin inline value classes and F# units of measure both give *distinct compile-time types at zero runtime cost* (erased to the underlying primitive), which is exactly the "don't add EUR to USD / metres to seconds" guarantee; the price is erasure (no runtime unit info), boxing at generic/nullable/interface boundaries, and awkward interop.

### Cited Findings

**Kotlin inline value classes [BIG]**
- Declares: `@JvmInline value class Password(private val s: String)`; exactly one property in the primary constructor; may have `init` blocks (`require(fullName.isNotEmpty())`), secondary constructors, computed properties, functions; may implement interfaces (statically resolved); cannot extend classes, always final; no backing fields/`lateinit`/delegated properties. — [Kotlin inline classes](https://kotlinlang.org/docs/inline-classes.html)
- Guarantee/representation: at runtime usually the underlying value (no allocation); "an inline class is boxed whenever it is used as another type" (generic `T`, interface, nullable `Foo?`); `===` prohibited; function names are mangled (`compute-<hash>(int)`) so `compute(UInt)` and `compute(Int)` don't clash; `@JvmName` to make them callable from Java. Unlike a `typealias`, it is a genuinely new type: `acceptNameInlineClass("")` is an error. — [Kotlin inline classes](https://kotlinlang.org/docs/inline-classes.html)

**F# units of measure [BIG idea]**
- Declares: `[<Measure>] type cm`, derived `[<Measure>] type ml = cm^3`, `[<Measure>] type N = kg m / s^2`; literals `1.0<cm>`, `55.0<miles/hour>`; conversion constants are ordinary dimensioned values (`2.54<cm/inch>`); generic units `float<'u>` let `genericSumUnits v1 v2` type-check while `genericSumUnits v1 x1` (m/s plus m) is a compile error; record types can be unit-generic (`vector3D<[<Measure>] 'u>`). Supported on float32/float/decimal and all signed and (since F# 6, RFC FS-1091) unsigned integer types. — [F# units of measure](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/units-of-measure)
- Guarantee and limits: "Units of measure are used for compile-time unit checking but are not persisted in the run-time environment"; therefore "implementing a ToString function to print out the units is not possible"; conversion to/from unitless is explicit (`float length`, multiply by `1.0<degF>`, or `LanguagePrimitives.FloatWithMeasure`); the compiler normalizes unit formulas (`kg m s^-2` and `m /s s * kg` both become `kg m/s^2`). The page notes FSharp.UMX uses the same mechanism for zero-cost type-safe tagging of other types (e.g. ids). — [F# units of measure](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/units-of-measure)

**Fowler's Money pattern [BIG for business apps]**
- "money isn't actually a first class data type in any mainstream programming language"; a Money class keeps currency with amount so adding different currencies without conversion is caught, and rounding to the smallest currency unit is done in one place rather than silently losing small amounts across the code. — [Fowler, Money](https://martinfowler.com/eaaCatalog/money.html)
- Allocation (secondary descriptions of PoEAA ch. 18): Money has an `allocate` method taking a list of proportions that distributes the amount without losing value to rounding; worked example of splitting 5 cents 70/30 where naive rounding leaves a stray cent and the remainder is handed out until all money is spent; go-money splits £2 three ways as 67p/67p/66p. — [Verraes, Fowler Money pattern in PHP](https://verraes.net/2011/04/fowler-money-pattern-in-php/); [go-money README](https://github.com/rhymond/go-money)

**Fowler's Quantity pattern (2004 draft) [BIG idea]**
- "The basic idea of Quantity is a class that combines the amount with the unit"; "Represent dimensioned values with both their amount and their unit." Arithmetic: addition should refuse nonsensical combinations (length plus weight); for similar units the simplest option rejects and makes the caller convert, a richer option converts via a converter; multiplication simplest with scalars only, richer deriving units (miles / hours = speed); comparison raises the same conversion questions; conversion usually belongs in a separate converter object; printing/parsing can be delegated to the unit. — [Fowler, Quantity](https://martinfowler.com/eaaDev/Quantity.html)
- Money as the special case Fowler uses most: exchange rates change over time so conversion needs a time reference and automatic conversion in arithmetic/comparison is often disallowed; Money encodes its own rounding rules; division needs a policy for leftover pennies; "you should never use real numbers for handling Money"; he would use Money even with a single currency because "much of the value of money comes from its behavior, not its multi-unit capabilities"; database storage left open (currency may be stored once per account rather than per entry). — [Fowler, Quantity](https://martinfowler.com/eaaDev/Quantity.html)
- The pattern family (Quantity, Conversion Ratio, Compound Units) originates in *Analysis Patterns* ch. 3; a 1999 UML companion models Quantity with amount, unit, conversion and compound units. — [Fowler/Janicijevic, Analysis Patterns ch. 3 UML (PDF)](https://www.martinfowler.com/apsupp/apchap3.pdf)

**Java value classes (JEP 401, preview in JDK 28) [small, future]**
- `value` modifier; instance fields implicitly final, class implicitly final unless abstract; may implement interfaces, extend `Object` or an abstract value class; `==` compares by field values; synchronization is an error (`IdentityException`); no `finalize`, no weak references; `value record Point(int x, int y) {}` is allowed and value records serialize automatically; JVM may flatten/scalarize at its discretion; preview, disabled by default (`--enable-preview`). — [JEP 401](https://openjdk.org/jeps/401)

**F# single-case unions as domain wrappers [small]**
- `type EmailAddress = EmailAddress of string`; the case name is the constructor; prevents mixing e.g. email and zip code ("primitive obsession"); smart-constructor `create` returning `Some`/`None` (or a result type with message); privacy via `.fsi` signatures (compiled projects only); limitations: `None` carries no reason, values must still be unwrapped at DB/UI boundaries, repetitive module code. — [F# for fun and profit: single-case DUs](https://fsharpforfunandprofit.com/posts/designing-with-types-single-case-dus/)

**Java records as value carriers**: see A6 (records are nominal product types with value-based `equals`; compact constructor for validation). — [JEP 395](https://openjdk.org/jeps/395)

### Inferences
- OF already has value objects (multi-property) but money/quantity today is a bare `BigDecimal`. Two mechanisms are worth separating: (a) a **single-property value type** (Kotlin value class / F# single-case union): `value type CustomerNo = string`, `value type Percent = BigDecimal` with an optional invariant; generated as a Java record (or later a Valhalla value class), mapped by ManMap to the underlying column type with no schema change. [small, high leverage] (b) a **dimensioned numeric** (F# UoM / Fowler Money): `money` with currency and `quantity<unit>`; the compiler-side rule set is small (same-unit add/compare, multiply by scalar, divide to ratio), and ManMap gets a canonical two-column mapping (amount DECIMAL + currency CHAR(3)) once instead of per model. [BIG]
- F#'s erasure limitation (no unit at runtime) does *not* apply to a business DSL: a money value must carry its currency at runtime because it comes from the database. So the OF design is "F# checking + Fowler runtime representation". Fowler's "no automatic currency conversion, conversion needs a time reference" is the rule that distinguishes money from physical quantities and argues for two distinct OF types rather than one generic `quantity<unit>`.
- Fowler's `allocate` is the one operation a generated Money type must provide that `BigDecimal` arithmetic does not: proportional split without losing cents. It is also the operation most often re-implemented ad hoc in business code (invoice line distribution, tax splits).
- Fowler's remark that the currency may be stored once per account rather than per entry is directly a ManMap option: money columns mapped as amount-only when the owning entity declares a fixed currency context, as amount + currency otherwise.
- Kotlin's boxing rule is a warning for codegen: a value class used in a `list` or as nullable will box; fine for business code, but the DSL should not promise "zero cost".

### Gaps
- The exact PoEAA ch. 18 text of Fowler's `allocate` method was not fetched; the allocation description relies on secondary write-ups (Verraes; go-money). The Quantity page itself is explicitly a 2004 draft that Fowler says he will not correct or update.
- No source on how commercial money libraries (JSR 354 / Moneta, Joda-Money) handle persistence mapping; the ManMap inference above is not backed by a library reference.

## A5. Refinement/constrained types, "parse, don't validate", and validation at the boundary

### Takeaway
Refinement types (Iron for Scala 3, Rust's "custom types for validation", F# smart constructors) move a constraint from a repeated runtime check to a type that can only be constructed through one validated path; Alexis King's "parse, don't validate" is the design rule behind it: the check should *return a more precise type* so the proof is kept, and should happen once at the boundary.

### Cited Findings

**"Parse, don't validate" (Alexis King, 2019) [BIG idea]**
- Core: the difference "lies almost entirely in how information is preserved"; validation returns nothing (the program forgets what it learned), parsing returns a more precise type. A parser is "just a function that consumes less-structured input and produces more-structured output". `head :: [a] -> a` is partial; returning `Maybe a` is total but pushes checks to every caller; strengthening the input to `NonEmpty a` puts the check once in `nonEmpty :: [a] -> Maybe (NonEmpty a)`, and removing the upstream check becomes a compile error. — [Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)
- "Shotgun parsing" (from the 2016 LangSec paper *The Seven Turrets of Babel*): mixing checks into processing code so invalid input may be discovered after part of it has been acted on. Advice list: use precise data structures (a `Map` instead of a list of pairs to rule out duplicate keys); push the burden of proof upward to the boundary; let datatypes inform code rather than adding boolean flags; be suspicious of functions whose only job is to raise an error; parse in multiple passes if needed; avoid denormalized data or hide it behind an abstraction; use abstract types (smart-constructor newtypes) when the type system cannot express a constraint. — [Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)

**Rust: custom types for validation [small]**
- `pub struct Guess { value: i32 }` with private field, `Guess::new` panicking outside 1..=100, and a `value()` getter: "Code outside the guessing_game module must use the Guess::new function ... ensuring that there's no way for a Guess to have a value that hasn't been checked"; a function taking `Guess` "wouldn't need to do any additional checks in its body". — [Rust book ch09-03](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)

**Iron (Scala 3 refinement-type library, v3.4.0) [BIG as mechanism]**
- Declares: `Base :| Constraint`, e.g. `Int :| Positive`, `String :| Alphanumeric`, `Int :| Greater[0]`. Literals/`inline val`s are checked at compile time (`val y: Int :| Greater[0] = -1` fails with "Should be strictly greater than 0"); non-inlined values must be refined at runtime via `refineUnsafe` (throws), `refineOption`, `refineEither` (message on the left), `refineValidation` (accumulating, Cats/ZIO), `refineFurtherEither` for stepwise refinement; `DescribedAs[C, "msg"]` attaches custom messages; `assume` is an unchecked zero-cost cast. — [Iron refinement methods](https://iltotore.github.io/iron/docs/reference/refinement.html)
- Integrations exist for JSON (Circe, Jsoniter, play-json, uPickle, ZIO JSON), DB (Doobie, Skunk), config (Ciris, PureConfig), ScalaCheck, etc., i.e. the constraint is reused by serdes and persistence. — [Iron docs index](https://iltotore.github.io/iron/docs/index.html)

**Kotlin value class with `init { require(...) }`** gives the same smart-constructor guarantee in Kotlin (see A4). — [Kotlin inline classes](https://kotlinlang.org/docs/inline-classes.html)

**Java record compact constructor** validates once at construction (`Range { if (lo > hi) throw ... }`), see A6. — [JEP 395](https://openjdk.org/jeps/395)

**Declarative constraints in the platforms** (details in B2-B4): Mendix entity validation rules (required, unique, equals, range, regex, max length) run on commit; Salesforce validation rules are formulas; OpenAPI/JSON Schema carry `minimum`/`exclusiveMinimum`/`pattern` etc. in the contract (3.1 made `exclusiveMinimum` a number). — [Mendix validation rules](https://docs.mendix.com/refguide/validation-rules/); [Trailhead validation rules](https://trailhead.salesforce.com/content/learn/modules/point_click_business_logic/validation_rules); [OpenAPI 3.0 to 3.1](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0)

### Inferences
- OF's current model: constraints live in preconditions inside service methods (procedural, repeated, and invisible to UI/API/ManMap). The refinement-type lesson is to allow **constraints on the type/property declaration**: `string(1..60) notEmpty`, `BigDecimal(12,2) >= 0`, `pattern`, `unique`. One declaration can then feed (1) a generated smart constructor / compact record constructor, (2) ManMap `CHECK`/`NOT NULL`/`UNIQUE`/`VARCHAR(n)`/`DECIMAL(p,s)`, (3) OpenAPI/JSON Schema `minLength`/`minimum`/`pattern`/`maxLength`, (4) UI field metadata. [BIG]
- "Parse, don't validate" argues for doing this at the DTO-to-entity boundary: a DTO property can be a plain `string`, the entity property a `NonEmptyString`; the one conversion is where user-correctable problems are raised (OF's precondition concept), and entity code downstream carries no re-checks. OF's existing precondition/guard split maps neatly: the boundary parse raises problems; guards then only cover true invariant breaches.
- Iron's compile-time check of literals is a small but attractive MPS feature: a literal assigned to a constrained property can be checked in the editor.
- OF's "strings are never null" convention is itself a mini refinement (string = non-null string); making empty vs absent explicit (`""` vs no value) would remove a known ambiguity for API consumers (GraphQL/OpenAPI distinguish `null` from `""`).

### Gaps
- No academic source on refinement types (e.g. Liquid Haskell, F*) was fetched; the inventory relies on Iron's documentation and the Rust book for the mechanism.

## A6. Java records and pattern matching (JDK 16/17/21): implications for generated code

### Takeaway
Since JDK 21 all of records (16), sealed types (17), pattern `switch` and record patterns (21) are final, so generated Java can express a status-with-payload as `sealed interface` + `record`s and consume it with an exhaustive, deconstructing `switch`; records also dictate immutability, value equality and a single validated construction point.

### Cited Findings
- Records (JEP 395, final in JDK 16): header components yield a private final field and public accessor each, a canonical constructor, `equals`/`hashCode`/`toString`; compact canonical constructor validates/normalizes without assigning fields (`record Range(int lo, int hi) { Range { if (lo > hi) throw ... } }`); records are implicitly final, cannot be abstract, cannot `extends` (superclass is `java.lang.Record`), can implement interfaces, cannot declare instance fields or instance initializers; equality is by component values; the JEP states no nullability policy for components. — [JEP 395](https://openjdk.org/jeps/395)
- Sealed types (JEP 409, final in JDK 17) and pattern matching for `switch` (JEP 441, final in JDK 21, after previews 406/420/427/433) and record patterns (JEP 440, final in JDK 21, previews 405/432): see A3 for the rules. — [JEP 409](https://openjdk.org/jeps/409); [JEP 441](https://openjdk.org/jeps/441); [JEP 440](https://openjdk.org/jeps/440)
- Runtime behaviour relevant to generated code: an exhaustive switch with no runtime match throws `MatchException`; a `null` selector throws NPE unless `case null` is present; dominated (unreachable) labels are compile errors. — [JEP 441](https://openjdk.org/jeps/441)
- Java nullness annotations for generated APIs: JSpecify 1.0 (`@NullMarked` at package level makes everything non-null by default). — [JSpecify 1.0.0](https://jspecify.dev/blog/release-1.0.0/)

### Inferences
- For OF codegen, records are the natural target for **value objects and DTOs** (immutable, value equality, one validated constructor) but not for JPA-style mutable entities. If OF value objects are generated as records, the compact constructor is where A5 constraints land.
- Records cannot extend classes: a generated DTO hierarchy must use interfaces (sealed interfaces work). Records have no nullability policy, so a nullable marker in OF must be emitted as JSpecify annotations on components.
- `status switch` codegen target: `switch` expression over a sealed interface with record patterns, no `default`; add `case null` only when the switched property is declared nullable.
- Caveat: the target JDK of the generated runtime must be 21 or later; JDK 17 gives sealed + records but not pattern `switch`.
- Value classes (JEP 401) are preview-only in JDK 28, so generated single-property value types should be plain records today; the `value record` form is a one-token upgrade later, and JEP 401's early-construction rule (fields set before `super(...)`, no `this` in constructors) is worth respecting now in generated record constructors so they stay compatible.

### Gaps
- Did not verify the JDK version currently targeted by the MoAI/ObjectFlow runtime library; the above assumes a JDK 21+ target is possible.

## B1. OpenAPI-first and GraphQL schema-first contracts: what they declare and how code is generated both ways

### Takeaway
Both contracts declare types, per-field nullability, closed enums and polymorphic unions; they differ on errors (OpenAPI: per-status-code response schemas; GraphQL: `data` + `errors` with null propagation), on pagination (OpenAPI: nothing native; GraphQL: a de-facto cursor/connection convention) and on versioning (OpenAPI: `info.version` and server URLs; GraphQL: "evolve without versions"). Mature generators exist in both directions (client SDKs and server stubs/resolver types).

### Cited Findings

**OpenAPI [BIG]**
- Current spec version 3.2.1 (dated 10 September 2026 on spec.openapis.org); the `openapi` field states the OAS version; `info.version` (required) is the version of the API *description document*; `servers` provides base URLs with templated variables (`https://{region}.example.com/{basePath}` with `enum`/`default`); default server is `/`. — [OAS latest](https://spec.openapis.org/oas/latest.html)
- 3.1 aligned Schema Objects with JSON Schema 2020-12: `nullable: true` removed in favor of `type: [string, "null"]`; `exclusiveMinimum: 7` is now a number; `example` became `examples` arrays; binary via `contentEncoding`/`contentMediaType`; `$schema` dialect allowed. — [OpenAPI 3.0 to 3.1](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0)
- Responses (OAS 3.2.1 normative): the Responses Object "must contain at least one response code", and if only one it should be the successful response; keys are HTTP status codes as strings (`"200"`), wildcard ranges limited to `1XX`, `2XX`, `3XX`, `4XX`, `5XX`; "the explicit code definition takes precedence over the range definition for that code"; optional `default` covers undeclared codes; the description should cover the success response and known errors. Response Object fields: `summary`, `description`, `headers` (case-insensitive, `Content-Type` ignored), `content` keyed by media type with most-specific match (`text/plain` over `text/*`), `links`. — [OAS 3.2.1, Responses Object and Response Object](https://spec.openapis.org/oas/latest.html)
- Same rules in tutorial form with an error example: `"404": {content: {application/json: {schema: $ref Error}}}`, `"5XX": {description: Unexpected server error}`; reusable responses in `components/responses` must be `$ref`'d explicitly. — [Swagger: describing responses](https://swagger.io/docs/specification/v3_0/describing-responses/)
- Schema Object (OAS 3.2.1): default dialect `https://spec.openapis.org/oas/3.2/dialect/YYYY-MM-DD` = OAS base vocabulary plus JSON Schema Draft 2020-12; `$schema` per schema resource or `jsonSchemaDialect` document-wide; `null` is a JSON Schema type, so nullability is `type: [boolean, "null"]`; `readOnly`/`writeOnly` are annotations whose validation is optional and direction-dependent (ignoring `readOnly` on required fields in a PUT is noted as useful, a change from 3.0). — [OAS 3.2.1, Schema Object](https://spec.openapis.org/oas/latest.html)
- Discriminator Object (OAS 3.2.1): `propertyName` required (if that property is optional a `defaultMapping` must be given); `mapping` from payload values to schema names/URIs; legal only with `oneOf`, `anyOf`, `allOf`; with `oneOf`/`anyOf` every candidate must be listed; normative: "`discriminator` MUST NOT change the validation outcome of the schema", it aids deserialization, efficiency and error messages. — [OAS 3.2.1, Discriminator Object](https://spec.openapis.org/oas/latest.html); tutorial: [Swagger: inheritance and polymorphism](https://swagger.io/docs/specification/v3_0/data-models/inheritance-and-polymorphism/)
- Code generation: OpenAPI Generator lists roughly 81 client generators, 73 server generators (incl. `spring`, `jaxrs-cxf`, `jaxrs-jersey`, `jaxrs-resteasy`, `aspnetcore`, `python-flask`, `go-gin-server`), 17 documentation/schema generators. — [OpenAPI Generator: generators](https://openapi-generator.tech/docs/generators)
- Pagination: not addressed by the specification excerpt read; no native construct found. — [OAS latest](https://spec.openapis.org/oas/latest.html)

**GraphQL [BIG]**
- Schema: object types with typed fields and named arguments with defaults (`length(unit: LengthUnit = METER): Float`); built-in scalars `Int, Float, String, Boolean, ID` plus custom `scalar Date` (serialization/validation implementation-defined); `enum`; `input` types (may only contain input types); `interface` with implementing types; `union SearchResult = Human | Droid | Starship` (members must be concrete object types); nullable by default, `!` non-null, list nullability per level. — [graphql.org/learn/schema](https://graphql.org/learn/schema/)
- Errors and partial results: normative text in A2 (`data` + `errors`, non-null propagation to parent, `message`/`locations`/`path`/`extensions`); "If the data entry in the response is not present, the errors entry in the response must not be empty"; input values are validated before execution begins (request error). — [GraphQL spec Oct 2021](https://spec.graphql.org/October2021/)
- Pagination: cursor-based "connection" convention: `friendsConnection(first: Int, after: ID): FriendsConnection!` with `edges { cursor node }`, `pageInfo { hasNextPage startCursor endCursor }`, `totalCount`; offset pagination described as having performance/consistency downsides when records are inserted; cursors are opaque (suggested base64) so the backend can change strategy; formalized by the Relay Cursor Connections spec. — [graphql.org/learn/pagination](https://graphql.org/learn/pagination/)
- Versioning: the Best Practices index describes schema design as "Design and evolve a type system over time without versions"; the spec is "intentionally silent" on networking, authorization and pagination. — [graphql.org/learn/best-practices](https://graphql.org/learn/best-practices/)
- Nullability rationale (official): networked services depend on databases and other services that can fail, and authorization can differ per field; if every field is nullable a failure affects only that field (returns `null`) instead of failing the whole request; if a non-null field errors, the nearest nullable parent becomes `null`; design each field by asking "what could go wrong and is `null` an acceptable result", and mark non-null (`Type!`) only when it is not. Versioning: GraphQL deliberately avoids versioning; because clients receive only explicitly requested data, adding types or fields is non-breaking, and the common practice is a versionless API without breaking changes. — [graphql.org/learn/schema-design](https://graphql.org/learn/schema-design/)
- Code generation: GraphQL Code Generator treats the SDL schema as source of truth and generates typed client operations/hooks (Apollo, URQL, React Query) and typed server resolvers (Yoga, Apollo, Java servers), re-run when schema or operations change. — [GraphQL Code Generator](https://the-guild.dev/graphql/codegen/docs/getting-started)

**Platform-generated contracts (derived from the domain model)**
- Mendix publishes entities and microflows as OData v4 services described as "a REST service with an OpenAPI contract"; it generates `$metadata` (CSDL XML), an OpenAPI 3.0 JSON file, optionally a GraphQL schema (read-only), with Swagger UI at `/odata-doc/`; insert/read/update/delete are enabled per entity via Capabilities; published microflows become OData actions; enumerations used are published automatically. — [Mendix published OData services](https://docs.mendix.com/refguide/published-odata-services/)
- Mendix published REST: expose an entity via "Expose as REST resource" or a microflow as a REST operation; auto-generated Swagger UI at `/rest-doc/` as OpenAPI 3.0 and 2.0 with JSON Schemas. — [Mendix published REST services](https://docs.mendix.com/refguide/published-rest-services/)

### Inferences
- OF has `API_METHOD` but no contract. The minimal contract concept that covers both OpenAPI and GraphQL is: per API method, the parameter and return DTO types (already present), **nullability per property** (A1), **enum = status** (closed set), **sealed DTO alternatives** (OpenAPI `oneOf` + discriminator / GraphQL union), **declared problems** as error responses (A2), and a **page/cursor DTO convention** for list-returning methods. From that, an OpenAPI 3.1 document is a straightforward generator output, and the existing JSON serdes becomes the contract's implementation. [BIG]
- Mendix shows the "derive the API from the domain model" route (entities exposed as OData/REST with generated OpenAPI). The alternative is OF's current "service method = API" route. Both can coexist; the generated contract is the common artifact.
- GraphQL's "nullable by default because a field may fail" is a *response* concern; OF's DTOs are produced in one transaction, so non-null-by-default (Kotlin/JSpecify stance) is the better default for an OF contract, with the GraphQL lesson being to make nullability explicit in the contract either way.
- Versioning: with no native OpenAPI versioning, OF would have to choose between URL/`servers` versioning and GraphQL-style additive evolution (deprecate, never remove). The deprecated "older API description concept" suggests additive evolution with `deprecated: true` flags is the cheaper path. [small]

### Gaps
- The OAS 3.2.1 Operation Object (`deprecated` flag) and Parameter Object (`required`, `allowEmptyValue`) sections were not in the slices read; only the Header Object's defaults (`required`/`deprecated` default false, `allowEmptyValue` must not be used) were seen. `@deprecated` in GraphQL SDL was not confirmed from the fetched pages.
- OpenAPI Generator's page does not state which OAS versions it supports.

## B2. Salesforce: trigger order, validation rules, SOQL, Flow, governor limits

### Takeaway
Salesforce fixes a single, documented save pipeline (before-save flows, before triggers, validation rules, duplicate rules, save, after triggers, workflow/after-save flows, roll-ups, commit), makes validation a declarative true/false formula with a field-anchored message, exposes relationships in the query language, and uses hard per-transaction limits to force bulk-oriented design.

### Cited Findings

**Order of execution [BIG as a concept]**
- Steps (as reproduced by a secondary source, since the official page returned 403): load record and overwrite with new values; system validation (layout/required/format for UI edits; API/Apex saves check only foreign keys); custom validation rules; before-save record-triggered flows; before triggers; validations again and duplicate rules (a "block" duplicate rule stops the save); save without commit; after triggers; assignment/auto-response/workflow rules; workflow field updates re-save and re-fire before/after update triggers once but do not re-run custom validation, duplicate rules or escalation; escalation and entitlement rules; processes and (after-save) flows; roll-up summary fields on parent/grandparent (which then run their own save procedure); criteria-based sharing; DML on related records; commit; post-commit actions (outbound messages, email). — [salesforcegeek: order of execution](https://salesforcegeek.in/order-of-execution-in-salesforce/) (secondary); official page: [Apex Developer Guide: Triggers and Order of Execution](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm) (not fetchable, HTTP 403)
- Note: the search-engine summary of the official page places before-save flows *before* before triggers and custom validation rules *after* before triggers (step 5), whereas the secondary page lists custom validation rules before before-save flows; the two sources disagree on the exact position of custom validation rules relative to before-save flows. — [search summary of official page](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm); [salesforcegeek](https://salesforcegeek.in/order-of-execution-in-salesforce/)

**Apex triggers [small]**
- Events `before/after insert|update|delete`, `after undelete`; `Trigger.new`/`old`/`newMap`/`oldMap`, `isInsert`/`isBefore`; before triggers may change values, after triggers see system-set values (Id) and records are read-only; triggers are bulk: DML on more than 200 records is processed in batches and the trigger fires once per batch; `addError()` on a record blocks its save and shows the message in UI; usually the whole operation rolls back (Bulk API saves non-erroring records). Guidance: prefer validation rules and flows for simple needs, triggers for complex/CPU-heavy logic. — [Trailhead: Apex triggers](https://trailhead.salesforce.com/content/learn/modules/apex_triggers/apex_triggers_intro)

**Validation rules [BIG for a DSL]**
- Declares: rule name, error condition formula (true = invalid, save blocked), error message, error location (a specific field in all examples). Examples: `AND(NOT(ISBLANK(AccountNumber)), NOT(ISNUMBER(AccountNumber)))`; `YEAR(My_Date__c) <> YEAR(TODAY())`; `(Salary_Max__c - Salary_Min__c) > 20000` anchored on Salary Max; `LEN(AccountNumber) <> 8`. Defined on objects, fields, campaign members, case milestones. — [Trailhead: validation rules](https://trailhead.salesforce.com/content/learn/modules/point_click_business_logic/validation_rules)
- Change-aware functions and practice: `ISNEW()` is true while a record is being created (pair with `ISCHANGED` since fields are not "changed" on new records); `ISCHANGED(field)` fires only when that field changed; `PRIORVALUE(field)` returns the previous value (use case: block moving away from Closed Won). Example: `AND(OR(ISNEW(), ISCHANGED(CloseDate)), CloseDate<TODAY())`. Pitfall: a rule without an `ISCHANGED` guard blocks edits to unrelated fields on pre-existing violating records. Advice: one scenario per rule, show the error on a field (Salesforce adds a jump link), include a unique error code per object because rules can fire when roll-ups or automation update related records. — [Trailhead: validation rules best practices](https://trailhead.salesforce.com/content/learn/modules/validation-rules/implement-best-practices)

**SOQL relationship queries [small]**
- `SELECT fields FROM Object WHERE ...`, no `*` (use `FIELDS(STANDARD|CUSTOM|ALL)`), fields not selected cannot be accessed; Apex variable binding with `:dept`; child-to-parent via dot notation `SELECT FirstName, Account.Name FROM Contact`; parent-to-child via subquery `SELECT Name, (SELECT LastName FROM Contacts) FROM Account` with children as a list on the parent sObject; `LIMIT 1` returns a single sObject. — [Trailhead: SOQL](https://trailhead.salesforce.com/content/learn/modules/apex_database/apex_database_soql)

**Flow (record-triggered) [small]**
- Trigger: only when created, anytime updated, created or updated, or only when deleted; "The criteria for a record change trigger are the object and specific changes to field values." Timing: Fast Field Update runs "before that update is saved" to update the triggering record or show a custom error, with minimal database impact; Related Records and Actions runs "after that update is saved" for creating/updating/deleting other records, subflows, email alerts, Chatter posts; Run Asynchronously runs "immediately after the record update that triggered the flow is complete" for long tasks such as external calls; Scheduled Paths run "In the future, after the trigger has fired, based on dates and times". — [Trailhead: get started with triggered flows](https://trailhead.salesforce.com/content/learn/modules/record-triggered-flows/get-started-with-triggered-flows)
- Architect decision guide: Record-Triggered Flow is the default; choose by *automation density*: low (fewer than 15 automations, 0-1 downstream DML) = Flow; medium (15-30, 2-4 downstream DML, recursion risk) = hybrid, Flow orchestrating Invocable Apex; high (more than 30, 5+ downstream DML, complex/recursive) = Apex triggers with a metadata-driven framework. One entry point per object (do not mix Flow and Apex triggers on one object; the platform does not guarantee their relative order). Entry conditions compare `$Record` with `$RecordPrior`; recursion control by gating on whether a field actually changed; ordered execution via Flow Trigger Explorer order values (Flow) or custom metadata (Apex). Before-save for same-record changes (avoids a second DML and recursive save); Invocable Apex is unavailable in before-save flows and Flow has no after-undelete, so those need Apex. Bypass logic via custom permissions in entry criteria. — [Salesforce Architects: record-triggered automation](https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered)
- Third-party: before-save flows avoid an extra save cycle and do not count against DML limits for the triggering record. — [Salesforce Ben](https://www.salesforceben.com/before-save-flow-vs-after-save-flow-in-salesforce/)

**Governor limits [BIG as design pressure]**
- Trailhead (Salesforce-authored): a SOQL query inside a loop "can exceed the query limit of 100 synchronous or 200 asynchronous queries"; "The runtime allows up to 150 DML calls per transaction"; "Triggers execute on batches of 200 records at a time"; patterns: query once with `IN :Trigger.new`, inner subqueries for children, collect changes in a list and run one DML after the loop, `switch on Trigger.operationType` to skip needless queries. — [Trailhead: bulk Apex triggers](https://trailhead.salesforce.com/content/learn/modules/apex_triggers/apex_triggers_bulk)
- Developer Guide (via search summaries only; pages return 403): exceeding a governor limit throws a run-time exception that cannot be handled; Batch Apex resets limits per `execute` batch; the `Limits` class exposes used/limit pairs at runtime. — [Apex: Running Apex within Governor Execution Limits](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/api/apex_limits_tips.htm); [Limits class](https://developer.salesforce.com/docs/atlas.en-us.apexref.meta/apex/apex_methods_system_limits.htm)

### Inferences
- A **declared save pipeline** is the transferable idea: OF entities could declare `before save` / `after save` hooks and the generator fixes the order (constraints, then hooks, then persistence, then post-commit) so that ordering is documented once rather than emergent. Salesforce's "field updates re-fire triggers but not validation" rule is a warning about recursion that a DSL should rule out syntactically (hooks may not re-save). [BIG]
- Salesforce validation rules = A5 constraints with *formula + message + field anchor*. The field anchor is the piece OF preconditions lack: a problem that names the offending property lets a UI place the message next to the field. [small, high value]
- SOQL's relationship navigation (parent dot-path, child subquery) is a query-language feature; for ManMap the analogue is generated relationship accessors / fetch-plan declarations that map to JOIN or a second query. [small]
- Governor limits are not a feature to copy, but they show that an N+1-query shape can be made *visible* in a DSL (e.g. a warning when a query sits inside a loop over entities). [small]
- `ISNEW()`/`ISCHANGED()`/`PRIORVALUE()` are the declarative form of "constraint applies only on this transition"; for OF this suggests constraints scoped to create vs. update and to a property's change, and access to the prior value inside a precondition. The Architect guide's "one entry point per object, ordered by an explicit order value" is a DSL rule that can be enforced structurally (one save pipeline per entity, hooks ordered in the model). [small]

### Gaps
- developer.salesforce.com (order of execution, governor-limits table, SOQL relationship queries) and help.salesforce.com (validation rule considerations, Flow concepts) remained unreachable in the second pass (HTTP 403 / Lightning shell). Covered instead by Salesforce-authored Trailhead and Architect pages plus one secondary blog. Still unconfirmed by a fetched source: the exact per-transaction figures for records retrieved by SOQL, DML rows, CPU time and heap; SOQL traversal depth limits and the `__r` suffix; whether validation rules run on delete; per-object validation-rule count limits.

## B3. Mendix: domain model, microflows/nanoflows, validation feedback, access rules, workflows, published APIs

### Takeaway
Mendix declares entity-level validation rules, event handlers and per-role access rules (including XPath row-level constraints) *on the domain model* and applies them in pages, microflows and published OData/REST services; business logic is visual (microflows server-side, nanoflows client-side), with `Validation Feedback` as the standard way to attach a message to a widget's attribute, and workflows as a long-running, entity-contextual layer above microflows.

### Cited Findings
- Domain model: per-module visual data model; entity kinds persistable (DB table per entity), non-persistable (memory only), external (from the Mendix Catalog), view (stored OQL, beta); each persistable attribute becomes a column except calculated attributes; associations with cardinality, owner side, stored in association tables by default, or direct (FK in own table) for 1-1/1-n; generalization with a specialization-indicator column; indicators for validation rules and event handlers. — [Mendix domain model](https://docs.mendix.com/refguide/domain-model/)
- Validation rules: Required (whitespace-only counts as empty), Unique (enforced by the database), Equals, Range (bounds fixed or from other attributes), Regular expression, Maximum length; checked on commit in configured order, uniqueness last (needs a DB query); all failing messages recorded; surfacing depends on caller: form shows a validation message on the page, microflow gets an error for custom error handling, elsewhere a Java exception; persistable entities only. — [Mendix validation rules](https://docs.mendix.com/refguide/validation-rules/)
- Validation Feedback activity (microflow and nanoflow): shows a red message below the widget bound to the given attribute/association of the given object; template with `{1}` placeholders in microflows, static text only in nanoflows; ignored in microflows called from offline/native apps. — [Mendix validation feedback](https://docs.mendix.com/refguide/validation-feedback/)
- Microflows: BPMN-like server-side logic; events (start, end, error, continue, break), decisions, object-type decisions, loops; object activities (cast, change, commit, create, delete, retrieve, rollback), list activities, calls (Java/JavaScript actions, microflows, nanoflows), client activities (show page, show message, validation feedback), integration (REST, web services, external databases); an error event re-throws so callers can detect failure. — [Mendix microflows](https://docs.mendix.com/refguide/microflows/)
- Microflow error handling and transactions: default is Rollback (database changes rolled back, microflow aborts, error passed to the caller; unhandled errors show a system message); a savepoint is created at the start of any end-user-started microflow; per activity/decision/loop: Custom with rollback (revert all, follow error flow, end event swallows or error event rethrows), Custom without rollback (keep changes before the failing activity), Continue (only on Call Microflow and loops; discouraged); `$latestError` (System.Error with ErrorType, Message, Stacktrace), `$latestSoapFault`, `$latestHttpResponse`; each custom handler adds a savepoint so a sub-microflow error rolls back to the nearest relevant savepoint. — [Mendix: error handling in microflows](https://docs.mendix.com/refguide/error-handling-in-microflows/)
- Entity event handlers: Before/After x Create/Commit/Delete/Rollback; Before Commit/Delete/Rollback microflows receive the object and return a Boolean (false cancels; first false wins, later handlers may not run); "Raise an Error When the Microflow Returns False" (default Yes) makes a Before Commit handler behave like native validation whose error custom error handling can catch; execution order between handlers not guaranteed; handlers can be bypassed by some microflow actions; on lists, handlers run for all objects first and then the event applies to the whole list. — [Mendix event handlers](https://docs.mendix.com/refguide/event-handlers/)
- Nanoflows: run "directly on a browser/device", work offline against the local database; online, each database activity (create, commit, retrieve, rollback) is a separate network request; create object can be client-only for non-persistable entities without event handlers/calculated/read-only attributes; run as the current user; recommended for UI logic, validation, calculations, navigation; a nanoflow with at most one DB activity performs like a microflow. — [Mendix nanoflows](https://docs.mendix.com/refguide/nanoflows/)
- Access rules: per entity, multiple rules each bound to module roles; create/delete rights; member rights None/Read/Read-Write per attribute and association (calculated and Autonumber never writable); XPath constraints for row-level access (not applied to create, applied to delete; persistable entities only; "Owner" and "Path to user" helpers); rules additive; not inherited by specializations; evaluated at retrieve and cached for the request; attributes a user may not view are never sent to the client; shown only when App Security is Production. — [Mendix access rules](https://docs.mendix.com/refguide/access-rules/)
- Workflows: visual language for long-running (hours to months) multi-party processes with human and automated steps; `$WorkflowContext` is a business entity instance travelling through the workflow, `$WorkflowInstance` the running instance; user tasks, decisions, parallel splits, boundary events/timers listed; microflows can Call Workflow / Complete User Task; Workflow Engine runs in the Mendix Runtime; Workflow Commons provides pages/dashboards; a separate "Workflow Versioning and Conflict Mitigation" topic exists. — [Mendix workflows](https://docs.mendix.com/refguide/workflows/)
- Published OData/GraphQL and REST: see B1 (OData v4 + OpenAPI 3.0 + optional read-only GraphQL; REST resources from entities or microflows with `/rest-doc/` Swagger). Authentication basic/active session/custom microflow; allowed module roles restrict access; media entities cannot be published via OData. — [Mendix published OData](https://docs.mendix.com/refguide/published-odata-services/); [Mendix published REST](https://docs.mendix.com/refguide/published-rest-services/)

### Inferences
- Mendix's entity validation rules are the closest existing analogue to the A5 proposal for OF: a *closed list of declarative constraint kinds* (required, unique, equals, range, regex, max length) with messages, checked at commit and surfaced per caller. Its "unique runs last because it needs the DB" and "uniqueness enforced by the database" are useful ManMap details: `UNIQUE` is both a schema artifact and a validation message. [BIG]
- `Validation Feedback(object, member, message)` is a concrete signature for OF problems: a problem referencing an entity/DTO *property* rather than only a text. [small]
- Access rules on members with XPath row constraints show "declare once, apply in pages, logic and OData" for security; OF has no comparable concept in the brief; a per-role read/write declaration on properties would be another cross-cutting derivation (UI read-only, API field omission, ManMap unaffected). [BIG, but a separate topic]
- Nanoflow vs microflow is the client/server split; OF's DTO/service architecture already fixes server-side logic, so the relevant lesson is only that "validation" is useful on the client too, which argues for shipping A5 constraints as metadata to the UI.

- Mendix's Before Commit handler returning Boolean with "raise error" semantics, plus savepoint-based partial rollback, is a concrete model for OF save hooks: a hook is a predicate with a message, and the generator decides whether failure aborts the transaction or only the save. [small]

### Gaps
- Mendix pages are long (150k+ chars); only the first 100k of each was read. Still not captured: workflow versioning/conflict mitigation, how access rules apply to published OData, and the full list of microflow activities that support custom error handling.

## B4. OutSystems: aggregates, server actions, timers, BPT processes

### Takeaway
OutSystems declares queries as *Aggregates* (visual, typed, optimized to fetch only used attributes), scheduled work as *Timers* (declarative schedule, 20-minute default timeout, retries, `Wake<Timer>`), and long-running entity lifecycles as *Processes* launched declaratively on an entity's Create action with human and automatic activities closed by entity events.

### Cited Findings
- Aggregate: "fetch data using an optimized query, tailored to your usage"; sources are entities combined with joins, filters, sorting, group-by and calculated attributes; only attributes used on the screen or action are fetched, and attributes abstract the data model so renames/type changes do not break the aggregate; runs client- or server-side in Reactive/Mobile, server-side (Preparation) in Traditional Web; properties Max. Records (Traditional Web; otherwise widgets use StartIndex + LineCount + 1), Start Index, Timeout (seconds), Cache in Minutes, Fetch "At start"; outputs List, Count, IsDataFetched, HasFetchError. — [OutSystems 11 Aggregate reference](https://success.outsystems.com/documentation/11/reference/outsystems_language/data/handling_data/queries/aggregate/)
- Aggregate grouping: once attributes are grouped or aggregated, those become the only output; dynamic sorting in ODC uses a text expression naming the group-by or calculated attribute; sorting "can significantly affect performance". — [OutSystems: Calculate values from grouped data](https://success.outsystems.com/documentation/11/building_apps/data_management/data_operations/calculate_values_from_grouped_data/); [ODC: Sort results in an aggregate](https://success.outsystems.com/documentation/outsystems_developer_cloud/building_apps/data_management/fetch_data_from_the_database_in_outsystems/query_data_using_aggregates/sort_results_in_an_aggregate/) (via search summary)
- ODC aggregates: client-side (screen/block, load on screen load) vs server-side (action flows); sources added in a Sources tab with join types (e.g. "Only With"); calculated attributes; properties Timeout ("Server Request Timeout" for screen aggregates), Max. Records, Cache in Minutes (not in client actions), Start Index (expression), Fetch "At start"; event On After Fetch; outputs List, Count, IsDataFetched, HasFetchError; pagination via Max. Records + Start Index; guidance: no aggregates inside loops, fetch only used attributes, Test Query results may differ from the published app. — [ODC: Query data using aggregates](https://success.outsystems.com/documentation/outsystems_developer_cloud/building_apps/data_management/fetch_data_from_the_database_in_outsystems/query_data_using_aggregates/)
- Server Action: "runs logic on the server side"; properties Name, Description, Public (default No; Yes lets other modules depend on it), Function (default No; Yes means it must return a value and can be used in expressions, global scope only, server-side expressions only), Icon, Advanced > Cache in Minutes; exposure rule: an action cannot be exposed if a parameter is typed by an Entity or Structure that is not exposed or is reused from another module; producer/consumer modules with different User Providers have separate sessions. The page does not describe transaction or exception behaviour. — [OutSystems 11 Server Action reference](https://success.outsystems.com/Documentation/11/Reference/OutSystems_Language/Logic/Implementing_Logic/Logic_Elements/Server_Action)
- Timer (OutSystems 11): properties Name, Action, Schedule (case-sensitive, not validated at design time; `"16:15"`, `"22:00 Mon Fri"`, `"15:30 16"`, `"00:15 2nd Tue"`, `"When Published"`), Timeout in Minutes (default 20), Priority 1-4 (default 3), Is Multi-tenant; activation in Service Center; wake mechanics: scheduler finds due timers, locks the timer so no other front-end runs it, runs, recalculates next run, logs; failed timers retried, default 3 retries configurable in Service Center. — [OutSystems 11 Timer reference](https://success.outsystems.com/documentation/11/reference/outsystems_language/processes/timer/)
- Timer (ODC): schedule recurring / on publish / none (on-demand), overridable per stage in ODC Portal; default timeout 20 minutes with a platform-capped maximum; timed-out timers retry up to three times so logic should tolerate re-runs; `Wake<TimerName>` sets NextRun to now without changing the schedule; a timer never runs twice concurrently. — [ODC: Create and run Timers](https://success.outsystems.com/documentation/outsystems_developer_cloud/building_apps/use_timers/create_and_run_timers/)
- Process (BPT): "Launch On: Entity action that automatically starts the execution of a new process instance", the entity's primary key is added automatically as a process input parameter; also launched explicitly via Launch<Process> or nested via Execute Process; properties Public, Expose Process Entity, End-User Label/Detail; tools: Automatic Activity, Conditional Start, Decision, Execute Process, Human Activity, Send Email, Wait, Process Start/End, Decision Outcome, Timer. — [OutSystems 11 Process reference](https://success.outsystems.com/documentation/11/reference/outsystems_language/processes/process_elements/process/)
- Process execution: instances run in a separate context (on Oracle/PostgreSQL/DB2 commit open transactions before launching); each activity on the path gets an activity instance; a process is limited to 10,000 activity instances and is suspended beyond that. — [OutSystems 11: Processes](https://success.outsystems.com/Documentation/11/Developing_an_Application/Use_Processes_(BPT)/Processes)
- Human Activity: appears in every user's Taskbox unless User/Roles set; Destination screen; Close On a `Create<Entity>`/`Update<Entity>` event with attribute conditions (e.g. interview status updated to canceled), affecting only new instances; Taskbox shows Label, Detail, Instructions, Due/Start Date; Allow Skip for failed activities (not Wait); runtime ClosedBy/ClosedInstant/Skipped; callbacks exist (documented separately). — [OutSystems 11 Human Activity](https://success.outsystems.com/documentation/11/reference/outsystems_language/processes/process_tools/human_activity/)
- Automatic Activity: runs an action flow without human intervention; where side effects (add/change/delete records, external systems) belong; can use process inputs, earlier outputs, local variables; optional Start Date expression (not with Light Process Execution); on error the flow stops and retries from the beginning after a delay until success or process termination; Service Center shows erroring activities. — [OutSystems 11 Automatic Activity](https://success.outsystems.com/Documentation/11/Reference/OutSystems_Language/Processes/Process_Tools/Automatic_Activity)
- Automatic activities have a fixed 5-minute timeout that "cannot be 'personalized'"; recommended pattern: the activity prepares work and launches a Timer, the process waits, the timer signals completion by closing the Wait activity or creating/updating an entity. — [OutSystems support: BPT automatic activities timeout](https://success.outsystems.com/support/troubleshooting/application_runtime/bpt_automatic_activities_timeout/)

### Inferences
- Aggregates are "declared queries" whose *projection is derived from usage*. For OF/ManMap the transferable idea is a declared query element (sources, joins, filters, sort, group) typed against the entity model, with the generator deriving the SQL and the DTO shape; OutSystems' "renames don't break it" is exactly the MPS reference advantage. [BIG]
- `Launch On Create<Entity>` and `Close On Update<Entity> where status = X` are declarative *entity-event triggers*: a process step completes when an entity reaches a state. Combined with A3 (status with payload), OF could declare "when Shipment enters Delivered, complete task Y" without procedural glue. [BIG, process-level]
- Timers as DSL elements (schedule string, timeout, retry, idempotency expectation, no concurrent runs) are a small, well-bounded addition. The 20-minute/60-minute limits and "make it re-runnable" advice are operational rules a DSL can state as a declared contract. [small]
- OutSystems' Max Records / Start Index map directly to the pagination convention needed for an API contract (B1). [small]

- OutSystems' exposure rule (an action cannot be public if its parameters use non-exposed or foreign entities/structures) is a dependency-hygiene rule for OF's `API_METHOD`: an API method's parameter and return DTO types must themselves be part of the published contract, which a generator can check. [small]

### Gaps
- The Server Action page does not describe transaction scope (commit/abort) or exception handling; the Service Action reference page fetched contained only a properties table, so the server-vs-service action distinction (separate transaction, REST-based weak dependency) is not sourced here. The ODC "Create and run Timers" page did not state the 60-minute maximum that a search summary attributed to ODC; treat "60 minutes" as unconfirmed.
- Third-party claims about Max Records limiting transfer vs. DB fetch are disputed in the OutSystems forums and are not relied upon.

## C. Across both groups: what is declared once and reused in persistence, UI and API

### Takeaway
The reusable declarations that recur across languages and platforms are: per-property nullability, closed enumerations/sealed alternatives, constrained scalar types, unique/required/range rules with field-anchored messages, access rights per member, and a query/pagination shape. Platforms that derive persistence, UI and API from one model (Mendix, OutSystems) get this for free; typed languages get it by making the facts part of the type.

### Cited Findings
- Nullability: Kotlin types, JSpecify annotations, GraphQL `!`, OpenAPI `type: [..,"null"]`/`required`. — [Kotlin null safety](https://kotlinlang.org/docs/null-safety.html); [JSpecify](https://jspecify.dev/docs/user-guide/); [graphql.org/learn/schema](https://graphql.org/learn/schema/); [OpenAPI 3.0 to 3.1](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0)
- Closed alternatives: Java sealed + records, Scala enums, Rust enums, GraphQL `enum`/`union`, OpenAPI `oneOf` + `discriminator`; Mendix publishes used enumerations automatically in OData contracts. — [JEP 409](https://openjdk.org/jeps/409); [Scala 3 ADTs](https://docs.scala-lang.org/scala3/reference/enums/adts.html); [Swagger polymorphism](https://swagger.io/docs/specification/v3_0/data-models/inheritance-and-polymorphism/); [Mendix published OData](https://docs.mendix.com/refguide/published-odata-services/)
- Constraints: Iron refinement types reused by JSON and DB integrations; Mendix validation rules enforced at commit, in forms and as microflow errors, uniqueness by the database; Salesforce validation rules as formulas with field anchor. — [Iron docs](https://iltotore.github.io/iron/docs/index.html); [Mendix validation rules](https://docs.mendix.com/refguide/validation-rules/); [Trailhead validation rules](https://trailhead.salesforce.com/content/learn/modules/point_click_business_logic/validation_rules)
- Access: Mendix member-level read/write per role with XPath row constraints, applied at retrieve and hidden from the client. — [Mendix access rules](https://docs.mendix.com/refguide/access-rules/)
- Model-to-API derivation: Mendix OData/REST with generated OpenAPI; GraphQL/OpenAPI generators produce both server and client code from the contract. — [Mendix published OData](https://docs.mendix.com/refguide/published-odata-services/); [OpenAPI Generator](https://openapi-generator.tech/docs/generators); [GraphQL Code Generator](https://the-guild.dev/graphql/codegen/docs/getting-started)
- Query shape and pagination: OutSystems Aggregate (Max Records, Start Index, Count), GraphQL connections. — [OutSystems Aggregate](https://success.outsystems.com/documentation/11/reference/outsystems_language/data/handling_data/queries/aggregate/); [graphql.org/learn/pagination](https://graphql.org/learn/pagination/)
- Save pipeline: Salesforce order of execution; Mendix event handlers and commit-time validation; OutSystems entity Create/Update events launching/closing process activities. — [salesforcegeek order of execution](https://salesforcegeek.in/order-of-execution-in-salesforce/); [Mendix domain model](https://docs.mendix.com/refguide/domain-model/); [OutSystems Human Activity](https://success.outsystems.com/documentation/11/reference/outsystems_language/processes/process_tools/human_activity/)

### Inferences (ranked inventory for ObjectFlow/ManMap)
- [BIG] **Per-property nullability marker** (A1): feeds Java/JSpecify codegen, `:eq:`/`:ne:` necessity, ManMap `NOT NULL`, OpenAPI `required`/null-type, UI mandatory marks.
- [BIG] **Status with payload per state** as sealed interface + records, exhaustive deconstructing switch (A3/A6): feeds codegen, ManMap (status column + per-state nullable columns with CHECK, or side tables), API `oneOf`/union.
- [BIG] **Declared constraints on properties and single-property value types** (A4/A5): smart constructors / record compact constructors, ManMap `CHECK`/`UNIQUE`/`VARCHAR(n)`/`DECIMAL(p,s)`, JSON Schema keywords, UI metadata; "parse, don't validate" at the DTO-to-entity boundary.
- [BIG] **Money/quantity as a dimensioned type** (A4): compile-time currency/unit checks, canonical two-column mapping in ManMap, explicit conversion.
- [BIG] **API contract from `API_METHOD`** (A2/B1): parameter/return DTOs + nullability + status enums + sealed alternatives + declared problems as error responses + pagination DTO, emitted as OpenAPI 3.1 (optionally GraphQL SDL), with the existing serdes as implementation.
- [BIG] **Declared queries** (B4 Aggregates, B2 SOQL): typed over the entity model, projection derived from usage, generator emits SQL for Oracle/MySQL/MariaDB via ManMap.
- [small] **Field-anchored problems** (B2/B3): `problem(property, message)` so UI and API can place messages; collect-all mode for preconditions.
- [small] **Declared save pipeline / entity events** (B2/B4): fixed order for constraints, hooks, persistence, post-commit; no re-save from hooks; entity-state events usable as triggers.
- [small] **Timers** (B4): schedule, timeout, retry, idempotency expectation as declared contract.
- [small] **No-`default` exhaustive switch codegen and `case null` rule** (A3): immediate improvement to the existing `status switch`.
- [separate topic] **Member-level access rules** (B3): declare once, derive UI read-only, API omission, row filters.
