# Java model-driven business platforms: Apache Causeway, Axelor Open Platform, OpenXava, Jmix — inventory of declarative mechanisms

Scope note: inventory of what each platform expresses as a *declaration* (annotation, XML, naming convention, config) rather than hand-written code, with runtime effect and criticism, as input for extending ObjectFlow (entities/VOs/DTOs/status types/services/commands) and ManMap (table mappings, repositories, mapped queries, explicit save/delete, custom SQL read models, optimistic locking, audit fields). UI layout itself is out of scope; derivation of UI/REST from the model is in scope.

Legend used throughout: **[BIG]** = new concept family MoWare does not have; **[small]** = option, flag or checker rule that could be added to an existing concept.

## Key question 1 — Apache Causeway (Naked Objects pattern): actions, supporting methods, mixins, view models, services, metamodel validator, derived UI/REST, commands/audit/events, SecMan

### Takeaway
Causeway's core idea is that the *metamodel* built by reflection over POJOs (members + prefixed supporting methods + annotations) is the single source for UI (Wicket), REST (Restful Objects, GraphQL), security feature tree (SecMan), auditing (command log / audit trail / execution log) and a startup-time validator. The two mechanisms with the most transfer value for an MPS-based DSL are (a) the per-member business-rule triple hide/disable/validate (plus choices/autoComplete/default) as first-class, and (b) mixins/domain events as decoupled contribution points; the main criticism is the non-customizable generated UI and the long-URL view-model state.

### Cited Findings

**Domain object members and the supporting-method convention [BIG for "member business rules"; MoWare has preconditions/validations only on services]**
- `hideXxx()` returns boolean (member omitted from page); `disableXxx()` returns String reason (member read-only/greyed, reason shown); `validateXxx(proposed)` returns String reason. Action parameters have per-position forms: `hide1ShipTo(boolean sameAsBillingAddress)` (takes preceding params), `disable1Categorize(Category c)`, `validate0PlaceOrder(Product p)`, and a whole-argument form `validatePlaceOrder(Product p, int qty)`; declarative alternative `@Parameter#mustSatisfy()` / `@Property#mustSatisfy()` (specification objects). Properties are non-editable by default (config `causeway.applib.annotation.domain-object.editing`), overridable with `@Property(editing=ENABLED)` or `@DomainObject(editing=DISABLED)`. Collections are always read-only — changes only via actions; no implicit add/remove. Each argument is validated separately first, all-args validation only if each passes. If all members hidden, user sees a "no such object" 404 — [Business rules](https://causeway.apache.org/userguide/latest/business-rules.html).
- Reason strings can be `TranslatableString` for i18n — [Business rules](https://causeway.apache.org/userguide/latest/business-rules.html).
- `choicesXxx()` (property) / `choicesNXxx()` (param N, zero-based) returns a collection → drop-down; `defaultNXxx()` for action params (properties have no default method; initialize in constructor); `autoCompleteXxx(String search)` / `autoCompleteNXxx` with `@MinLength(n)`; dependent choices: `choicesN` may take earlier params as input; multi-select collection params need choices/autoComplete or `@Action#choicesFrom()` naming an existing collection; `@DomainObject(bounded=true)` gives automatic drop-down for reference data; enums get drop-downs automatically; `@DomainObject(autoCompleteRepository=..., autoCompleteMethod=...)` names a service method for global autocomplete; mixins may match supporting methods by parameter *name* or via a record/parameters class — [Drop-downs and defaults](https://causeway.apache.org/userguide/latest/drop-downs-and-defaults.html).
- `@DomainObject` attributes: `nature` (ENTITY, VIEW_MODEL, MIXIN), `editing`, `editingDisabledReason`, `bounding`, `autoCompleteRepository/Method`, `entityChangePublishing` (publish property changes to audit subscribers), `introspection`, `mixinMethod` (default `$$`), `aliased` (alternative logical type names), default `actionDomainEvent/propertyDomainEvent/collectionDomainEvent` classes, lifecycle event classes for created/persisting/persisted/loaded/updating/updated/removing (each may be Default/Doop/Noop), QueryDSL auto-complete tuning (min length, limit, extra predicates) — [@DomainObject reference 4.0.0-M2](https://causeway.apache.org/refguide/latest/applib/index/annotation/DomainObject.html).
- Metamodel validator config: `allow-deprecated` (default true), `explicit-logical-type-names` (default enabled — every object must declare a logical type name, usually `@Named("module.Type")`), `allow-logical-type-name-as-alias` (default off), `action-collection-parameter-choices` (default true: actions with collection params must have choices/autoComplete or `choicesFrom`), `jaxb-view-model.date-time-type-adapter` (default true); introspector `validate-incrementally` (default true) and `lock-after-full-introspection`; under lazy introspection validation errors may surface late — [Core MetaModel Validator config](https://causeway.apache.org/refguide/3.5.0/config/sections/causeway.core.meta-model.validator.html), [Core MetaModel Introspection config](https://causeway.apache.org/refguide/3.2.0/config/sections/causeway.core.meta-model.introspector.html). **[small: checker rules like "action with collection param must declare a choices source" are directly transferable]**

**Entities, services, repositories [small / confirmatory]**
- Entities are JPA/EclipseLink classes with required boilerplate `@EntityListeners(CausewayEntityListener.class)` (so services can be injected into loaded entities), `@Named("simple.SimpleObject")` logical type name (used by security and bookmarks), `@Id @GeneratedValue`, `@Version` for optimistic locking; `@DomainObject` optional but recommended. Named JPQL queries via `@NamedQuery`, executed with `RepositoryService.allMatches(Query.named(Class,"name").withParameter(...))`. Aggregates: a repository per aggregate root (e.g., `OrderRepository`), parts reached through the root's *lazily loaded* collection; Causeway is "less strict than classic DDD" about root-only references — [Domain entities](https://causeway.apache.org/userguide/latest/domain-entities.html).
- `@DomainService(nature=VIEW)` exposes actions as menu items and top-level REST actions; `nature=REST` only in REST; plain Spring `@Service/@Repository` components are invisible to UI/REST; metamodel services can only declare actions (no properties/collections). `RepositoryService.persist/remove` are *lazy* (queued to transaction end, before a query, or `TransactionService.flush()`); `*AndFlush` variants immediate; updates need no API — the ORM detects dirty objects. Constructor injection only for services and non-JAXB view models; entities and mixins require field/setter injection — [Domain services](https://causeway.apache.org/userguide/latest/domain-services.html).

**Mixins [BIG: "contributed member" concept]**
- A mixin is a class with a single-arg public constructor whose parameter type is the contributee (concrete, abstract, interface or `Object`); annotated `@Action`, `@Property` or `@Collection` (meta-annotations implying `@DomainObject(nature=MIXIN)`); implementing method `act`/`prop`/`coll`; supporting methods `hideAct`, `disableAct`...; class naming `Mixee_memberName` gives the member id. Contributed properties/collections are derived, read-only, side-effect-free, parameterless; `Map` not supported. Mixins may live in another module than the mixee (decoupling, avoids "big ball of mud"), can be nested in the mixee class, get services via `@Inject`; created via `FactoryService#mixin(...)` — [Mixins](https://causeway.apache.org/userguide/latest/mixins.html).

**View models and DTOs [BIG for "serializable use-case object"; relevant to ObjectFlow commands/pages]**
- View models are not persisted; the framework recreates them on each interaction from state serialized into the URL ("the browser holds their state"; URLs tend to be long). Uses: aggregating over several entities, proxying external data, supporting a use case (intray, quarterly invoicing, payment batches), dashboards; recommended as "desire lines" after the entity layer exists. Four programming models: JAXB (`@XmlRootElement`, entity refs via `@XmlJavaTypeAdapter(PersistentEntityAdapter.class)` → serialized as OidDto), `@DomainObject(nature=VIEW_MODEL)` + `@Property` (properties only, no collections, no view-model refs), `ViewModel` interface (`viewModelMemento()` string + constructor taking memento), `java.io.Serializable` (entity refs as `Bookmark`s, services `transient`). `UrlEncodingService` can swap the memento for a server-side GUID, encrypt per user, or expire. JAXB view models double as DTOs with XSD; `Dto` marker adds download-XML/XSD actions. Exposing entities directly over REST is discouraged (leaks implementation) — [View models](https://causeway.apache.org/userguide/latest/view-models.html).

**Domain events, UI events, lifecycle events [BIG: event bus with veto phases]**
- Each user interaction with a property/collection/action fires a domain event up to five times with `getEventPhase()`: hide, disable, validate, executing, executed — so a subscriber in another module can hide/disable/veto/enrich the member. UI events let a subscriber supply title/icon/cssClass/layout (take precedence over `title()`/`iconName()`), e.g., to re-skin library objects (SecMan) or JAXB view models. Lifecycle events: created, loaded, persisting, persisted, updating, updated, removing (none for view models; no "creating", no post-removal event). Custom events via `EventBusService.post`; subscribers use Spring `@EventListener` — [Events](https://causeway.apache.org/userguide/latest/events.html).

**Command log / execution log / audit trail [BIG: "command as persisted record" + property-level audit trail]**
- Command Log implements `CommandSubscriber` and persists each top-level action invocation / property edit (only the outermost command) as `CommandLogEntry`; config `causeway.extensions.command-log.publish-policy` = `always` (default) or `only-if-system-changed` (skip commands that changed no state, e.g., safe finders). `BackgroundService` persists a command as a CommandLogEntry for later execution by a Quartz `RunBackgroundCommandsJob` (non-re-entrant, ~10s interval) via `CommandExecutorService`; background actions must be in the metamodel (not `@Programmatic`). Command Log = user intention; Audit Trail = resulting state changes; correlated by `interactionId`. Execution Log's `ExecutionSubscriber` fires for every execution incl. nested ones — [Command Log](https://causeway.apache.org/userguide/latest/commandlog/about.html), [Execution Log](https://causeway.apache.org/userguide/3.2.0/executionlog/about.html).
- Audit Trail: `EntityPropertyChangeSubscriberForAuditTrail` persists one `AuditTrailEntry` per changed property per event; entries with the same interaction id can be grouped; enabled per entity via `@DomainObject(entityChangePublishing=...)` — [Audit Trail about (3.3.0)](https://causeway.apache.org/security/3.3.0/audittrail/about.html), [EntityPropertyChangeSubscriberForAuditTrail](https://causeway.apache.org/refguide/3.3.0/extensions/index/audittrail/applib/spiimpl/EntityPropertyChangeSubscriberForAuditTrail.html), [@DomainObject](https://causeway.apache.org/refguide/latest/applib/index/annotation/DomainObject.html). (The refguide class-level text erroneously describes logon/logout logging — documentation error noted in search results.)

**SecMan security [BIG: permission tree derived from metamodel; small: ALLOW/VETO specificity rule]**
- Users ↔ roles ↔ permissions stored as domain entities and editable inside the app; each permission is ALLOW or VETO on a feature at member (`myapp.customer.CustomerAddress#zipCode`), type (logical type name) or namespace (`myapp.customer`, multipart inheritance) level; the *most specific* permission wins — type-level ALLOW overrides namespace VETO, member-level VETO overrides type ALLOW. Feature set is derived from the metamodel ("type-safe"). Multitenancy via `ApplicationTenancy.atPath`, `HasAtPath` on objects and the `ApplicationTenancyEvaluator` SPI deciding hidden/disabled — stated limitation: "only skin deep", presentation-layer only, restricted objects can still be loaded; deeper options are EclipseLink `@Multitenant`, DB-level tenancy or one instance per tenant. SecMan can be authorizer only alongside Spring/Keycloak authenticators — [SecMan](https://causeway.apache.org/security/latest/secman/about.html).

**Derived REST / GraphQL**
- Restful Objects viewer implements the Restful Objects spec (generic hypermedia REST over the domain model), aimed at bespoke SPAs, integrations, bulk upload/migration; Causeway-specific enhanced content negotiation ("Apache Causeway v2 Profile"); a GraphQL API viewer does the same with GraphQL — [Restful Objects viewer](https://causeway.apache.org/vro/latest/about.html). With 4.0.0-M1 the viewer moved off RestEasy to a new artifact `causeway-viewer-restfulobjects-viewer` — [4.0.0-M1 migration notes](https://causeway.apache.org/relnotes/latest/2025/4.0.0-M1/mignotes.html).

**Value types [medium: custom scalar + composite value types with semantics provider]**
- Built-in values: wrappers/primitives, `String`, any `Enum`, `BigDecimal`/`BigInteger` (with `@Digits` for scale), `java.time` types (preferred) and legacy `java.util/sql` dates, `UUID`, `Locale`, `URL` (rendered as link), `BufferedImage` (read-only), Causeway `Blob`, `Clob`, `Markup`, `LocalResourcePath`, `TreePath`/`TreeNode`; extension catalog `AsciiDoc`, `Markdown`, `Vega` — [Value types](https://causeway.apache.org/userguide/latest/value-types.html).
- Custom scalar value type: class annotated `@org.apache.causeway.applib.annotation.Value` (e.g., `EmailAddress`), plus a `@Component @Named` `ValueSemanticsAbstract<T>` implementing `getSchemaValueType()` (determines UI widget), `decompose()/compose()` (XSD-based JSON/XML for REST and command DTOs), `getDefaultsProvider()`, `getRenderer()` (title presentation), `getParser()` (parse text, `typicalLength()/maxLength()`), `getIdStringifier()` (URL-safe, so the value can be part of an identifier); persistence via JPA `AttributeConverter` with `@Converter(autoApply=true)` — [Value types](https://causeway.apache.org/userguide/latest/value-types.html).
- Composite value type (e.g., `DateInterval(startDate,endDate)` with `overlaps()`/`gap()`): a mixin named `..._default` annotated `@Action(semantics=SAFE)` + `@ActionLayout(promptStyle=INLINE_AS_IF_EDIT)` with `act(start,end)`, `defaultStartDate()`, `validateAct()` supplies the input prompt; semantics provider returns `ValueType.COMPOSITE`, `decompose()` via `typedTupleBuilder`; no parser/id-stringifier; persisted with JPA `@Embedded/@Embeddable`. Stated limitations: composite values cannot be part of an object's identifier; mutable `java.util.Date`/`java.sql.*` are poor value types; `Markup` needs input sanitization — [Value types](https://causeway.apache.org/userguide/latest/value-types.html).

**@Action / @Property attribute inventory [small: option vocabulary]**
- `@Action`: `semantics` (SAFE_AND_REQUEST_CACHEABLE, SAFE, IDEMPOTENT, NON_IDEMPOTENT, `*_ARE_YOU_SURE` adds confirmation; safe actions skip the concurrency check, non-safe perform it), `commandPublishing`, `executionPublishing`, `restrictTo=PROTOTYPING`, `domainEvent` (Default/Doop/Noop), `choicesFrom` (collection checkboxes feed multi-select params), `typeOf`, `fileAccept`, `commandDtoProcessor` (transform command DTO for replication; returning null excludes from replay; implies command publishing) — [@Action reference](https://causeway.apache.org/refguide/latest/applib/index/annotation/Action.html).
- `@Property`: `editing`/`editingDisabledReason`, `mustSatisfy` (Specification classes, all must pass), `maxLength` (inferred from `@Column(length)` with JPA), `regexPattern`/`regexPatternFlags`/`regexPatternReplacement` (error message, not i18n), `optionality` (mandatory by default; must align with `@Column(nullable)` or boot fails), `commandPublishing`, `executionPublishing`, `entityChangePublishing` (DISABLED excludes this property from audit), `hidden(Where)` (EVERYWHERE, OBJECT_FORMS, ALL_TABLES...), `domainEvent`, `projecting` (view-model property referencing the underlying entity; bookmarks redirect), `snapshot` (include/exclude in mementos), `fileAccept`, `queryDslAutoComplete`, `commandDtoProcessor` — [@Property reference](https://causeway.apache.org/refguide/latest/applib/index/annotation/Property.html). **[small checker rule: optionality vs nullable mismatch is a boot failure in Causeway — an MPS checker could flag the same]**

**Audit Trail details (closing earlier gap)**
- "Each and every change to a entity property is persisted as an individual `AuditTrailEntry` instance"; entries carry an interaction id grouping all changes of one interaction and, with Command Log enabled, trace back to the causing action/edit; `AuditTrailMenu` offers `findMostRecent`, `findAuditEntries`, `findAll`; setup = BOM `causeway-extensions-audittrail` (4.0.0-M2) + persistence module (JPA or JDO) + menubar entries — [Audit Trail 3.3.0](https://causeway.apache.org/security/3.3.0/audittrail/about.html). In 4.0.0-M2 "Auditing now logs only updates, not creates or deletes" and Command Log gained bulk export/upload of commands — [4.0.0-M2 release notes](https://causeway.apache.org/relnotes/latest/2026/4.0.0-M2/relnotes.html).
- 4.0.0-M2 (Spring Boot 4.0.5, EclipseLink 5.0.0, Jackson 3): view-model bookmark URLs are now HMAC-signed by default (`causeway_hmac_sha256`, min 16 bytes); property "clear" supporting methods removed; metamodel inspector supports type hierarchies; clearer validation errors when `-parameters` compiler flag is missing; Java Records as view models honour introspection policy; EclipseLink static weaving automatic; inconsistent weave state in hierarchies fails early; OpenTelemetry integration via `observation` profile — [4.0.0-M2 release notes](https://causeway.apache.org/relnotes/latest/2026/4.0.0-M2/relnotes.html).

**Restful Objects spec details (closing earlier gap)**
- Implements Restful Objects **v1.0**, "all the mandatory features"; `domainModel` scheme is "formal" only (the "simple" scheme is not supported); optional capabilities `blobsClobs`, `deleteObjects`, `validateOnly`, `protoPersistentObjects` supported; extensions beyond v1.0: `x-ro-domain-type` content negotiation, an Apache Causeway simplified profile, `x-ro-follow-links` to cut round-trips; URLs like `/restful/objects/PARENT/0` (logical type name + instance id); UI hints such as `Render(EAGERLY)` ignored by default (`causeway.viewer.restfulobjects.honor-ui-hints`) — [RO spec page](https://causeway.apache.org/vro/latest/ro-spec.html).

**Criticism / limitations**
- Pattern creator Richard Pawson concedes the non-customizable auto-generated UI "is one of the biggest factors that has limited both the applicability and the appeal of the naked objects pattern" and that early versions permitted no UI customization; he also rebuts the misconception that the pattern puts UI logic into domain objects — [InfoQ: Naked MVC](https://www.infoq.com/articles/Nacked-MVC).
- A 2005 comparative case study (Keränen & Abrahamsson) reported 79% less application code and 91% less UI code with Naked Objects, but found the framework version "not mature enough" for all required functionality; single mobile app — [VTT publication](https://cris.vtt.fi/en/publications/naked-objects-versus-traditional-mobile-platform-development-a-co/).
- Largest known deployment: Irish Department of Social Protection, ~1500 users, mission-critical (vendor-side account) — [Pawson QCon London 2011 slides](https://qconlondon.com/london-2011/qconlondon.com/dl/qcon-london-2011/slides/RichardPawson_LargeScalePureOOAtTheIrishGovernment.pdf).
- View-model state in URLs leads to long URLs; URL limits require custom `UrlEncodingService` — [View models](https://causeway.apache.org/userguide/latest/view-models.html). Collections read-only; updates rely on ORM dirty tracking and lazy loading — the opposite of MoWare's explicit save — [Business rules](https://causeway.apache.org/userguide/latest/business-rules.html), [Domain services](https://causeway.apache.org/userguide/latest/domain-services.html).

### Inferences
- The hide/disable/validate triple and choices/autoComplete/default are *per member and per action parameter*; in ObjectFlow these would translate to optional declarative "enablement", "visibility", "validation", "choices" slots on entity properties and command/service parameters, checked by a metamodel-style validator at build time (MPS checker) instead of at startup.
- Mixins are the cleanest existing model of "contribute an action/derived property to a type from another module without editing it"; for MPS this could be a cross-model concept referencing an ObjectFlow entity.
- Command Log + Audit Trail with correlation by interaction id is exactly the pairing MoWare could offer at the "command/session check-in" boundary: ObjectFlow commands already have a session acting as unit of work and an explicit check-in, which is the natural persistence point for a command record and the property diff.
- SecMan's feature tree derived from the metamodel, with namespace/type/member scope and "most specific wins", is reproducible from an MPS model (modules → entities/commands → members) without reflection.

### Gaps
- The full field list of `AuditTrailEntry` (pre/post value columns, truncation limits) is still not documented on the fetched pages; only the per-property granularity and interaction-id grouping are confirmed.
- Exact Restful Objects resource-to-URL derivation rules beyond the `/restful/objects/{type}/{id}` example were not extracted (the spec page refers to a diagram image).
- Causeway has no declarative status/state-machine construct in the fetched user guide; status handling is done via enums + hide/disable/validate rules on actions (inference from [Business rules](https://causeway.apache.org/userguide/latest/business-rules.html) and [Drop-downs](https://causeway.apache.org/userguide/latest/drop-downs-and-defaults.html), not an explicit statement).

## Key question 2 — Axelor Open Platform: XML domain models, generated JPA, field types, selections, sequences, audit/tracking, actions, BPM, Studio

### Takeaway
Axelor is the most "ManMap-like" of the four: entities, fields, relations, indexes, unique constraints, finders, computed/formula fields, sequences and change-tracking are all declared in an XML domain model from which JPA classes and repositories are generated; behaviour is declared separately as reusable XML "actions" bound to view events. Distinctive first-class constructs: sequences with prefix/padding, `<track>` audit messages with conditions, JSON custom fields at runtime, and `<finder>` with generated AND-filters.

### Cited Findings

**XML domain model [BIG as a whole; several small items]**
- `<module name package repo-package table-prefix>`; `<entity>` attributes: `name`, `sequential` (dedicated id sequence, default true), `cacheable` (default false), `repository` (`none|default|abstract`), `table`, `logUpdates` (default true), `extends`, `implements`, `persistable` (false → `@MappedSuperclass`), `strategy` (SINGLE|JOINED|CLASS inheritance), `equalsIncludeAll`, `jsonAttrs` — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html).
- Common field attributes: `title`, `help`, `column`, `index` (`true` or `idx_...`), `default`, `required`, `readonly`, `unique`, `insertable/updatable`, `hidden`, `transient`, `initParam` (constructor param), `massUpdate`, `nullable`, `selection` (key of selection list), `equalsInclude`, `formula`. Field types: string (`min`,`max`,`large`,`search`,`sequence`,`multiline`,`translatable`,`password`,`encrypted`,`json`,`namecolumn`), boolean, integer/long (`min`,`max`), decimal (`precision`,`scale`), date/time/datetime (`tz="true"` → ZonedDateTime), enum (`ref`), binary (`image`,`encrypted`), many-to-one, one-to-one (`mappedBy`,`orphanRemoval`), one-to-many (`mappedBy`, `orphanRemoval` default **true**, `orderBy`), many-to-many — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html). **[small: `namecolumn`, `search`, `massUpdate`, `translatable`, `encrypted`, `initParam` are property-level flags MoWare could adopt]**
- Enums with persistence values: `<enum name="OrderStatus"><item name="DRAFT"/><item name="OPEN" value="open"/></enum>`; `numeric="true"` makes values numeric; in JPQL enum values must be bound as parameters, literal strings are wrong — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html). **[small: explicit persistence value per enum literal]**
- Formula fields (`formula="true"`, body is raw SQL incl. subselects, read-only, not a column, reduces portability) vs. calculated fields (Java-like expression in element body; `namecolumn="true"`, `search="firstName,lastName"` control display/search) — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html). **[small: computed property with SQL body vs Java body]**
- `<index columns="firstName,lastName,fullName" name="idx_names"/>`, `<unique-constraint columns="..."/>`; reference fields and `namecolumn`/`name`/`code` fields indexed automatically; `<entity-listener class=.../>` adds `@EntityListeners`; `encrypted="true"` uses AES-256, requires `encryption.password` — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html).
- `<finder name="findByCountry" using="String:country" filter="self.country.code = :country" all="true"/>`; `using` may be field names (generator builds ANDed filter) or `type:name` params; `orderBy`, `cacheable`, `flush`; `<extra-imports>`/`<extra-code>` inject code into the generated repository (advised against); recommended override path: `repository="abstract"` then subclass `AbstractTitleRepository` — [Repositories 8.0](https://docs.axelor.com/adk/8.0/dev-guide/models/repositories.html). **[small: ManMap already has mapped queries; `all`, `cacheable`, `flush` are option ideas]**
- Entities are JPA POJOs with Hibernate; generated classes include "added features to deal with collection fields & computed fields" — [Models index 8.0](https://docs.axelor.com/adk/8.0/dev-guide/models/index.html).

**Sequences [small/medium: formatted business sequence as declaration]**
- `<sequence name="sale.order.seq" initial="1" increment="1" padding="5" prefix="SO"/>` referenced by `<string name="name" sequence="sale.order.seq"/>`; values like SO00001 assigned automatically when saving new records; stored as `MetaSequence` records (meta update needed after adding); `JpaSequence.nextValue(name)` for early use inside `@Transactional` — [Sequences 8.0](https://docs.axelor.com/adk/8.0/dev-guide/models/sequences.html).

**Audit fields and change tracking [BIG: declarative, conditional change-log messages]**
- `AuditableModel` (`@MappedSuperclass`): `createdOn`, `updatedOn` (LocalDateTime), `createdBy`, `updatedBy` (User); base `Model`: `id` Long, `version` Integer, `archived` Boolean, `cid`, `selected` — [AuditableModel javadoc 8.1](https://docs.axelor.com/adk/8.1/javadoc/com/axelor/auth/db/AuditableModel.html).
- `<track>` inside `<entity>`: `<field name on if/>` and `<message if on tag fields>` children; `on` ∈ CREATE|UPDATE|ALWAYS; `if` is a JEL boolean expression; attributes `files`, `subscribe`, `replace`; tags important/success/warning/info. Example: `<field name="confirmDate" on="UPDATE" if="status == 'confirmed'"/>`, `<message if="status == 'confirmed'" on="UPDATE">Order confirmed.</message>`. Runtime: a tracked field produces a message only when its value changes and `if` holds; root message on create, later messages threaded as replies; tracking runs asynchronously after the user's transaction; passwords, encrypted, binary, O2M/M2M and transient fields excluded; shown via `<panel-mail>` with `<mail-messages>` and `<mail-followers>`; email notifications to followers — [Messaging 8.1](https://docs.axelor.com/adk/8.1/dev-guide/modules/messaging.html).

**Actions [BIG: behaviour declared as reusable named XML bound to lifecycle events]**
- Actions give default values, change form values/field attributes, call controller methods, validate the record; triggered on `onNew`, `onLoad`, `onSave`, `onChange`, `onSelect`, `onClick`; special actions `save`, `new`, `close`, `validate` can be chained (`onChange="save,some-action,another-action,save"`). Expression forms: `eval:` Groovy, `select:` JPQL with EL, `action:` another action, `call: Controller:method`, `#{...}` Java EL, plain constant; context variables `__this__` (form values), `__self__` (DB record), `__parent__`, `__ref__`, `__id__`, `__ids__`, `__user__`, `__date__`, `__time__`, `__datetime__`, `__config__`; helpers `__repo__(Class)`, `__bean__(Class)` — [Actions 8.0](https://docs.axelor.com/adk/8.0/dev-guide/actions/index.html).
- `<action-view name title model icon>` with `<view type name/>`, `<view-param name value/>` (forceEdit, showArchived, popup, limit, search-filters ...), `<domain>` JPQL where-clause with named params, `<context name expr/>`; special context `_showRecord`, `_showSingle`, `__check_version` (version check in form); menus via `<menuitem>` with `groups`/roles — [action-view 8.0](https://docs.axelor.com/adk/8.0/dev-guide/actions/action-view.html).
- `<action-validate>` has `<error if message>` and `<alert if message>` children (verified only on the 6.1 page) — [action-validate 6.1](https://docs.axelor.com/adk/6.1/dev-guide/actions/action-validate.html).
- Default grid/form views are generated when missing but "may not look good"; providing views is advised — [Object views 8.1](https://docs.axelor.com/adk/8.1/dev-guide/views/index.html).

**JSON custom fields / custom models [BIG: schema-less extension fields]**
- Entities get an `attrs` JSON column by default (`jsonAttrs="true"`) or any `<string json="true">`; fields are defined at runtime as `MetaJsonField` (name, type, selection, widget, showIf/hideIf/requiredIf/readonlyIf JS expressions, includeIf server expression, contextField/contextFieldValue for context-aware fields, valueExpr computed, targetModel for relations, sequence, regex ...); PostgreSQL/MySQL/Oracle supported; JPQL functions `json_extract*`, `json_set`; `<custom-fields for=... on="attrs">` for data import — [Custom fields 8.0](https://docs.axelor.com/adk/8.0/dev-guide/models/custom-fields.html).
- Studio: custom models/fields stored as JSON (`MetaJsonModel`/`MetaJsonField`), no schema migration; code-defined models can only be *extended* (fields, views) not created/deleted from Studio; recommends standard models when DB constraints, indexing or complex relations are needed; Studio Apps package models/fields/menus/actions/charts/dashboards for export/import — [Studio 3.5](https://docs.axelor.com/studio/3.5/studio-docs/index.html).

**BPM**
- BPMN 2.0 processes are deployed to take effect; script tasks (Groovy execution, Groovy query, web-service connector) with model settings choosing which data is visible and a "Display status" option injecting `$wkfStatus` on the model's form; user tasks bind to a model, choose buttons visible on the view and show the task name as status; BPM menu has Process Instances, BPM Migration between model versions, YAML-based instance modification — [Script tasks 3.2](https://docs.axelor.com/studio/3.2/bpm-docs/BPMN/tasks/script_task.html), [User tasks 3.2](https://docs.axelor.com/studio/3.2/bpm-docs/BPMN/tasks/user_task.html), [BPM docs 3.2](https://docs.axelor.com/studio/3.2/bpm-docs/index.html).

**Selections and status handling [medium: status = integer/selection + conditional buttons; no state machine]**
- Selection lists are declared in view XML: `<selection name="order.status.selection"><option value="DRAFT" color="blue">Draft</option>...<option value="CLOSED" color="green">Closed</option></selection>` and bound by `<field name="orderStatus" widget="SingleSelect" selection="order.status.selection"/>`; option attributes `value` (stored), `color`, `icon`, `data-*` (e.g., `data-domain`, `data-grid`, `data-form` for RefSelect); `NavSelect` is "a breadcrumb-like widget for selection fields": `<field name="status" widget="NavSelect"/>` — [Widgets 8.0](https://docs.axelor.com/adk/8.0/dev-guide/web-client/widgets.html).
- Convention in Axelor Open Suite (sale module): `<integer name="statusSelect" title="Status" selection="sale.order.status.select" readonly="true"/>` with constants in `<extra-code>` (`STATUS_DRAFT_QUOTATION = 1` ... `STATUS_CANCELED = 5`), a second `orderingStatus` selection field, `<track><field name="statusSelect"/>` and status-driven messages like `<message if="statusSelect == 1" tag="important">Draft quotation</message>` — [AOS SaleOrder domain](https://raw.githubusercontent.com/axelor/axelor-open-suite/master/axelor-sale/src/main/resources/domains/SaleOrder.xml). The form shows `<field name="statusSelect" showTitle="false" widget="NavSelect"/>` and transitions are buttons guarded by expressions, e.g. `<button name="finalizeBtn" showIf="statusSelect == 1" onClick="action-group-sale-order-finalize-quotation"/>`, `<button name="confirmOrderBtn" showIf="statusSelect == 2" onClick="action-sale-group-confirmed"/>`, `<button name="cancelBtn" showIf="id && (statusSelect == 1 || statusSelect == 2)" onClick="save,action-sale-order-view-cancel"/>` — [AOS SaleOrder views](https://raw.githubusercontent.com/axelor/axelor-open-suite/master/axelor-sale/src/main/resources/views/SaleOrder.xml). I.e., the state machine is implicit: states are selection values, transitions are buttons with `showIf` guards and action chains; no declarative transition table exists in the platform.

**Remaining action types (closing earlier gap)**
- `<action-record name model search ref copy saveIf>` constructs (or finds and optionally copies) a record with `<field name expr if copy/>` children; `expr` forms `eval:`, `call:`, `action:`, `select:` (first match), `select[]:` (all), else static; `saveIf` saves when the expression is true and `id` is null or a `version` is provided. Example: `<action-record name="default-order-record" model="com.axelor.sale.db.Order"><field name="customer" expr="action:default-customer-record" if="!_contact"/><field name="orderDate" expr="eval: __date__"/><field name="items" expr="action:default-orderline-record"/></action-record>` — [action-record 8.0](https://docs.axelor.com/adk/8.0/dev-guide/actions/action-record.html).
- `<action-method name><call class="...HelloController" method="say(fullName)"/></action-method>` calls a `@CallMethod`-annotated controller method, optionally passing field values; result assignable to a field — [action-method 8.0](https://docs.axelor.com/adk/8.0/dev-guide/actions/action-method.html).
- `<action-attrs name><attribute for="orderDate" name="readonly" expr="confirmed"/><attribute for="name" name="hidden" expr="!id"/></action-attrs>`; supported attribute names: `required`, `readonly`, `hidden`, `focus`, `domain`, `selection-in`, `value`/`value:set`/`value:add`/`value:del`, `title`, `css`, `icon`, `collapse`, `active`, `precision`, `scale`, `refresh`, `url`, `prompt`, `link` — [action-attrs 8.0](https://docs.axelor.com/adk/8.0/dev-guide/actions/action-attrs.html). **[small: `selection-in` = dynamically narrowing the allowed enum/status values per context — a declarative "allowed next states" surrogate]**
- `AuditInterceptor` (`com.axelor.auth`) extends Hibernate `EmptyInterceptor` overriding `onSave`, `onFlushDirty`, `onDelete` — consistent with populating `createdBy/updatedBy` there, but the javadoc does not state it — [AuditInterceptor javadoc 6.1](https://docs.axelor.com/adk/6.1/javadoc/com/axelor/auth/AuditInterceptor.html).

**Criticism / limitations**
- Forum reports: refreshing views after XML changes took 2 to 35+ minutes in one setup, ~10 s with ~700 views in another; signature/new-class changes still require restarts; IntelliJ hot-reload plugins as workaround (anecdotal) — [Axelor forum: view refresh](https://forum.axelor.com/t/view-refresh-when-add-fields-or-modify-xml-views/5638).
- Formula fields reduce DB portability; `long` fields discouraged (Oracle allows one long column per table) — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html).
- Tracking is asynchronous (eventual visibility) and excludes collection fields — [Messaging 8.1](https://docs.axelor.com/adk/8.1/dev-guide/modules/messaging.html).
- One-to-many defaults to `orphanRemoval=true`, i.e., implicit cascade semantics on the collection — contrary to MoWare's no-cascade principle — [Models 7.4](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html).

### Inferences
- Axelor's `<track>` is the strongest template for a declarative "business audit" in ObjectFlow: per-field tracking with event (create/update) and condition, plus templated human-readable messages, decoupled from technical audit fields that ManMap already has.
- `<sequence>` as a first-class ManMap/ObjectFlow concept (prefix/suffix/padding/initial/increment) replaces hand-written number generators; the Axelor runtime assigns it "on save of new records", which maps to MoWare's explicit save/check-in.
- `<finder using="field1,field2">` generating an AND filter is an "80% shortcut" over ManMap's mapped `where` — a small generator convenience.
- Axelor's action XML (eval/select/call expressions on onNew/onChange/onSave) is essentially a scripting layer; the transferable part is not the scripting but the *event vocabulary* (onNew default values, onChange derived values, onSave validation) attached to the model.

### Gaps
- `action-script`, `action-group`, `action-condition` detail pages for 8.x were not fetched (only linked); `action-validate` syntax verified on the 6.1 page only.
- No dated changelog for Open Platform 8.x found; 8.2 release notes exist without a date.
- The exact code populating `createdBy/updatedBy` (AuditInterceptor behaviour) is inferred from method names, not documented.
- The `sale.order.status.select` selection definition itself was in the unread tail of the AOS views file; labels were taken from the card template (1 draft quotation, 2 finalized quotation, 3 order confirmed, 4 order completed, 5 canceled).

## Key question 3 — OpenXava: @View/@Tab deriving UI from entities, calculators, validators, calculations, collections, @SearchKey, @ReferenceView, modules, access tracking

### Takeaway
OpenXava keeps JPA entities as the single "business component" and layers UI-derivation annotations on top (`@View`, `@Tab`, `@ReferenceView`, `@CollectionView`, `@ListProperties`, `@DescriptionsList`), plus small declarative behaviour hooks (`@DefaultValueCalculator` with `@PropertyValue` wiring, `@Calculation` expression strings, `@Depends`, `@PropertyValidator`/`@EntityValidator`/`@RemoveValidator`, `@Condition`, `@SearchKey`). Modules compose a model + controllers + view + tab in `application.xml`, with automatic default modules per entity. Audit/"access tracking" and fine-grained security are commercial XavaPro features.

### Cited Findings

**Model-level declarations [mostly small]**
- Entity = JPA `@Entity` POJO; `@EntityValidator` and `@RemoveValidator` repeatable at class level; `@Embeddable` instances have no identity and belong strictly to the owner (no JPA callbacks). Property annotation stack: `@Stereotype`, size constraints, `@Required`, `@Id`, `@Hidden`, `@SearchKey`, `@Version`, `@Formula`, `@Calculation`, `@DefaultValueCalculator`, `@PropertyValidator` — [OpenXava model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html).
- `@Hidden`: excluded from generated UI but usable in code; `@SearchKey`: properties the user types to find a reference (default: `@Id` properties, or first view property if ids hidden); `@Version`: optimistic concurrency (int/Integer/short/long/Timestamp), counts as hidden; `@Required` also implied by `@Min`, `@Range`, `@Length(min>0)` (Bean Validation since v5.3) — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html). **[small: SearchKey = "lookup key" on entity]**
- Stereotypes: a named type behaviour bundling editor, default size and validators (e.g., `@Stereotype("PERSON_NAME")`, since v6.6 annotations like `@PersonName`, `@Money`, `@TextArea`, `@File`, `@Mask` v7.1), configured through `editors.xml`, `default-size.xml`, `validators.xml` — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html). **[small: value-type "stereotype" bundling validation + presentation]**
- `@Calculation("((hours * worker.hourPrice) + tripCost - discount) * vatPercentage / 100")` (v5.7): arithmetic over same-entity properties incl. reference paths, recalculated live in UI, persisted only on save, all operands must be displayed; vs. calculated property = getter without field, read-only, not persistent, `@Depends("unitPrice")` lists triggers for UI recalculation; vs. `@Formula` (Hibernate SQL fragment computed by DB, filterable in list mode, no `@Depends`) — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html). **[small: three flavours of derived property — expression / Java / SQL]**
- `@DefaultValueCalculator(value=Calc.class, properties={@PropertyValue(name="x", from="drivingLicence.type")})`: initial value only; `@PropertyValue` injects constants or other displayed properties (recalculated when source changes since v5.1); `IJDBCCalculator` variant gets a connection — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html).
- `@PropertyValidator(value=..., properties=..., onlyOnCreate=..., message=...)` runs before store; `@EntityValidator` for multi-property checks with `@PropertyValue` wiring; `@RemoveValidator` can deny removal — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html). **[small: delete-precondition validator; "onlyOnCreate" flag]**
- References: `@ManyToOne(fetch=LAZY)` recommended always; `@Embedded` embeddable with references allowed; collections: `@OneToMany(mappedBy, cascade=REMOVE)` + `@OrderBy`/`@XOrderBy`, `@Size(min=1)` element-count constraint checked before save, `@Condition("${warehouse.zoneNumber} = ${this.warehouse.zoneNumber} AND ...")` restricts shown elements (UI-only; getter returns null), `@OrderColumn` (v5.3), `@ElementCollection` of embeddables edited inline and saved with parent (v5.0; no nested collections) — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html).
- Finders are static methods using `XPersistence.getManager()` JPQL (style recommendation, not framework construct); business methods on the entity preferred over controller actions; `@PrePersist` for defaults on create; enums shown as combos, `@Required` on enum removes empty option (v5.3), `IIconEnum` for icons — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html).

**UI derivation [BIG as a pattern: layout DSL string on the entity; the pieces are small]**
- `@View(name, members="zoneNumber, officeNumber, number; name")` — comma same row, semicolon new row, `#` column alignment, `[ ]` groups (framed), `{ }` sections (tabs), `extendsView="super.X"`/`"DEFAULT"`; `forViews`/`notForViews` scope member annotations to views; `flowLayout=true` ignores `#`/`;` for responsive layout — [view docs](https://openxava.org/OpenXavaDoc/docs/view_en.html).
- `@ReferenceView("Simple")`, `@NoFrame`, `@SearchAction`, `@OnChangeSearch`; `@DescriptionsList(descriptionProperties, depends="family", condition="${family.number} = ?", order=...)` dependent combos; `@CollectionView`, `@ListProperties("number, name, seller.level.description")`, `@NewView/@EditView` (v7.7), `@ListAction/@RowAction/@DetailAction`, `@OnChange(Action.class)`, `@Action("Delivery.generateNumber")` link beside field, `@ReadOnly(forViews=...)` — [view docs](https://openxava.org/OpenXavaDoc/docs/view_en.html).
- `@Tab(name, properties="number, name+", baseCondition="${zone} = 'A'", defaultOrder="${year} desc", filter=IFilter.class, rowStyles=@RowStyle(...), editableProperties (v7.6, model validations run but not controller actions/@OnChange), editor/editors)`; `baseCondition` may start with `from` (partial JPQL) or be a full select; `tabs-default-values.xml`; collection paths in `properties` let users filter parents by collection content — [tab docs](https://openxava.org/OpenXavaDoc/docs/tab_en.html). **[small: "list view spec" = named read model with base condition, order, columns]**

**Modules and controllers [medium: module = model + controllers + view + tab]**
- `application.xml` `<module name>` with `<model>`, `<view>`, `<web-view>`, `<tab>`, `<controller>`*, `<mode-controller>` (Mode|DetailOnly), `<env-var>`; every entity gets a default module (`/modules/Invoice`) with `Typical` controller (extends `Print` and `CRUD`); resolution order: explicit module → controller with same name → `<default-module>` → fallback Typical. Read-only module via `XAVA_SEARCH_ACTION=CRUD.searchReadOnly`, list-only via empty `XAVA_LIST_ACTION` — [application docs](https://openxava.org/OpenXavaDoc/docs/application_en.html).
- `controllers.xml`: `controller` groups `action`s and `subcontroller`s, `extends`, `excluded-actions`; action attributes for mode (list/detail), confirm, keystroke, `on-init`; actions are short-lived objects, session objects injected with `@Inject`/`<use-object>` and written back; `IAvailableAction.isAvailable()` for conditional actions; `ViewBaseAction`/`TabBaseAction`; override defaults by redefining a controller of the same name (must keep all original action names); `default-controllers-ext.xml` (v7.5) — [controllers docs](https://openxava.org/OpenXavaDoc/docs/controllers_en.html).

**Security and access tracking (XavaPro, commercial)**
- XavaPro adds users/roles/modules tables; modules public/hidden/read-only per role; fine-grained restriction of actions, properties, references, collections per user or read-only "without programming"; History module logs data access and actions with date, time, user, IP, action, entity, key and field-level change details; multitenancy (several companies, each limited to own data); automatic REST API with CRUD, pagination, filtering, OpenAPI, JWT; generated mobile UI — [XavaPro](https://www.openxava.org/xavapro). Open-source edition scope not stated on the page.

**Criticism / limitations**
- A review site states the convention-based approach "can become restrictive when applications require custom user interfaces or non-standard workflows" and that OpenXava is optimized for server-rendered apps rather than SPAs/REST backends (third-party, weak) — [FitGap](https://us.fitgap.com/products/openxava). Jmix's comparison page claims OpenXava "comes with more limitations" for complex customization (competitor marketing) — [Jmix vs OpenXava](https://jmix.io/jmix-vs-openxava).
- Doc-stated constraints: `@Calculation` operands must all be displayed in the UI; `@Condition` affects only the generated UI (getter returns null); `@ElementCollection` embeddables can't hold collections; `@Formula` can't use `@Depends` — [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html).
- No independent, hands-on critical reports found (see Gaps).

### Inferences
- OpenXava's split of derived properties into `@Calculation` (UI-live expression), getter-only calculated (Java), and `@Formula` (SQL) maps well onto ObjectFlow (expression/Java) vs ManMap (SQL read model column) and suggests a declarative "depends-on" list for recalculation.
- `@Tab` is effectively a declarative *read model over an entity* (columns incl. paths, base condition, default order, filter, sums) — close to ManMap's custom-SQL DTO read models but derived from the mapping instead of hand-written.
- `@RemoveValidator` / `@EntityValidator(onlyOnCreate)` show that validations benefit from a *lifecycle phase* attribute (create/update/delete) — a small addition to ObjectFlow validations.
- OpenXava's entity-level `@SearchKey` and `@DescriptionsList` are declarations of "how to look this entity up / how to show it in a combo" — a reference-selection contract that is UI-independent.

### Gaps
- Current OpenXava 8.0 "access tracking"/History module details (tables, how enabled) are only on the XavaPro marketing page; a second targeted search found no documentation page.
- `@Finder` annotation does not appear in the model docs excerpt; finders are plain static methods.
- The model docs page was only partially read (first 100k of 124k chars); `@ListProperties` and `@ReferenceView` were obtained from the view docs instead.
- No neutral critical literature on OpenXava found; comparison-site statements are weak.
- Declarative status/state handling: a targeted search returned nothing OpenXava-specific; the fetched model/view/controller docs offer only enums-as-combos, `@OnChange` actions, `IAvailableAction.isAvailable()` for conditional actions and `@RemoveValidator` — no transition table or state-machine construct ([controllers docs](https://openxava.org/OpenXavaDoc/docs/controllers_en.html), [model docs](https://openxava.org/OpenXavaDoc/docs/model_en.html)).

## Key question 4 — Jmix (ex CUBA): entities and traits, fetch plans, DataManager with security, row-level roles, Entity Log, soft deletion, dynamic attributes/model, pessimistic locking, reports, BPM, REST, snapshots

### Takeaway
Jmix is the richest in *data-access-level* declarations: entity traits (audit, soft delete, version, UUID, tenant) by annotation, `@Composition` aggregates with `@OnDelete/@OnDeleteInverse` policies, explicit fetch plans (named graphs) governing loading, a `DataManager` that enforces resource-role CRUD/attribute policies and row-level JPQL/predicate policies on every load/save, entity events before/after commit, Entity Log and snapshots as add-ons, and a generic REST API that reads the same security. Its lazy-loading-with-fetch-plans, soft deletion and runtime roles are also where documented pitfalls cluster.

### Cited Findings

**Entities and traits [small→medium: declarative traits]**
- Every JPA or DTO entity needs `@JmixEntity`; traits: Has UUID (`@JmixGeneratedValue`, assigned in memory on creation; UUIDv7 since 2.5), Versioned (`@Version` Integer, never set by app), Audit (`@CreatedBy @CreatedDate @LastModifiedBy @LastModifiedDate`, filled on save), Soft Delete (`@DeletedBy @DeletedDate`), Has Tenant ID (`@TenantId`, Multitenancy add-on); `@InstanceName` on attribute or method (with `@DependsOnProperties`) gives the human label; `@Composition` = child cannot exist without owner, edited and saved together in one transaction; `@OnDelete(DENY|CASCADE|UNLINK)` on soft-deleted entities, `@OnDeleteInverse` on referenced side; embedded entities `@JmixEntity @Embeddable`; `@PropertyDatatype("year")`; `@Store(name="inmem")` for additional data stores; `@JmixEntity(annotatedPropertiesOnly=true)` — [Entities](https://docs.jmix.io/jmix/data-model/entities.html). **[BIG: `@Composition` + delete policies as declared aggregate boundary; small: InstanceName]**
- Enumerations: `enum X implements EnumClass<String|Integer>` with `id` field, `getId()`, static `fromId()`; entity stores the raw id in a field of id type and converts in getter/setter, so constants can be renamed/reordered without data change — [Enumerations](https://docs.jmix.io/jmix/data-model/enumerations.html). **[small: persistence id per enum literal]**
- Soft deletion: remove marks records deleted; loads by id and JPQL exclude soft-deleted; to-many collections exclude deleted items but to-one references may still point at a deleted instance; unique constraints need DB-specific tricks (PostgreSQL partial index `where DELETED_DATE is null`; Oracle/SQL Server composite index incl. DELETED_DATE; MySQL/HSQL extra non-null `DELETED_DATE_NN` column kept in sync in setter); `PersistenceHints.SOFT_DELETION=false` to include deleted or hard-delete — [Soft deletion](https://docs.jmix.io/jmix/data-model/soft-deletion.html). **[BIG with caveats]**
- Bean Validation: attribute constraints, class-level constraints for cross-attribute rules, custom and composed constraints (`@ReportAsSingleViolation`), method validation (`@Validated` services, `@Valid` cascading), groups `Default`, `UiComponentChecks`, `UiCrossFieldChecks`, `RestApiChecks`; EclipseLink validates on save via DataManager/EntityManager/repositories (disable with `jakarta.persistence.validation.mode=NONE`); `@NotNull` marks field required in UI; date constraints set picker ranges; `CustomValidationException` for service-level errors in Bean-Validation format — [Bean validation](https://docs.jmix.io/jmix/data-model/bean-validation.html). **[small: validation groups per channel (UI/REST/service)]**

**Fetch plans and loading [BIG: explicit load graph as named declaration]**
- A fetch plan defines which part of the object graph is eagerly loaded; used by DataManager, UI data components and REST; declared inline in view descriptors (`<fetchPlan>`), programmatically (`FetchPlans` builder) or in shared `fetch-plans.xml` (`jmix.core.fetch-plans-config`) by name; built-ins `_local`, `_instance_name`, `_base` (= local + instance name + embedded); a reference in the plan is loaded in the same query with a join; references outside the plan are *lazily loaded on access* for JPA entities through DataManager ("fully compatible"), which can cause N+1; local attributes omitted from a plan are left empty and accessing them throws `IllegalStateException` ("Cannot get unfetched attribute"); id and version always loaded; partial plans recommended "sparingly" for wide entities in large lists — [Fetching](https://docs.jmix.io/jmix/data-access/fetching.html). (Jmix 3 docs; fetchMode AUTO/JOIN/BATCH not on this page.)
- Data repositories (Spring Data): `JmixDataRepository<E,ID>` over DataManager; derived methods, `@Query` JPQL (scalar/aggregate via `properties` into `KeyValueEntity`), `@FetchPlan` annotation or `FetchPlan` parameter (priority: param > context > annotation); `@ApplyConstraints(false)` switches to `UnconstrainedDataManager` — [Data repositories](https://docs.jmix.io/jmix/data-access/data-repositories.html).

**DataManager, security and events [BIG: data access API that enforces declared security; medium: entity events]**
- `DataManager.load(E.class).id()/ids()/all()/query()/condition()` with `one()/optional()/list()`; abbreviated JPQL (`select` omitted, alias `e`); `PropertyCondition`/`LogicalCondition` (negative operators exclude null by default); `lockMode()` for DB pessimistic locks; `loadValues(query).properties(...)` → `KeyValueEntity` projections and `loadValue(query, Type)` scalars (single data store only, not in REST DataStore); `save()` returns the saved instance which may differ because of events/triggers/access rules — "always continue with the returned instance"; `saveWithoutReload()`; `SaveContext` with `setDiscardSaved`; `remove()` dependents first; batches of ~1000; `UnconstrainedDataManager` skips security. Security effect: save/remove throw `AccessDeniedException` without CREATE/UPDATE/DELETE; load returns null/empty without READ (references still load); JPQL row-level policies apply only to root entity, predicate policies to root and linked entities — [DataManager](https://docs.jmix.io/jmix/data-access/data-manager.html). **[small: "KeyValueEntity" = ad-hoc projection — ManMap already has DTO read models]**
- `EntitySavingEvent` (before save, `isNewEntity()`), `EntityChangedEvent` (type create/update/delete, id, `AttributeChanges` with old values incl. old references/collections), `EntityLoadingEvent`; `@EventListener` runs before commit in same transaction (exception rolls back all), `@TransactionalEventListener` after commit (exceptions silent, needs `REQUIRES_NEW` to load/save); documented use cases: audit trail entity, recalculating `Order` amount from `OrderLine` changes, notification after commit, order-number generation, encryption on save/decrypt on load; only local attributes safe in saving/loading listeners — [Entity events](https://docs.jmix.io/jmix/data-access/entity-events.html).

**Security roles [BIG: declarative resource + row-level policies]**
- Resource roles as annotated interfaces: `@ResourceRole(name, code, scope)` with `@EntityPolicy(entityClass|entityName="*", actions)`, `@EntityAttributePolicy(attributes="*", action VIEW|MODIFY)`, `@ViewPolicy`, `@MenuPolicy`, `@SpecificPolicy` (checked in code via `AccessManager`); scopes `UI` and `API`; a user with no resource roles has no access at all; recommended fine-grained design-time roles aggregated into coarse ones; runtime roles editable in UI — [Resource roles](https://docs.jmix.io/jmix/security/resource-roles.html).
- Row-level roles: `@RowLevelRole` interface with `@JpqlRowLevelPolicy(entityClass, join="join {E}.customer c", where="c.active = TRUE")` using `{E}` alias and session params like `:current_user_id`, or `@PredicateRowLevelPolicy(entityClass, actions={READ|CREATE|UPDATE|DELETE})` returning `RowLevelPredicate<E>` (or `RowLevelBiPredicate` with ApplicationContext); runtime roles use Groovy predicates (`!{E}.confidential`), disable-able with `jmix.security.data.groovy-enabled=false` / global `jmix.core.unsafe-runtime-features-enabled`. Limitations: JPQL policy filters only the root entity, not nested collections; READ predicates run in memory per instance (slow for large sets); for entities loaded as both root and nested, define both — [Row-level roles](https://docs.jmix.io/jmix/security/row-level-roles.html).

**Audit: Entity Log and snapshots [medium]**
- Entity Log records the changed instance, old and new attribute values, when and by whom; configured at runtime (Audit → Entity Log → Setup: entity, attributes, Auto on commit vs Manual) or via `LoggedEntity`/`LoggedAttribute` rows (`AUDIT_LOGGED_ENTITY`, `AUDIT_LOGGED_ATTR`) e.g., in Liquibase; entries in `AUDIT_ENTITY_LOG`; export/import as JSON/ZIP; requires `entity-log` role. Limitations: does not work with native SQL; manual registration only for managed entities in a transaction (entities from DataManager are detached) — [Entity log](https://docs.jmix.io/jmix/audit/entity-log.html).
- Entity snapshots: object graph serialized to XML in `AUDIT_ENTITY_SNAPSHOT`, created e.g. after editor commit; `snapshotDiff` fragment compares snapshots (collection adds/removes highlighted; element position changes not recorded); `EntityDifferenceManager.getDifference`, `EntitySnapshotManager.extractEntity`; rollback not built in (1.x docs; 3.0 API still has `EntitySnapshotManager`) — [Entity snapshots 1.7](https://docs.jmix.io/1.x/jmix/1.7/audit/entity-snapshots.html), [forum: entity versioning](https://forum.cuba-platform.com/t/entity-versioning/16891), [EntitySnapshotManager 3.0 API](https://docs.jmix.io/api/3.0/io/jmix/audit/snapshot/EntitySnapshotManager.html). Jmix 3.0 removed XStream from Audit/Reports (must be added explicitly) — [3.0 what's new](https://docs.jmix.io/jmix/whats-new/release-3.0.html).

**Pessimistic locking [small: entity-level flag]**
- `@PessimisticLock(timeoutSec=120)` on the entity (default 300 s); standard detail view locks on open and switches to read-only if locked by someone else; `LockManager.lock(entity)` returns `LockInfo` of the holder or null; expiry via Quartz (`jmix.pslock.expiration-cron`, default every minute); locks replicated in cluster; admin Locks view can unlock — [Pessimistic locking](https://docs.jmix.io/jmix/pessimistic-lock/index.html).

**Dynamic attributes / Dynamic model [BIG: runtime schema extension]**
- Dynamic Attributes add-on: EAV-stored extra properties defined by administrators (name, type, validation, which views/components show them), loaded/saved with the entity automatically, shown in grids/forms — [Dynamic attributes](https://docs.jmix.io/jmix/dyn-attr/index.html).
- Dynamic Model add-on (3.0, Enterprise): adds real attributes (side tables) and new entities (dedicated tables) at runtime, with dynamic enums, references, collections, calculated attributes, validation, uniqueness, resource-role security, runtime views/menus/UI handlers, stored as versioned YAML with history, cluster-wide application — [Dynamic model](https://docs.jmix.io/jmix/dyn-model/index.html); webinar material labels it experimental — [Jmix 3.0 webinar/blog](https://www.jmix.io/blog/jmix-3-0-is-released/).

**REST, Reports, BPM**
- Generic REST add-on: CRUD on entities, calling registered service methods, predefined JPQL queries, files, data model metadata, current user/permissions; OAuth2; all endpoints respect Jmix security; Services API via `@RestService/@RestMethod` or `rest-services.xml` (`/rest/services/{service}/{method}`); custom Spring MVC controllers must use `EntitySerialization` with `DO_NOT_SERIALIZE_DENIED_PROPERTY` to honour attribute policies — [REST overview](https://docs.jmix.io/jmix/rest/index.html), [REST business logic](https://docs.jmix.io/jmix/rest/business-logic.html).
- Reports add-on: reports as annotated Java classes at design time or built at runtime/wizard; outputs DOCX/XLSX/HTML/CSV/PDF/text/table; XLSX grouping/aggregation/cross-tabs/formulas; access control, REST, execution history; PDF/DOC need LibreOffice — [Reports](https://docs.jmix.io/jmix/reports/index.html).
- BPM add-on: Flowable engine, requires commercial BPM subscription; BPMN 2.0 modeler in UI and Studio, process forms (Input Dialog, Jmix View, Custom Form), user/service/entity-data/email tasks, DMN 1.3 — [BPM](https://docs.jmix.io/jmix/bpm/index.html); schedule post noted BPM for 3.0 awaited a Spring-Boot-4-compatible Flowable 8 — [Jmix forum schedule](https://forum.jmix.io/t/release-schedule-update-2-8-lts-in-march-3-0-in-june/7313).

**REST Entities API details (closing earlier gap)**

**Security enforcement matrix (closing earlier gap)**
- DataManager checks entity *operation* policies for the root entity only (related entities load regardless); the authorization matrix marks DataManager "No" for entity *attribute* checks, which are applied in UI data-aware components and in REST `/entities`, `/queries`, `/services`; row-level JPQL policies root-only, predicate policies also filter linked entities; predicate CREATE/UPDATE/DELETE checks run in DataManager and REST `/entities` but not `/queries`; `UnconstrainedDataManager` and `EntityManager` perform no checks; direct JPQL (e.g., in reports) bypasses security; `AccessManager.applyConstraints()` with access contexts (`CrudEntityContext`, `EntityAttributeContext`, `UiShowViewContext`, `UiMenuContext`, `InMemoryCrudEntityContext`) is the extension point for custom constraints — [Authorization](https://docs.jmix.io/jmix/security/authorization.html). **Dynamic Attributes API (closing earlier gap)**

### Inferences
- Fetch plans are the closest existing analogue to what ManMap already does implicitly with explicit `get/where/joins` repositories; the transferable idea is *naming* a load graph (`_base`, `full`) once and reusing it across repository, UI binding and REST — without Jmix's lazy fallback, which is the source of its unfetched/N+1 problems.
- Jmix's `@Composition` + `@OnDelete(DENY|CASCADE|UNLINK)` is a declarative aggregate boundary that still keeps deletes explicit (DENY is the default-like safe choice); a "no cascade but DENY/UNLINK checks" variant would fit ManMap's explicit save/delete philosophy.
- Row-level policies as declared JPQL fragments appended to every load of a root type are directly reproducible in ManMap mapped queries (a repository-level "where fragment with session parameters"), and the documented limitation (root-only) is acceptable when there is no lazy loading.
- Entity events with `AttributeChanges` old values at check-in time give ObjectFlow's session a natural place for a declarative "on change of X recompute Y / log Z" rule; Jmix implements these as Spring listeners (hand-written), i.e., it is *not* declarative there — an opportunity.
- Validation groups per channel (UI/REST/service) suggest a small ObjectFlow option: tag validations with the phase/channel in which they apply.

### Gaps
- Dynamic Model limitations page not fetched; the exact DDL mechanism for side tables is undocumented on the overview page.
- `rest-queries.xml` syntax (query name, jpql, params, fetchPlan) not verified; only the endpoint `/queries/:entityName/:queryName` is confirmed.
- What exactly happens to a denied attribute in a DataManager result (the authorization matrix says DataManager does not check attributes; UI/REST do) — the UI rendering (hidden vs read-only) is not spelled out in the fetched pages.
- Jmix 3.0 release date not stated on the docs page; blog/forum suggest June–July 2026.
- Supported dynamic attribute types (references, enumerations) not listed on the API page.

## Key question 5 — Cross-platform: value objects/embeddables, enums with persistence values, computed properties, cross-entity invariants, aggregates vs free navigation, read models/projections, background jobs

### Takeaway
All four lean on JPA embeddables for value objects and none has a richer value-object concept than MoWare's; enums with explicit persistence ids are first-class only in Axelor (XML) and Jmix (EnumClass idiom); computed properties exist in three flavours (UI expression, Java getter, SQL formula); cross-entity invariants are expressed as class-level validators or event subscribers rather than declarations; only Jmix declares aggregate boundaries (`@Composition`); read models are ad-hoc (view models, KeyValueEntity, `@Tab`, formula fields); background work is Quartz-based everywhere, with Causeway uniquely persisting *commands* for background replay.

### Cited Findings
- Value objects / embeddables: Causeway treats values via JAXB/`@Property` in view models and mentions a separate Value Types page (not fetched) — [View models](https://causeway.apache.org/userguide/latest/view-models.html); OpenXava `@Embeddable` (no identity, owned, no callbacks; may hold references) and `@ElementCollection` of embeddables — [OpenXava model](https://openxava.org/OpenXavaDoc/docs/model_en.html); Jmix `@JmixEntity @Embeddable` embedded entities, included in `_base` fetch plan — [Jmix entities](https://docs.jmix.io/jmix/data-model/entities.html), [Fetching](https://docs.jmix.io/jmix/data-access/fetching.html); Axelor has no embeddable element in the documented field types (only relational types) — [Axelor models](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html).
- Enums with persistence values: Axelor `<enum>` items with `value` and `numeric="true"` — [Axelor models](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html); Jmix `EnumClass<ID>` with `fromId` and raw id column — [Jmix enumerations](https://docs.jmix.io/jmix/data-model/enumerations.html); OpenXava plain Java enums shown as combos (persistence via JPA default) — [OpenXava model](https://openxava.org/OpenXavaDoc/docs/model_en.html); Causeway enums automatically get drop-downs — [Drop-downs](https://causeway.apache.org/userguide/latest/drop-downs-and-defaults.html).
- Computed/derived: Causeway contributed properties via mixins (`prop`, side-effect-free) — [Mixins](https://causeway.apache.org/userguide/latest/mixins.html); Axelor calculated (Java body) vs formula (SQL body) fields — [Axelor models](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html); OpenXava `@Calculation` expression, getter-only + `@Depends`, `@Formula` SQL — [OpenXava model](https://openxava.org/OpenXavaDoc/docs/model_en.html); Jmix `@InstanceName` method with `@DependsOnProperties`, Dynamic Model "calculated attributes" — [Jmix entities](https://docs.jmix.io/jmix/data-model/entities.html), [Dynamic model](https://docs.jmix.io/jmix/dyn-model/index.html).
- Cross-entity invariants: Causeway domain events in validate phase let other modules veto ("referential integrity restriction") — [Events](https://causeway.apache.org/userguide/latest/events.html); OpenXava `@EntityValidator` with `@PropertyValue` wiring and `@RemoveValidator` — [OpenXava model](https://openxava.org/OpenXavaDoc/docs/model_en.html); Jmix class-level Bean Validation constraints and `EntitySavingEvent`/`EntityChangedEvent` listeners (e.g., recomputing Order amount from OrderLines before commit) — [Bean validation](https://docs.jmix.io/jmix/data-model/bean-validation.html), [Entity events](https://docs.jmix.io/jmix/data-access/entity-events.html); Axelor `<action-validate>` with `<error if>`/`<alert if>` bound to onSave (6.1 page) — [action-validate](https://docs.axelor.com/adk/6.1/dev-guide/actions/action-validate.html).
- Aggregates vs free navigation: Causeway recommends a repository per aggregate root but is "less strict than classic DDD"; parts reached via lazily loaded collections — [Domain entities](https://causeway.apache.org/userguide/latest/domain-entities.html); Jmix `@Composition` (saved together in one transaction) and `@OnDelete`/`@OnDeleteInverse` (DENY/CASCADE/UNLINK) — [Jmix entities](https://docs.jmix.io/jmix/data-model/entities.html), [Soft deletion](https://docs.jmix.io/jmix/data-model/soft-deletion.html); Axelor one-to-many `orphanRemoval` default true — [Axelor models](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html); OpenXava collections with `cascade=REMOVE` and `@ElementCollection` saved with parent — [OpenXava model](https://openxava.org/OpenXavaDoc/docs/model_en.html).
- Read models / projections: Causeway view models (incl. mapping an RDBMS view to a non-durable entity as public contract) and JAXB DTOs — [View models](https://causeway.apache.org/userguide/latest/view-models.html); Jmix `loadValues` → `KeyValueEntity`, repository `@Query` with `properties`, Reports datasets — [DataManager](https://docs.jmix.io/jmix/data-access/data-manager.html), [Data repositories](https://docs.jmix.io/jmix/data-access/data-repositories.html); OpenXava `@Tab` with partial/complete JPQL select and `+` sums — [Tab docs](https://openxava.org/OpenXavaDoc/docs/tab_en.html); Axelor formula fields and `<action-view><domain>` filtered views — [Axelor models](https://docs.axelor.com/adk/7.4/dev-guide/models/models.html), [action-view](https://docs.axelor.com/adk/8.0/dev-guide/actions/action-view.html).
- Background jobs: Causeway `BackgroundService` persists commands for a Quartz `RunBackgroundCommandsJob` — [Command Log](https://causeway.apache.org/userguide/latest/commandlog/about.html); Jmix pessimistic lock expiry and other scheduling via Quartz add-on — [Pessimistic locking](https://docs.jmix.io/jmix/pessimistic-lock/index.html); Axelor change tracking runs asynchronously after the transaction and IMAP fetching needs Quartz — [Messaging 8.1](https://docs.axelor.com/adk/8.1/dev-guide/modules/messaging.html).
- Optimistic locking everywhere: Causeway `@Version` — [Domain entities](https://causeway.apache.org/userguide/latest/domain-entities.html); Axelor `Model.version` and `__check_version` view flag — [AuditableModel](https://docs.axelor.com/adk/8.1/javadoc/com/axelor/auth/db/AuditableModel.html), [action-view](https://docs.axelor.com/adk/8.0/dev-guide/actions/action-view.html); OpenXava `@Version` — [OpenXava model](https://openxava.org/OpenXavaDoc/docs/model_en.html); Jmix Versioned trait — [Jmix entities](https://docs.jmix.io/jmix/data-model/entities.html).

- Declarative status/state handling: none of the four platforms offers a transition table or state-machine construct in the fetched documentation. Axelor models status as an `integer` field with a `selection` list, shows it via `NavSelect`, and guards transition buttons with `showIf="statusSelect == N"` plus action chains — [Widgets 8.0](https://docs.axelor.com/adk/8.0/dev-guide/web-client/widgets.html), [AOS SaleOrder views](https://raw.githubusercontent.com/axelor/axelor-open-suite/master/axelor-sale/src/main/resources/views/SaleOrder.xml); Causeway uses enums plus per-action `hide/disable/validate` rules and domain events — [Business rules](https://causeway.apache.org/userguide/latest/business-rules.html), [Events](https://causeway.apache.org/userguide/latest/events.html); Jmix uses `EnumClass` attributes plus hand-written listeners or BPM (no add-on found) — [Enumerations](https://docs.jmix.io/jmix/data-model/enumerations.html), [Jmix marketplace](https://www.jmix.io/marketplace/); OpenXava uses enums and `IAvailableAction` conditional actions — [controllers docs](https://openxava.org/OpenXavaDoc/docs/controllers_en.html). Process-level state lives in BPM engines (Axelor `$wkfStatus`, Jmix Flowable) — [Script tasks 3.2](https://docs.axelor.com/studio/3.2/bpm-docs/BPMN/tasks/script_task.html), [Jmix BPM](https://docs.jmix.io/jmix/bpm/index.html).
- Value objects, revisited with the Causeway value-types page: Causeway is the only one of the four with a *framework-level* value-type contract (parse/render/defaults/decompose/id-stringify) and composite values edited through a mixin, persisted via JPA converter or `@Embeddable`; composites cannot be part of identifiers — [Value types](https://causeway.apache.org/userguide/latest/value-types.html).

### Inferences
- Candidate **big ideas** for ObjectFlow/ManMap (ranked by how little they depend on an ORM/lazy loading): (1) member-level business rules hide/disable/validate/choices/default on entity properties and command parameters (Causeway); (2) declarative conditional change-tracking messages per field (Axelor `<track>`); (3) command record + property-diff audit correlated by interaction id at session check-in (Causeway); (4) declared aggregate boundary with DENY/UNLINK delete policies and "saved together" composition, without cascade (Jmix); (5) named load graphs reused by repository/UI/REST (Jmix fetch plans minus lazy fallback); (6) declarative row-level security fragments with session parameters (Jmix JPQL policies) and a metamodel-derived permission tree (SecMan); (7) mixin-style contributed members from other modules (Causeway); (8) formatted business sequences (Axelor).
- Candidate **small** items: enum literal persistence ids (Axelor/Jmix); `onlyOnCreate`/delete-phase validators (OpenXava); `@SearchKey`/instance-name/name-column lookup contracts (OpenXava/Jmix/Axelor); three flavours of derived property with depends-on lists; `massUpdate`, `translatable`, `encrypted`, `namecolumn` flags (Axelor); validation groups per channel (Jmix); `@PessimisticLock(timeout)` entity flag (Jmix); checker rules such as "parameter of collection type needs choices source" (Causeway validator); formatted-sequence field; "only-if-system-changed" command logging policy.
- Status/state handling is hand-written or BPM-driven in all four; MoWare's explicit status types are already ahead, and the gap worth closing is a declarative transition table (allowed transitions, guards, side effects) that generates the `showIf`/disable rules Axelor and Causeway otherwise code by hand.
- Things all four hand-write (no declaration): cross-entity invariants spanning aggregates, denormalization/recalculation on change, notifications after commit — these are implemented as listeners/validators in Java in every platform, so a declarative form in ObjectFlow would go beyond the state of the art.

### Gaps
- Confirmed by targeted searches: no declarative *state machine* in any of the four (see status finding above). ObjectFlow's status types therefore have no direct counterpart to borrow from; the closest declarative fragments are Axelor's `selection-in` attribute (narrowing allowed values per context) and `showIf` button guards.
- No independent benchmarks or peer-reviewed evaluations found for Axelor, OpenXava or Jmix; criticism is limited to forum anecdotes, vendor comparisons and doc-stated limitations.
- Background job declarations beyond Quartz wiring (e.g., declarative scheduling on the model) were not found in any platform's fetched docs.
