## Key question 1: iDempiere / ADempiere — Application Dictionary, Document Engine, Model Validators, Processes, Workflow, Info Windows, sequences, multi-tenancy, accounting facts

### Takeaway
iDempiere's core idea is a *metadata-driven* platform: tables, columns, references, validation rules, callouts, processes, info windows, workflows and document types are rows in `AD_*` tables, interpreted at runtime by a small number of generic engines (PO persistence, DocumentEngine, ModelValidationEngine/OSGi events, SvrProcess, workflow engine, Doc posting). The document lifecycle (DocStatus/DocAction with prepareIt/completeIt/voidIt/reverseCorrectIt...) and the hook timings around it are the single most reusable pattern; the price is hand-written Java per action, status transition logic buried in one 1300-line class, and many string-typed conventions.

### Cited Findings

**Versions / status**
- iDempiere 13 "Orion" is presented as an LTS release; the wiki changelog runs into April 2026 and a Feb-2026 committee meeting says Release 13 was ready — [iDempiere 13 announcement](https://idempiere.org/?p=3658); [ChangeLog Release 13](https://wiki.idempiere.org/en/ChangeLog_Release_13) (snippet).
- ADempiere latest stable: 3.9.4 (Jan 2023); forked from Compiere in Sept 2006; GPLv2; database support limited to PostgreSQL and Oracle; Application Dictionary "extends the Data Dictionary concept into the application" so entities, validation rules and screen layouts are controlled from within the application — [Wikipedia ADempiere](https://en.wikipedia.org/wiki/ADempiere).

**Application Dictionary (AD) — [BIG] metadata-as-data model of the whole app** 
- AD_Table flags: View (not synchronized to DB), Data Access Level (default role access), Maintain Change Log (writes to AD_ChangeLog), Records Deleteable, High Volume. Tooling: "Create Columns from DB", "Synchronize Column" (creates/alter table in DB) — [ADempiere AD overview](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html).
- AD_Column: System Element (name/description inherited from AD_Element at save), **Column SQL** (virtual column = SELECT expression joined to main table), Reference (data type + GUI behaviour), Validation rule / Reference Key (dynamic vs. static filtering), **Default Logic** (context variables or SQL; `;`-separated alternatives, first non-null wins), Key / Parent Link column (table may have several parents), Mandatory / Updateable / Always Updateable, **Read-only logic / Mandatory logic** (conditional expressions; IsActive and Processed already make a record read-only), Identifier (columns used in lists), **Callout**, Selection Column, Translated (`<Table>_Trl` convention), Encryption (not reversible) — [same](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html).
- AD_Reference types: Account, Amount, Button, Date, ID, Integer, List, Location, Memo, Number, Quantity, Search, String, Table, Table Direct, Text, Text Long, Yes-No...; Table Direct derives table name from column name minus `_ID`; List = static key/name pairs stored as key with "no foreign-key protection" when a key changes; Table/Search carry a *table validation* (Table, Key Column, Display Column, WHERE, ORDER BY; WHERE may use context variables resolved at window start) — [same](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html).
- AD_Val_Rule (validation rule): SQL fragment appended to the WHERE clause of the referenced table/list; filters pick-lists dynamically with context variables; the iDempiere wiki lists rule types SQL, JavaScript, Java (ADempiere overview: SQL only) — [Validation Rules window (snippet)](https://wiki.idempiere.org/en/Validation_Rules_(Window_ID-103)); [ADempiere AD overview](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html).
- Entity types ("Dictionary", "Adempiere" reserved) map to their own model package since 3.3.1 (e.g., `org.evolution.model`) — generated `X_` classes per entity type — [same](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html).
- Criticism recorded on the page itself: "String callouts fire on every keystroke"; advises against using callouts for validation ("must still happen on save"); field changes take effect only after restart because of caching; changing standard model classes requires manual merges on each upgrade — [same](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html); [ADempiere Model Validator page](https://adempiere.io/community/wiki/developers-guide/model-validator.html).

**Callouts — [SMALL] (field-change hooks declared per column)**
- `IColumnCallout.start(ctx, WindowNo, GridTab mTab, GridField mField, Object value, Object oldValue)`: "Callout's are used for cross field validation and setting values in other fields. When returning a non empty (error message) string, an exception is raised. When invoked, the Tab model has the new value!" — [IColumnCallout.java](https://github.com/idempiere/idempiere/blob/master/org.adempiere.base/src/org/adempiere/base/IColumnCallout.java).
- Callout class is a string on AD_Column; runs in the UI tab model, i.e. not on API/import paths (hence the advice that save-time validation must be separate) — [ADempiere AD overview](https://adempiere.io/community/wiki/developers-guide/application-dictionary-overview.html).

**Document Engine — [BIG] generic status/action lifecycle with per-document hook methods**
- `DocAction` interface, status codes: DR Drafted, IP In Progress, AP Approved, NA Not Approved, CO Completed, CL Closed, VO Voided, RE Reversed, IN Invalid, WC Waiting Confirmation, WP Waiting Payment, ?? Unknown. Action codes: PR Prepare, AP Approve, RJ Reject, CO Complete, WC WaitComplete, VO Void, CL Close, RC Reverse-Correct, RA Reverse-Accrual, RE Re-activate, IN Invalidate, XL Unlock, PO Post, `--` None. Methods: `prepareIt()` returns new status (IP or IN), `completeIt()` returns status (CO, IP, IN, WC/WP), `voidIt/closeIt/reverseCorrectIt/reverseAccrualIt/reActivateIt/approveIt/rejectIt/unlockIt/invalidateIt` return boolean, plus `getSummary`, `getDocumentInfo`, `getProcessMsg`, `getDoc_User_ID`, `getApprovalAmt`, `getC_Currency_ID`, `createPDF` — [DocAction Javadoc 13](https://jenkins-artifacts.idempiere.org/javadoc13/org/compiere/process/DocAction.html).

- "What makes documents special from other entities ... are that they have a document status"; a document generating accounting needs `Posted`, `ProcessedOn`, `C_DocType_ID`; after completion a matching `Doc_*` class handles posting, loaded via factory in iDempiere — [Create a custom document class (snippet)](https://wiki.idempiere.org/en/Create_a_custom_document_class); [Hackers Guide to Documents (snippet)](https://wiki.idempiere.org/en/Hackers_Guide_to_Documents).

- **Period control [SMALL→BIG]:** `MPeriod.isOpen(ctx, DateAcct, DocBaseType, AD_Org_ID, forPosting)` — period open state is per DocBaseType and per Org and distinguishes "open for DocAction" from "open for posting"; `isOpen(ctx, tableID, recordID, trxName)` resolves period from a record — [MPeriod.java](https://github.com/idempiere/idempiere/blob/master/org.adempiere.base/src/org/compiere/model/MPeriod.java). `C_PeriodControl` has DocBaseType, PeriodStatus, PeriodAction — [I_C_PeriodControl Javadoc](https://jenkins-artifacts.idempiere.org/javadoc13/org/compiere/model/I_C_PeriodControl.html). iDempiere 11 added a "closed for new documents" period state (blocks document actions, still allows reposting) and "disallow period close when unposted completed documents exist" — [NF11 Period Control Document Close (snippet)](https://wiki.idempiere.org/en/NF11_Period_Control_Document_Close); [NF11 Period Close Disallow (snippet)](https://wiki.idempiere.org/en/NF11_Period_Close_Disallow_When_Unposted_DocsExists).
- Reversal pattern: `reverseCorrectIt` (same date) vs `reverseAccrualIt` (current date); result status RE; the reversed document references its counterpart via `Reversal_ID` (metasfresh keeps the same column) — [DocAction Javadoc](https://jenkins-artifacts.idempiere.org/javadoc13/org/compiere/process/DocAction.html); [metasfresh IDocument.java `Reversal_ID`](https://github.com/metasfresh/metasfresh/blob/master/backend/de.metas.adempiere.adempiere/base/src/main/java/de/metas/document/engine/IDocument.java).

**Criticism / limitations**
- A 2012 thesis frames ADempiere's architecture as outdated relative to its functionality and proposes DI/REST replacements; metasfresh's founders cite "tight coupling to the database" inherited from Compiere as a fork motive — [UDLA thesis](https://dspace.udla.edu.ec/jspui/handle/33000/2588?mode=full); [Wikipedia Metasfresh](https://en.wikipedia.org/wiki/Metasfresh).
- Status/action rules are code, not data: valid-action computation is a large per-table switch in `DocumentEngine.getValidActions` — [DocumentEngine.java](https://github.com/idempiere/idempiere/blob/master/org.adempiere.base/src/org/compiere/process/DocumentEngine.java).
- Hooks return error *strings* (null = ok), event types are ints/topic strings; several compatibility aliases (`TYPE_NEW`, `CHANGETYPE_NEW`, `DOCTIMING_*`) — [ModelValidator.java](https://github.com/idempiere/idempiere/blob/master/org.adempiere.base/src/org/compiere/model/ModelValidator.java).

### Inferences
- The AD+PO+DocumentEngine combination is a *runtime interpreter* of metadata; ObjectFlow/ManMap generate code at design time, so the transferable part is the **vocabulary** (status codes, action names, before/after timings, period control, posting statuses), not the interpreter.
- Period control is a cleanly separable, data-driven constraint ("is action X allowed for doc base type Y on date Z for org O") that could be a declarative precondition family.
- Info Windows are the closest analogue to ManMap's "custom SQL + row mapper into DTO" and show what to add declaratively: criteria columns with operators/functions, identifier columns, access-filter injection, paging, related sub-queries.
- The dual validator/OSGi mechanism shows that the *timing enumeration* is the stable asset; registration mechanics churn (interface → OSGi topics → annotations).

## Key question 2: metasfresh — evolution from ADempiere: model interceptors, document actions, async workpackages, event bus/notifications, caching, IQueryBL, migration scripts, "terminal" style

### Takeaway
metasfresh kept the ADempiere data model and lifecycle codes but replaced the hook, query and job APIs with typed Java constructs: annotation-based model interceptors (`@Interceptor/@ModelChange/@DocValidate` with `ifColumnsChanged`, `afterCommit`), a `DocumentHandler` SPI instead of `M*` subclasses, a typed query builder (`IQueryBL`), an async "workpackage" queue with DB-backed elements, a local/distributed event bus (RabbitMQ) and a table-keyed cache with remote invalidation. Migration is by SQL scripts, auto-recorded from Application Dictionary changes.

### Inferences
- metasfresh's path is the one closest to MoWare: keep the lifecycle vocabulary, make hooks typed and column-aware, move from inheritance to SPI/handler objects, and bind background work to the committing transaction (`bindToThreadInheritedTrx`, `afterCommit`).
- `ifColumnsChanged` on a hook and `expectedDocStatus` on `processEx` are cheap, high-value checker-style rules.
- The "collect/collectChildren" navigation in IQueryBuilder is a declarative substitute for joins that fits ManMap's "mapped queries" without introducing lazy loading.
- Recording dictionary edits as SQL migration scripts is the ERP equivalent of a schema migration story MoWare lacks; the mechanism (log every metadata write as a replayable statement) is generic.

## Key question 3: Apache OFBiz — Entity Engine (entitymodel XML, view-entities, EECA), Service Engine (service definitions, SECA, transactions, async/job scheduler), Minilang/Groovy, Entity Sync, status items / status valid changes

### Takeaway
OFBiz is the most *fully declarative* of the Java systems: entities, relations, view-entities (joins/aggregates as read models), service contracts (typed IN/OUT attributes, transaction and retry policy), and both entity- and service-level event-condition-action rules are XML; status machines are **data** (`StatusItem`/`StatusValidChange`) checked by services. Its weaknesses are a steep learning curve, XML-as-code (Minilang deprecated since 2017 but still in trunk), and hand-created scheduler jobs.

### Cited Findings

**Versions / status**
- 24.09 series is feature-frozen with bug-fix point releases: 24.09.01 released April 2025; 24.09.07 June 2026 — [Release notes 24.09.01](https://ofbiz.apache.org/release-notes/24.09.01.html); [Release notes 24.09.07](https://ofbiz.apache.org/release-notes/24.09.07.html).
- 24.09.01 framework changes: GroovyDsl allowed in FlexibleStringExpander, reduced `${groovy:}` expressions, optimized `removeJob` service, security fixes incl. path-traversal RCE CVE-2024-36104 — [Release notes 24.09.01](https://ofbiz.apache.org/release-notes/24.09.01.html).

**Entity Engine — [BIG] declarative entity model with relations, locking, stamps**
- `<entity entity-name package-name table-name? enable-lock? never-cache? no-auto-stamp? auto-clear-cache?>` with `<field name type/>`, `<prim-key field/>`, `<relation type="one|one-nofk|many" rel-entity-name fk-name?><key-map field-name rel-field-name?/>`; `one` creates FK, `one-nofk` none, `many` no FK and key-maps not restricted to PK — [Entity Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Entity+Engine+Guide); [entitymodel.xsd](https://github.com/apache/ofbiz-framework/blob/trunk/framework/entity/dtd/entitymodel.xsd) (attributes `enable-lock`, `no-auto-stamp`, `never-cache`, `auto-clear-cache`).
- `enable-lock="true"` = optimistic locking; requires `lastUpdatedStamp`; mismatch throws `EntityLockedException`; default false — [Entity Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Entity+Engine+Guide).
- Example:
  ```xml
  <entity entity-name="OrderItem" package-name="org.example.order" enable-lock="true">
    <field name="orderId" type="id"/><field name="orderItemSeqId" type="id"/><field name="productId" type="id"/>
    <prim-key field="orderId"/><prim-key field="orderItemSeqId"/>
    <relation type="one" rel-entity-name="Product"><key-map field-name="productId"/></relation>
  </entity>
  ``` — [Entity Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Entity+Engine+Guide).
- Delegator API: `GenericDelegator` create/find/store/remove, `GenericValue` self-storing, `storeAll` insert-or-update, `EntityCondition` (`EntityExpr`, `EntityConditionList`, `EntityFieldMap`, `EntityWhereString` as last resort), `EntityListIterator` streaming, `*Cache` find variants cleared automatically on create/store/remove — [Entity Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Entity+Engine+Guide).
- `EntityQuery` fluent API (`EntityQuery.use(delegator).from("StatusValidChange").where("statusId", a, "statusIdTo", b).cache(true).queryOne()`): "All methods to set options modify the EntityQuery instance then return this modified object to allow method call chaining"; `orderBy` overwrites earlier ordering; `cache(true)` reads/writes the entity cache — [EntityQuery Javadoc](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/entity/util/EntityQuery.html); [OrderServices.java](https://github.com/apache/ofbiz-framework/blob/trunk/applications/order/src/main/java/org/apache/ofbiz/order/order/OrderServices.java).

**View entities — [BIG] declarative joins/aggregates as read models**
- `<view-entity>` with `<member-entity entity-alias entity-name/>` (same entity may appear twice), `<alias entity-alias name field? prim-key? group-by? function?/>`, `<alias-all/>`, `<view-link entity-alias rel-entity-alias rel-optional?>` (`rel-optional="true"` = outer join), `<relation>` on the view, `<entity-condition>` (e.g. order-by); functions min, max, sum, avg, count, count-distinct, upper, lower; PK inferred from aliased PK fields; all members must be in the same database; join style ANSI/Theta configurable — [Entity Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Entity+Engine+Guide).
- Real example (`StatusValidChangeToDetail`): `alias-all` of SVC and SI, `view-link` SVC→SI on statusIdTo→statusId, `entity-condition order-by sequenceId` — [framework/common/entitydef/entitymodel.xml](https://github.com/apache/ofbiz-framework/blob/trunk/framework/common/entitydef/entitymodel.xml).
- Guide example of aggregate view:
  ```xml
  <view-entity entity-name="OrderItemTotal" package-name="org.example.order">
    <member-entity entity-alias="OI" entity-name="OrderItem"/><member-entity entity-alias="OH" entity-name="OrderHeader"/>
    <alias entity-alias="OI" name="orderId" group-by="true"/><alias entity-alias="OI" name="quantity" function="sum"/>
    <view-link entity-alias="OI" rel-entity-alias="OH"><key-map field-name="orderId"/></view-link>
  </view-entity>
  ``` — [Entity Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Entity+Engine+Guide).

**Entity ECA (EECA) — [BIG] persistence-level triggers calling services**
- Schema: `<entity-eca><eca entity operation event run-on-error? enabled?>` with `operation ∈ {create, store, remove, find, create-store, create-remove, store-remove, create-store-remove, any}`, `event ∈ {validate, run, return, cache-check, cache-put, cache-clear}`; children `<condition field-name operator value type?/>` (operators less, greater, less-equals, greater-equals, equals, not-equals, is-empty, is-not-empty, contains; types String, BigDecimal, Double, Long, Integer, Date, Timestamp, Boolean, Object...), `<condition-field>`, `<condition-service>`, `<set field-name value? format?/>` (formats append, to-upper, to-lower, hash-code, long, double, db-to-java, java-to-db...), `<action service mode="sync|async" result-to-value? abort-on-error? rollback-on-error? persist?/>` — [entity-eca.xsd](https://github.com/apache/ofbiz-framework/blob/trunk/framework/entity/dtd/entity-eca.xsd).
- Production example (`applications/product/entitydef/eecas.xml`): `Product create/return → indexProductKeywords (sync)` if `autoCreateKeywords != N`; `InventoryItem create-store/return` with conditions `productId is-not-empty`, `availableToPromiseTotal <= 0 (BigDecimal)` → `checkProductInventoryDiscontinuation` **async** — [product eecas.xml](https://github.com/apache/ofbiz-framework/blob/trunk/applications/product/entitydef/eecas.xml).
- `DelegatorEcaHandler` constants list the operations (create, store, remove, find) and events (validate, run, return, cache check/clear/put) — [DelegatorEcaHandler Javadoc](https://nightlies.apache.org/ofbiz/next/javadoc/org/apache/ofbiz/entityext/eca/DelegatorEcaHandler.html). Registered via `ofbiz-component.xml` `entity-resource type="eca"`; file conventionally `eecas.xml` in `entitydef` — [ESME/OFBiz collaboration page](https://cwiki.apache.org/confluence/display/ESME/Collaboration+with+OFbiz).

**Service Engine — [BIG] typed service contracts with transaction/retry policy**
- `<service name engine location? invoke? auth=true debug default-entity-name export=false max-retry=-1 require-new-transaction=true use-transaction=true transaction-timeout=0 semaphore=none|wait|fail semaphore-wait-seconds=300 semaphore-sleep=500 validate=true>`; `<attribute name type mode="IN|OUT|INOUT" optional?/>`; `<auto-attributes include="pk|nonpk|all" mode optional/>` derives attributes from an entity; `<implements service=".."/>` inherits an `interface` service; `<permission-service service-name main-action="CREATE"/>`; validation: required IN checked before call, OUT after; undeclared non-optional parameter → failure — [Service Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Service+Engine+Guide).
- Engines: java (static method), groovy, simple (Minilang), entity-auto (generated create/update/delete with four PK patterns), interface, group (send-mode all/first-available/random/round-robin), routeservice (only its ECAs run), http (sync, remote `export=true`), jms (async), custom engines implementing `GenericEngine`/`GenericAsyncEngine` — [Service Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Service+Engine+Guide).
- Caveats recorded: a same-named service in a later component silently overrides an earlier one; `max-retry` only for persisted async; async ECA actions never update the parent context — [Service Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Service+Engine+Guide).

**Service ECA (SECA) — [BIG] cross-document consistency wiring**
- Events: `auth, in-validate, invoke, out-validate, commit, return` (and `global-commit-post-run` in current trunk); `<eca service event run-on-error=false>` with `<condition>`, `<condition-field ... to-field-name>`, `<set>`, `<action service mode="sync|async" result-to-context=true result-to-result=false ignore-error=true persist=false run-as-user?/>` — [Service Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Service+Engine+Guide); [order secas.xml](https://github.com/apache/ofbiz-framework/blob/trunk/applications/order/servicedef/secas.xml).
- Production example (order): on `changeOrderStatus` commit with `statusId == ORDER_CANCELLED` → `releaseOrderPayments`, `processRefundReturnForReplacement`; on `global-commit-post-run` with `statusId == ORDER_COMPLETED` and `statusId != oldStatusId` → `createInvoiceFromOrder (run-as-user=system)`, `resetGrandTotal`, `sendOrderCompleteNotification (async, persist=true)`, `createReturnItemForRental`; on `commit` with `orderTypeId == PURCHASE_ORDER` and `ORDER_APPROVED` → `createPaymentFromOrder` — [order secas.xml](https://github.com/apache/ofbiz-framework/blob/trunk/applications/order/servicedef/secas.xml).

**Async services and Job Scheduler — [BIG]**
- Async call = job queued in the Job Scheduler: `RecurrenceInfo`/`RecurrenceRule` created, `JobSandbox` row stored, context serialized into `RuntimeData`; one management thread + one thread per invocation; iCalendar-style recurrence; `dispatcher.schedule("svc", context, start, RecurrenceRule.SECONDLY, 5, 10)`; "Jobs are no longer defined in XML. They live in the JobSandbox entity ... currently have to be created by hand" — [Service Engine Guide](https://cwiki.apache.org/confluence/display/OFBIZ/Service+Engine+Guide).

**Status as data — [BIG] declarative state machine in tables**
- `StatusItem(statusId PK, statusTypeId, statusCode, sequenceId)`, `StatusType(statusTypeId, parentTypeId, hasTable)`, `StatusValidChange(statusId, statusIdTo PK; conditionExpression long-varchar; transitionName)` plus view `StatusValidChangeToDetail` — [framework/common/entitydef/entitymodel.xml](https://github.com/apache/ofbiz-framework/blob/trunk/framework/common/entitydef/entitymodel.xml).
- Enforcement is in services: `changeOrderStatus` queries `StatusValidChange` for (current, target) and returns error "...StatusIsNotAValidChange: [old] -> [new]" if no row; same pattern for order items (warning + skip), allocation plan header/item — [OrderServices.java ~L2457, L2550, L7037, L7091](https://github.com/apache/ofbiz-framework/blob/trunk/applications/order/src/main/java/org/apache/ofbiz/order/order/OrderServices.java).
- Status history is kept in separate `*Status` entities (e.g. `InventoryItemStatus` gained `changeByUserLoginId` in 16.11.01) — [OFBIZ-7624](https://issues.apache.org/jira/browse/OFBIZ-7624).

**Minilang / Groovy — criticism**
- Project decision (April 2017): deprecate Minilang; reasons "XML-based code is hard to deal with when it comes to refactoring", cannot be debugged, hard to review/maintain, verbose, slower; no new Minilang accepted; conversion to Groovy tracked in OFBIZ-9350 with subtasks (invoice services OFBIZ-9986, fact services OFBIZ-11030, Minilang tests OFBIZ-11232) — [Minilang deprecation wiki](https://cwiki.apache.org/confluence/x/-hwjB); [OFBIZ-9350](https://issues.apache.org/jira/browse/OFBIZ-9350).
- `framework/minilang` still exists in trunk (2026) — [ofbiz-framework tree](https://github.com/apache/ofbiz-framework/tree/trunk/framework/minilang).
- Third-party review: "significant learning challenge because of its framework conventions, custom entity engine, and unusual architecture"; documentation "thorough but overwhelming" — [FitGap review](https://us.fitgap.com/products/apache-ofbiz).

**Entity Sync — [SMALL]**
- `EntitySync(entitySyncId, runStatusId, lastSuccessfulSynchTime, lastHistoryStartDate, preOfflineSynchTime, offlineSyncSplitMillis, syncSplitMillis, syncEndBufferMillis, maxRunningNoUpdateMillis, targetServiceName, targetDelegatorName, keepRemoveInfoHours, forPullOnly, forPushOnly)` + `EntitySyncInclude(entityOrPackage, applEnumId)`, `EntitySyncIncludeGroup`, `EntitySyncHistory` — timestamp-window based replication of selected entities/packages between instances over HTTP/RMI, driven by the automatic `lastUpdatedTxStamp`/`createdTxStamp` stamps — [framework/entityext/entitydef/entitymodel.xml](https://github.com/apache/ofbiz-framework/blob/trunk/framework/entityext/entitydef/entitymodel.xml); [Sync Setup Notes and Example](https://cwiki.apache.org/confluence/x/AgaP).

### Inferences
- OFBiz separates "what may happen" (StatusValidChange rows) from "what happens when it does" (SECA on the status-change service) — a two-layer model MoWare could mirror: a declarative transition table on a status type plus declared post-commit reactions.
- `require-new-transaction`, `use-transaction`, `semaphore`, `max-retry`, `persist` are a compact vocabulary of **service execution policy** that is currently implicit in MoWare commands/services.
- View-entities with `function`/`group-by` are the declarative equivalent of ManMap's SQL-with-row-mapper read models; the aggregate example shows a "balance/total" read model without stored derived data.
- The `global-commit-post-run` event with `oldStatusId != statusId` condition is the idiom for "reaction to a state change after commit" — the explicit `oldStatusId` parameter is the price of not having a change-tracking engine.

### Gaps
- The cwiki page for EECA found by search was an ESME integration tutorial; no primary OFBiz doc page for EECA beyond the XSD was fetched.
- No documentation of `conditionExpression` semantics on `StatusValidChange` found (field exists; usage in services only checks row existence).
- Service ECA `global-commit-post-run` event not documented on the guide page (only seen in production XML).
- No measured/performance critique of EECA/SECA found.

## Key question 4: Odoo ORM (non-Java idea source) — computed/stored fields, onchange, constraints, record rules, domains, delegation inheritance, mail.thread tracking, server/automated/scheduled actions, state + statusbar

### Takeaway
Odoo pushes nearly all business-logic plumbing into **field and model declarations**: dependency-tracked computed fields (optionally stored), Python and SQL constraints, deletion guards, row-level security as declarative domains, a composable domain expression language, delegation inheritance, opt-in per-field change tracking, and metadata-defined automation (server actions, automation rules with rich triggers, cron). The old workflow engine was removed (v10/11) in favour of a plain `state` Selection field plus buttons and automation rules.

### Cited Findings

**Version**
- Current documentation branch 19.0; release date sources conflict: planned for Odoo Experience 18-20 Sept 2025 vs "released in October 2025" — [Odoo 19 preview (Agile Infoways)](https://www.agileinfoways.com/blog/odoo-19); [ecosire latest-version page](https://ecosire.com/blog/latest-odoo-version). No official release note fetched.

**Computed fields — [BIG] (declared derived data with dependency tracking)**
- `total = fields.Float(compute='_compute_total')` + `@api.depends('value','tax')`; not stored by default; `store=True` persists and makes it searchable/groupable; `compute_sudo` defaults True for stored, False for non-stored; `inverse=` makes it writable; `search=` supplies a domain-returning method; `recursive=True` required for self-referencing paths like `parent_id.X`; `precompute=True` computes before INSERT; dotted dependency paths allowed; `@api.depends_context('pricelist')` for context-dependent non-stored computes — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).
- Related fields: `fields.Char(related='partner_id.name', store=True, depends=[...])`; not stored/copied, readonly by default; x2many cannot be chained — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).
- Criticism (blog, single author): compute methods depending on their own output, writing other fields, or over-broad `@api.depends` cause "excessive recomputation, slow forms, and high CPU"; `store=True` misuse listed — [dev.to: Computed fields causing infinite recomputations](https://dev.to/aaron_jones_d34b57d1b44ba/computed-fields-causing-infinite-recomputationsodoo-4ck5).

**onchange — [SMALL]**
- `@api.onchange('partner_id')` runs on a pseudo-record in the form; cannot call CRUD; x2many cannot modify itself — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**Constraints — [SMALL] (two layers)**
- `@api.constrains('name','description')` runs only when a listed field is in the create/write vals; raise `ValidationError`; dotted names ignored. SQL: `_my_check = models.Constraint("CHECK (x > y)", "x > y is not true")`, `_name_idx = models.Index("(last_name, first_name)")`; message may be a function `(env, diag)` — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).
- Deletion guard: `@api.ondelete(at_uninstall=False) def _unlink_if_...: raise UserError(...)`; `Many2one(ondelete='set null'|'restrict'|'cascade')`; Selection `ondelete` per value (`'set null'|'cascade'|'set default'|'set VALUE'|callable`) — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).
- Error taxonomy: `UserError` (action makes no sense in current state), `ValidationError`, `AccessError`, `MissingError`, `RedirectWarning(message, action_id, button_text)` — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**Reserved/automatic fields — [SMALL]**
- Automatic: `id`, `display_name`, and with `_log_access` (defaults to `_auto`) `create_date, create_uid, write_date, write_uid`; reserved names: `name` (default `_rec_name`), `active` (archiving), `state` (Selection for lifecycle stages), `parent_id` (+ `_parent_store`/`parent_path` for `child_of`/`parent_of`), `company_id` (multi-company checks) — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**Access rights and record rules — [BIG] (row-level security as declared domains)**
- `ir.model.access`: per model+group `perm_read/write/create/unlink`; empty group = everyone incl. portal/public; grants are additive (union across groups); no matching ACL = denied — [Security 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/security.html).
- `ir.rule`: `model_id`, `groups` (empty = global), `domain_force` (domain; variables `time`, `user`, `company_id`, `company_ids`), `perm_*` selecting operations (all by default); default-allow if no rule applies; **global rules intersect (AND), group rules unite (OR) within global bounds; the first group rule added to a global ruleset restricts**; "creating multiple global rules risks non-overlapping rulesets that block all access" — [Security 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/security.html).
- Field access: `groups="..."` on a field removes it from views and `fields_get()` and raises AccessError on explicit read/write — [Security 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/security.html).
- Pitfalls documented: any public method is RPC-callable with arbitrary params; ACLs only checked during CRUD; avoid raw SQL / string-built domains; use `SQL` wrapper and `Domain` class — [Security 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/security.html).
- Performance: forum report of a 3rd-party OR'd follower/parent record rule causing ~4 s responses; OCA contributor: record rules "make little difference", bigger issue is PostgreSQL plans with skewed `company_id` distribution; multi-company deployments with 89 and 96 companies reported no penalty from company count — [Odoo forum: record rule performance](https://www.odoo.com/forum/help-1/record-rule-performance-235360); [OCA contributors list](https://odoo-community.org/groups/contributors-15/contributors-243418).

**Domains — [BIG] (filter expression language, composable, used for search, rules, triggers, window actions)**
- `Domain('name','=','ABC') & (Domain('phone','ilike','7620') | Domain('mobile','ilike','7620'))`; `'any'` operator over x2many sub-domains: `Domain('order_line', 'any', Domain('product_id.qty_available', '<=', 0))`; relative dates `'now'`, `'=monday -1w'`; `filtered_domain([...])` evaluates a domain in memory on a recordset; `_read_group(domain, groupby, aggregates like 'amount_total:sum')` — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**Inheritance — [BIG] delegation**
- Classical (`_name` + `_inherit` copies base into new model), extension (`_inherit` only, in-place), delegation (`_inherits = {'delegation.screen': 'screen_id'}` + `Many2one(..., required=True, ondelete='cascade')`: fields delegated, methods not), incremental field redefinition (same name/type overrides selected attributes) — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**ORM semantics worth noting — [SMALL]**
- Recordsets, prefetch of simple stored fields on iteration, `search_fetch`, x2many writes via `Command` (create/update/link/unlink/clear/set); raw SQL requires `flush_model([...])` before reads and `invalidate_model/invalidate_recordset` + `modified([...])` after writes — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**mail.thread tracking — [BIG] (opt-in per-field change history with subtypes)**
- `_inherit = ['mail.thread']`; `name = fields.Char(tracking=True)` "logs changes in chatter"; `_track_subtype(init_values)` chooses a `mail.message.subtype` (e.g. when `state` becomes confirmed); `message_post(...)`, `message_subscribe(...)`; context keys `mail_notrack` (skip value tracking), `tracking_disable` (skip all thread features), `mail_create_nolog`; `_mail_post_access` — [Mixins 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/mixins.html).
- Implementation: `_track_get_fields()` collects fields with a `tracking` attribute (plus `properties` fields whose definition record is tracked); `_track_prepare/_track_finalize/_message_track(fields_iter, initial_values_dict)` compare initial vs new values on write and create `mail.tracking.value` rows; `_track_template(changes)` can send templates on specific changes — [mail_thread.py (19.0)](https://github.com/odoo/odoo/blob/19.0/addons/mail/models/mail_thread.py).

**Server actions, automation rules, cron — [BIG] (metadata-defined behaviour)**
- `ir.actions.server.state ∈ {code, object_create, object_write, multi}` (docs); `fields_lines` with `type ∈ {value, reference, equation}`; evaluation context `model, record(s), env, datetime, dateutil, time, timezone, log(), UserError`; bindings `binding_model_id`, `binding_type=action|report`, `binding_view_types` — [Actions 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/actions.html).
- `base.automation.trigger` selection (source, 19.0): `on_stage_set, on_user_set, on_tag_set, on_state_set, on_priority_set, on_archive, on_unarchive, on_create, on_create_or_write, on_write (deprecated), on_unlink, on_change, on_time, on_time_created, on_time_updated, on_message_received, on_message_sent, on_webhook`; supporting fields `trg_selection_field_id`, `trg_field_ref`, `trg_date_id`, `trg_date_range(_type/_mode before|after)`, `filter_pre_domain`, `filter_domain`, `on_change_field_ids`, `trigger_field_ids`, `webhook_uuid`/URL — [base_automation.py (19.0)](https://github.com/odoo/odoo/blob/19.0/addons/base_automation/models/base_automation.py).
- User doc: "Before Update Domain defines the conditions a record must meet before the update" and "is not checked upon the creation of a record"; timing triggers "Based on date field", "After creation", "After last update" with Delay; the time-based check cron runs every 4 hours by default; `On UI change` only with Execute Code and only for UI edits; actions `Update Record, Create/Duplicate Record, Create Activity, Send Email/SMS, Add/Remove Followers, Execute Code, Send Webhook Notification`; actions run in sequence and later actions see earlier updates — [Studio Automation rules 19.0](https://www.odoo.com/documentation/19.0/applications/studio/automated_actions.html).
- `ir.cron`: `interval_number`, `interval_type (minutes|hours|days|weeks|months)`, `model_id`, `code` (`model.method()`), `nextcall`, `priority`; cron functions should process one batch (~seconds), the framework commits per batch and re-calls; `_commit_progress(processed, remaining=)`; `_trigger(at=)` schedules an immediate run; 3 consecutive errors skip a run, 5 failures over ≥7 days deactivate the job and notify the admin — [Actions 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/actions.html).
- `@api.autovacuum` registers a method with the daily vacuum cron; `@api.private` blocks RPC — [ORM API 19.0](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html).

**State field + statusbar + buttons — [SMALL]**
- Form `header` holds workflow buttons and `<field name="state" widget="statusbar" statusbar_visible="draft,posted" options="{'clickable': 1}"/>`; buttons `type="object|action"`, `invisible="state != 'done'"` Python expression, `confirm="..."`, `groups` — [View architectures 19.0](https://www.odoo.com/documentation/19.0/developer/reference/user_interface/view_architectures.html).
- Workflow engine removal: community answers state the engine was partially removed in Odoo 10 and removed in Odoo 11, replaced by the status bar plus automated actions (no official release note located) — [Odoo forum: workflows in Odoo 11](https://www.odoo.com/forum/help-1/workflows-in-odoo-11-125992); [Odoo forum: how to create workflow v11](https://www.odoo.com/forum/help-1/workflow-158942).

### Inferences
- Odoo demonstrates that "state machine" can be degraded to a `state` enum + guarded methods + declarative reactions (automation rules on `on_state_set`) — close to ObjectFlow's status types; what Odoo adds declaratively is the *trigger catalogue* (state set to X, date-based, after creation/update, webhook) and *pre/post domain filters*.
- Stored computed fields are Odoo's answer to "derived aggregates kept consistent" — purely dependency-driven, with the known failure mode of recomputation storms; a generated-code environment could make `store=True`+`depends` an explicit, checkable declaration.
- Record rules as domains = MoWare's repositories could accept a declared per-role filter that is ANDed into every mapped query (same idea as iDempiere `addAccessSQL`, but typed).
- `tracking=True` per field is the minimal declarative audit: one flag, one generic value table, optional subtype/template hooks.

- `ir.actions.server` additional states (mail_post, followers, next_activity, sms, webhook) are only in the user-facing Studio docs, not in the developer reference fetched.
- No official statement on the workflow-engine removal was found; only forum threads.
- No authoritative critique of automation rules / server actions found.

## Key question 5: Cross-cutting — document/status lifecycle, cross-document consistency and reversals, derived aggregates, history/change tracking, background jobs, multi-tenancy

### Takeaway
Across the four systems the same six concerns recur, with two main styles: the Compiere family (iDempiere/metasfresh) embeds a fixed lifecycle vocabulary and hook timings in the persistence layer; OFBiz and Odoo externalize transitions and reactions as data/metadata (status tables + ECA rules; state field + automation rules + computed fields). Reversal is modeled as a counter-document (iDempiere) or compensating services (OFBiz), never as deletion.

### Inferences — candidate idea list for ObjectFlow/ManMap
- **[BIG] Document lifecycle type**: a status type variant with named actions (prepare/complete/void/close/reverse/reactivate), per-action hook slots (before/after), result-status contract (`completeIt` returns status), and an "expected status after action" assertion (metasfresh `processEx`). Source vocabulary: iDempiere/metasfresh.
- **[BIG] Declared transition table**: allowed (from, to, transitionName, condition) rows on a status type, checked by generated code (OFBiz `StatusValidChange`), replacing hand-written `getValidActions`-style switches (iDempiere's weak point).
- **[BIG] Reaction rules (ECA)**: declarative "on service/command X at commit, if condition, call Y sync/async(persist)" with `oldValue != newValue` conditions and run-as (OFBiz SECA/EECA; Odoo automation triggers; metasfresh `ifColumnsChanged`, `afterCommit`).
- **[BIG] Period/posting control** as a reusable precondition family keyed by (doc base type, date, org, action-vs-posting) (iDempiere `MPeriod`).
- **[BIG] Declarative read models**: view-entity-style joins/aggregates with functions and group-by (OFBiz) and criteria-column metadata with operators/functions, identifier columns and access-filter injection (iDempiere Info Window) — extensions of ManMap's custom SQL + row mapper.
- **[BIG] Row-level filters per role** ANDed into mapped queries (Odoo `ir.rule`, iDempiere `addAccessSQL`).
- **[BIG] Derived field declaration** with explicit dependency list and optional storage (Odoo `compute/depends/store`), plus checker rules against self-dependency and side effects.
- **[BIG] Background unit of work**: queue of record references + parameters, bound to committing transaction, with retry/skip semantics and tenant context (metasfresh workpackages; OFBiz persisted async; Odoo cron batch protocol with `_commit_progress`).
- **[SMALL] Per-field `tracking` flag** writing a generic old/new value table (Odoo `tracking=True`, iDempiere Maintain Change Log) — a cheap audit extension over ManMap's audit fields.
- **[SMALL] Optimistic-locking column choice** (iDempiere `set_OptimisticLockingColumns`, OFBiz `enable-lock` requiring `lastUpdatedStamp`).
- **[SMALL] Service execution policy** attributes: `use-transaction`, `require-new-transaction`, `transaction-timeout`, `semaphore wait|fail`, `max-retry` (OFBiz).
