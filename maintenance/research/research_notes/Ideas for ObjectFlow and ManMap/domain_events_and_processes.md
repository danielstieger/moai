# Frameworks for domain logic, events and long-running processes (Axon, Eventuate Tram, Temporal, Camunda 8, Spring Modulith, state machines, rules) — inventory for ObjectFlow

Research date: 2026-10-19. Versions seen in the fetched docs: Axon Framework reference 4.11 (deadline pages served as 5.4), Spring Modulith 2.1.1, Spring Statemachine 4.0.2, Stateless4j 2.6.0, XState v5 docs, Camunda 8 (user tasks "introduced in 8.6"), Apache KIE/Drools 10.2.0, Easy Rules 4.1.x (maintenance mode), Temporal docs current (worker versioning noted as replacing a pre-2025 experimental mechanism in March 2026).

Legend used throughout: **[BIG]** = a mechanism that would be a new concept/axis in a DSL like ObjectFlow; **[SMALL]** = an incremental addition to existing concepts (service methods, commands, status types, batch pairs). Each "ObjectFlow note" is my inference, not a sourced claim.

ObjectFlow baseline for comparison (given in assignment, not researched): entities/value objects/DTOs, status types (enum-like, persistence value, ON_CREATION default), stateless services with preconditions (user-correctable) and guards (technical), `validation` blocks, commands as use cases (SEARCH, GRAPH_OWNER with own session/commit, GRAPH_EDIT, modal owner) with pages and conclusions, session operations committed on owner's final OK, successor commands, "session queue next command", batch producer/consumer pairs with exception strategies and cron, roles/scopes/identities, headless test DSL. Missing today: domain events, declarative state machine, outbox, saga/process manager, specifications/rules, scheduling beyond cron.

## Key question 1 — Axon Framework: aggregates with @CommandHandler/@EventSourcingHandler, event publication, sagas with deadlines, projections, snapshotting, upcasting; what is useful without event sourcing?

### Takeaway
Axon's separable, reusable parts are: (a) *command handlers located on the aggregate* that validate and then `apply()` a domain event, (b) *event processors* (subscribing = same thread/transaction, streaming = own thread with persisted tracking token and replay), (c) *sagas* routed by association property with `@StartSaga/@EndSaga`, and (d) *deadlines* scoped to the aggregate/saga that scheduled them. Event sourcing itself (event-sourcing handlers, snapshots, upcasters) is optional: Axon's own "state-stored aggregate" keeps JPA persistence and still publishes events, and is explicitly allowed to put decision and state change in one command handler.

### Cited Findings

**Aggregate declaration (event-sourced)**
- `@AggregateIdentifier` "is the external reference point to into the `GiftCard` Aggregate"; a `@CommandHandler` constructor creates the aggregate; decision logic lives in `@CommandHandler` methods; "The static `AggregateLifecycle#apply(Object…)` is what is used when an Event Message should be published."; "As all the Event Sourcing Handlers combined will form the Aggregate, this is where all the _state changes_ happen."; the identifier "**must** be set in the `@EventSourcingHandler`" of the creation event; a no-arg constructor is required; `isLive()` returns false during replay so side effects can be skipped; `markDeleted()` should be called from an event sourcing handler; "By default, Axon will configure your Aggregate as an 'Event Sourced' Aggregate." — [Axon 4.11: Aggregate](https://docs.axoniq.io/axon-framework-reference/4.11/axon-framework-commands/modeling/aggregate/)
- Minimal shape (condensed from the GiftCard example on that page):
  ```java
  public class GiftCard {
      @AggregateIdentifier private String id;
      @CommandHandler
      public GiftCard(IssueCardCommand cmd) { apply(new CardIssuedEvent(cmd.getCardId(), cmd.getAmount())); }
      @EventSourcingHandler
      public void on(CardIssuedEvent evt) { this.id = evt.getCardId(); }
      protected GiftCard() {}
  }
  ```
  — [Axon 4.11: Aggregate](https://docs.axoniq.io/axon-framework-reference/4.11/axon-framework-commands/modeling/aggregate/)

**State-stored aggregate (no event sourcing, events still published)**
- A state-stored aggregate is a JPA `@Entity` with `@Id @AggregateIdentifier`, child entities as `@AggregateMember`, loaded/saved via `GenericJpaRepository`. The command handler validates, mutates state directly, then calls `apply(...)` which "publishes the given objects as event messages within the aggregate's scope". Verbatim handler:
  ```java
  @CommandHandler
  public void handle(RedeemCardCommand cmd) {
      // ... validation ...
      remainingValue -= cmd.getAmount();
      transactions.add(new GiftCardTransaction(id, cmd.getTransactionId(), cmd.getAmount()));
      apply(new CardRedeemedEvent(id, cmd.getTransactionId(), cmd.getAmount()));
  }
  ```
  State-stored aggregates "can pair the decission making logic and state changes in a Command Handler" with no consequences, because no event sourcing handlers drive state. `@EventHandler` methods on the aggregate/entities run before any external handler. The identifier must be initialized by the first published event at the latest. — [Axon 4.11: State-stored aggregates](https://docs.axoniq.io/axon-framework-reference/4.11/axon-framework-commands/modeling/state-stored-aggregates/)

**Event processors (how events reach handlers)**
- Subscribing processors "subscribe to a source of events and are invoked by the thread managed by the publishing mechanism"; streaming processors "pull their messages from a source using a thread that it manages itself"; "the default processor implementation used by Axon is the Tracking Event Processor". Both "start a unit of work and possibly a transaction"; default `RollbackConfiguration` rolls back on any `Throwable`. Streaming processors on error "go into error mode, releasing any tokens and retrying at an incremental interval (starting at 1 second, up to max 60 seconds)"; subscribing processors "report a publication error to the component that provided the event". Error handling is split into `ListenerInvocationErrorHandler` (per handler group, default logs and continues) and `ErrorHandler` (per processor, default `PropagatingErrorHandler` rethrows); dead-letter queues park problematic events. Handlers within one processor are invoked in registration order; across processors there is no ordering. No explicit delivery guarantee (exactly-once etc.) is stated. — [Axon 4.11: Event processors](https://docs.axoniq.io/axon-framework-reference/4.11/events/event-processors/)

**Sagas**
- `@Saga` class; `@SagaEventHandler(associationProperty = "orderId")` routes events to saga instances by key/value association (a match may hit zero, one or several sagas); `keyName` lets a differently named event property map to the same association key; `@StartSaga` creates a saga if none is associated (`forceNew = true` always creates); `@EndSaga` ends the lifecycle after the handler; `SagaLifecycle.end()` ends conditionally. Resources are `transient` and re-injected after deserialization. Infrastructure: `AnnotatedSagaManager` driven by an event processor (default processor name `<SagaName>Processor`), `AnnotatedSagaRepository` guaranteeing one instance per saga id in the JVM, `SagaStore` implementations `JpaSagaStore`, `JdbcSagaStore`, `MongoSagaStore`, `InMemorySagaStore` (default, not persisted), `CachingSagaStore`; serializers XStream or Jackson. — [Axon 4.11: Implementing sagas](https://docs.axoniq.io/axon-framework-reference/4.11/sagas/implementation/)

**Deadlines**
- A deadline is "a mechanism which enables certain actions to be executed after a certain amount of time", runs in the context of the aggregate or saga that scheduled it, and can be cancelled when obsolete. — [Axon 4.11: Deadlines](https://docs.axoniq.io/axon-framework-reference/4.11/deadlines/)
- API: `String deadlineId = deadlineManager.schedule(Duration.ofMillis(500), "myDeadline");` (also `Instant`, optional payload); `deadlineManager.cancelSchedule("myDeadline", deadlineId)`; `cancelAll(name)` crosses instances; `cancelAllWithinScope(name)` limits to the calling aggregate/saga. Handler: `@DeadlineHandler(deadlineName = "myDeadline") public void on(MyDeadlinePayload p) {...}`; the handler must live in the same aggregate or saga that scheduled it; a saga may put `@EndSaga` on a deadline handler. Implementations: `SimpleDeadlineManager`, `JobRunrDeadlineManager`, `QuartzDeadlineManager`, `DbSchedulerDeadlineManager`. Limitations: JobRunr non-Pro can only find deadlines by id, so `cancelAll*` is not implemented; db-scheduler must deserialize all tasks to implement `cancelAll`. "Unlike Event Scheduling, when a deadline is triggered there will be no storing of the published message." — [Axon: Deadline managers](https://docs.axoniq.io/axon-framework-reference/4.11/deadlines/deadline-managers/)
- Event schedulers (the alternative): publish a real event at a later time, return a `ScheduleToken` for cancellation. `SimpleEventScheduler` is in-memory ("schedules are lost when the JVM shuts down", "unsuitable for long-term schedules"); JobRunr: publication "might be a little late, but it will be published"; db-scheduler needs one table and joins the current transaction when a `TransactionManager` is set; Quartz offers persistence, clustering and misfire management but "has seen little recent activity"; Axon Server variant requires Axon Server. Scheduled events are published on scheduler-managed threads, so a `TransactionManager`/`UnitOfWorkFactory` must be configured for transactional listeners. — [Axon 4.11: Event schedulers](https://docs.axoniq.io/axon-framework-reference/4.11/deadlines/event-schedulers/)

**Snapshotting**
- A snapshot "summarises an arbitrary amount of events into a single one"; `EventCountSnapshotTriggerDefinition(snapshotter, 500)` triggers when more than N events are needed to load; `@Aggregate(snapshotTriggerDefinition = "giftCardSnapshotTrigger")`; `AggregateSnapshotter` stores the actual aggregate instance; the snapshotter should run on a separate thread (default thread is "generally not recommended for production"); `@Revision("1")` on the aggregate installs a `RevisionSnapshotFilter` to ignore outdated snapshots; events covered by a snapshot are normally never read again and may be archived. — [Axon 4.11: Event snapshots](https://docs.axoniq.io/axon-framework-reference/4.11/tuning/event-snapshots/)

**Upcasting / event versioning**
- "Since the Event Store is considered a read and append-only data source, your application must be able to read all events, regardless of when they were added."; each event carries a revision from a `RevisionResolver` (e.g. `@Revision` annotation); `SingleEventUpcaster` implements `canUpcast`/`doUpcast` (example: revision "1.0" to "2.0" of `ComplaintEvent` adding a default `description`); also `EventMultiUpcaster`, context-aware variants, `EventTypeUpcaster`; "it is paramount to maintain the ordering of the upcasters"; upcasters cannot be automated because "the structure of the new event is unknown to the old event"; identifiers and timestamps cannot be changed. — [Axon 4.11: Event versioning](https://docs.axoniq.io/axon-framework-reference/4.11/events/event-versioning/)

**Query side / projections**
- A projection is a plain class with `@QueryHandler` methods (payload first parameter, return type is the response) and event handlers that update its storage:
  ```java
  public class CardSummaryProjection {
      private Map<String, CardSummary> cardSummaryStorage;
      @QueryHandler
      public CardSummary handle(FetchCardSummaryQuery query) { return cardSummaryStorage.get(query.getCardSummaryId()); }
      // omitted CardSummary event handlers which update the model
  }
  ```
  At most one handler per query-handling instance is invoked (most specific match); response types via `ResponseTypes.instanceOf/multipleInstancesOf`; "Each projection processes events at their own pace, so two projections might not have the data in sync." — build independent projections rather than chaining queries. — [Axon 4.11: Query handlers](https://docs.axoniq.io/axon-framework-reference/4.11/queries/query-handlers/)

**Event sourcing cost/criticism**
- Oskar Dudycz (event-driven.io, 2021-06-23), "When not to use Event Sourcing?": simple CRUD — "I agree that Event Sourcing will not suit such systems" and "a well-done CRUD is much better than a poorly done Event Sourcing"; supportive data-bag modules; configuration/dictionary services where "The amount of repetitive, boilerplate code was enormous" (replication may suffice); teams whose current process works; lack of team experience — "Technologies and patterns also need to be matched to the capabilities of the team we have"; lack of domain knowledge early — "We usually make the most important decisions when we are the dumbest: at the beginning of a project"; "It's easy to fall into accidental complexity"; and "It's not an all-or-nothing decision" — adopt per module (e.g. core business module only). He presents reporting and integration as benefits, not drawbacks. — [Dudycz: When not to use Event Sourcing](https://event-driven.io/en/when_not_to_use_event_sourcing/)
- Hossam Fares (HackerNoon, 17 Nov 2020): "Having event sourcing is more complex to manage and store compared to not using it."; "the misusage cost tech teams time and frustration."; "only use it when you really need it"; CQRS and ES need not be coupled; poor fits named: shopping carts, drafts/quotations, product/service data, form data; good fits: state machines with tracked transitions (order operations, shipment tracking), financial events/workflows, activity tracking. — [HackerNoon: Event Sourcing — It's Easy If You Do It Smart](https://hackernoon.com/event-sourcing-its-easy-if-you-do-it-smart-72d3w02)
- Search-level consensus (not individually verified): poor fits are "simple CRUD applications, domains without audit requirements, and teams without event-driven experience"; "if events are just CRUD verbs, you have audit logging rather than event sourcing"; counterpoint by Oskar Dudycz that ES also suits smaller systems. — [search aggregate: c-sharpcorner](https://www.c-sharpcorner.com/article/event-sourcing-in-net-when-to-use-it-and-when-to-avoid-it/), [themainthread](https://themainthread.beehiiv.com/p/event-sourcing-when-why-and-how-and-when-not-to), [Dudycz (could not be fetched)](https://event-driven.io/en/when_not_to_use_event_sourcing/)

### Inferences (ObjectFlow notes)
- **[BIG] Domain events as a language element.** Axon's state-stored aggregate is the exact shape ObjectFlow already has (entities persisted as state, service methods as command handlers). The missing piece is a declared `event` type plus an `emit`/`apply` statement inside service methods, and declared handlers. Axon shows the two dispatch modes a DSL would need to name: *in-session/same-transaction* (subscribing processor; natural fit for ObjectFlow's session operations committed on owner OK) and *after-commit/asynchronous with persisted position and replay* (streaming processor). The DSL value: the session already knows the transaction boundary, so "emit on commit" can be a guaranteed semantic rather than a convention.
- **[SMALL] Handler ordering and error policy as declarations.** Axon separates "handler failed" (log and continue vs propagate) from "processor failed" (retry with backoff, dead-letter). ObjectFlow's batch "exception strategies" are the same idea; they could be reused for event handlers.
- **[BIG] Saga = long-lived correlation object.** The key Axon idea for a DSL is not the saga class but *routing by association property* and *start/end markers*: a declarative "process type keyed by orderId, started by X, ended by Y, reacting to events A, B" is expressible in a DSL and persists like an entity. ObjectFlow's "queue next command" is one-hop; a saga is a persisted multi-hop reaction with explicit lifecycle.
- **[BIG] Deadlines scoped to an instance.** `schedule(duration, name, payload)` + `@DeadlineHandler` in the same aggregate/saga, cancellable by id or by scope, is a compact model for "if not approved within 14 days, escalate". ObjectFlow has cron on batch pairs only; a per-instance deadline is a different concept (time as an event source). Axon's distinction "deadline (not stored as event) vs scheduled event (stored, published)" is worth keeping.
- **[SMALL] Snapshotting and upcasting are only relevant if events become the source of truth.** Without event sourcing the DSL needs neither; but *event versioning* (`@Revision` + upcaster) becomes relevant as soon as events are persisted in an outbox or handled by a replayable streaming processor, because old serialized events will be read by new code.
- **[SMALL] `isLive()`** is a reminder that if ObjectFlow ever replays, side-effecting handlers need a "not during replay" guard.
- Criticism synthesis: the consistent advice is to adopt domain events (and possibly an outbox) without adopting event sourcing unless audit/history is itself a requirement. For a business-application DSL whose entities are already state-stored, "events as notifications, state as truth" is the lower-risk path.

## Key question 2 — Eventuate Tram: transactional outbox and CDC, saga orchestration DSL (steps, compensations, semantic lock)

### Takeaway
Eventuate Tram makes "write business state and the outgoing message in one local transaction, let a relay publish it" a library concern (MESSAGE table + CDC service, tailing or polling), and offers a fluent saga definition (`step().invokeParticipant(...).withCompensation(...)`) where compensations run in reverse order on failure. The isolation countermeasures (semantic lock, pivot/retriable classification) are *design rules* documented by Richardson and Microsoft, not DSL constructs in Eventuate.

### Cited Findings

**Transactional outbox pattern (the pattern)**
- Problem: "How to atomically update the database and send messages to a message broker?"; "2PC is not an option"; solution: store outgoing messages in the DB in the same transaction, a *message relay* publishes them; relay variants: transaction log tailing and polling publisher. Benefits: no 2PC, "Messages are guaranteed to be sent if and only if the database transaction commits", ordering preserved. Drawback: "Potentially error prone since the developer might forget to publish the message/event after updating the database." Duplicates are possible (relay crashes after publish, before marking), so consumers must be idempotent, e.g. by tracking processed message ids. — [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)

**Eventuate Tram implementation**
- Eventuate Tram lets services "send and receive messages as part of an database transaction" by implementing the transactional outbox; messages go to a `MESSAGE` table; the CDC service "reads messages inserted into the `MESSAGE` table" and publishes to a broker "such as Apache Kafka", using either "Transaction log tailing" or "Polling". Three styles: messaging over named channels; publish/consume domain events; command messages with reply. — [Eventuate Tram: About](https://eventuate.io/docs/manual/eventuate-tram/latest/about-eventuate-tram.html)
- Eventuate Tram "enables an application to atomically update a database and publish a message without using JTA"; the CDC service is a Spring Boot application; the example compose file is `docker-compose-mysql-binlog.yml` (implying binlog tailing for MySQL). — [Eventuate Tram Sagas: Getting started](https://eventuate.io/docs/manual/eventuate-tram/latest/getting-started-eventuate-tram-sagas.html)

**Saga orchestration DSL**
- "A saga consists of a series of a local transactions."; orchestration: "a centralized orchestrator uses request/asynchronous reply-style messaging to tell the participants what to do." Verbatim definition:
  ```java
  private SagaDefinition<CreateOrderSagaData> sagaDefinition =
          step()
            .withCompensation(this::reject)
          .step()
            .invokeParticipant(this::reserveCredit)
          .step()
            .invokeParticipant(this::approve)
          .build();
  ```
  with `return send(new ReserveCreditCommand(customerId, orderId, orderTotal)).to("customerService").build();` as the participant invocation, and `SagaCommandHandlersBuilder.fromChannel("customerService").onMessage(ReserveCreditCommand.class, this::reserveCredit)` on the participant side. The saga is created inside the `@Transactional` service method after saving the order (`createOrderSagaManager.create(data, Order.class, order.getId())`). — [Eventuate Tram Sagas: Getting started](https://eventuate.io/docs/manual/eventuate-tram/latest/getting-started-eventuate-tram-sagas.html)
- The orchestrator "executes the forward transactions sequentially" and on failure runs compensating transactions in reverse order; "Each transaction is the invocation of a saga participant using a command message." — [eventuate-tram-sagas README](https://github.com/eventuate-tram/eventuate-tram-sagas)

**Saga semantics, pivot/retriable, countermeasures**
- Saga: "a reliably coordinated sequence of local transactions"; "a developer must design compensating transactions" (no automatic rollback); lack of isolation needs countermeasures; the client needs a way to learn the outcome (delayed response, polling, notification). — [microservices.io: Saga](https://microservices.io/patterns/data/saga.html)
- Compensable transactions "can be undone or compensated for by other transactions with the opposite effect"; pivot transactions "serve as the point of no return in the saga. After a pivot transaction succeeds, compensable transactions are no longer relevant."; "Retryable transactions follow the pivot transaction. Retryable transactions are idempotent". Anomalies: lost updates, dirty reads, fuzzy/nonrepeatable reads. Countermeasures: semantic lock ("application-level locks when a saga's compensable transaction uses a semaphore to indicate that an update is in progress"), commutative updates, pessimistic view ("Reorder the sequence of the saga so that data updates occur in retryable transactions to eliminate dirty reads"), reread values, version files, risk-based concurrency by value. Considerations: "Compensating transactions might not always succeed, which can leave the system in an inconsistent state."; debugging complexity grows with participants; idempotence is required. Orchestration pros: better for complex workflows, avoids cyclic dependencies, clear separation; cons: coordination logic, single point of failure. — [Microsoft Azure Architecture Center: Saga](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)
- Richardson's semantic lock: "Compensatable transaction sets flag, retriable transaction releases it. Indicates a possible dirty read. Flag = lock: prevents other transactions from accessing it. Require deadlock detection, e.g. timeout. Flag = warning - treat the data differently, e.g. Order.state = PENDING" — [Richardson slides (via search snippet)](https://www.slideshare.net/chris.e.richardson/microxchg-managing-data-consistency-in-a-microservice-architecture-using-sagas)

### Inferences (ObjectFlow notes)
- **[BIG] Outbox as a built-in commit semantic.** ObjectFlow already owns the transaction (session operations committed on owner OK). A DSL-level `publish` inside that session can be implemented as outbox-by-construction: the generator writes the event row in the same transaction, a relay (batch consumer or CDC) publishes afterwards. This removes the pattern's stated drawback ("developer might forget") because the DSL, not the developer, inserts the row. Consequence to surface in the DSL: at-least-once delivery, so consumers must be idempotent (see Q8).
- **[BIG] Saga steps as a list with compensation per step.** The Eventuate DSL is small enough to transcribe into a DSL: ordered steps, each either a local action or a participant command, each optionally with a compensation; failure runs compensations in reverse. The *pivot/retriable* classification is a validation rule a DSL could check: steps after the pivot must not declare compensations and must be idempotent/retried.
- **[SMALL] Semantic lock maps onto ObjectFlow status types.** Richardson's "Flag = warning, e.g. Order.state = PENDING" is literally a status value. A DSL could mark a status as `pending` (semantic lock) so that other commands' preconditions can be generated ("not while PENDING").
- **[SMALL] Saga outcome delivery** (polling/notification to the UI) corresponds to what "successor command" and "queue next command" do today; a saga would need a place to attach a user-visible conclusion once completed.

### Gaps
- Eventuate docs fetched did not describe `invokeLocal`, `onReply`, the saga_instance persistence table, or the consumer-side duplicate detection table; those are known from the codebase but not confirmed from fetched pages.
- Richardson's countermeasure definitions were available only through a slide-deck search snippet; the microservices.io page defers them to his book (Chapter 4.3).

## Key question 3 — Temporal: durable workflows as code, activities, signals/queries/updates, timers, retries, versioning, child workflows; what a "durable command chain" could learn

### Takeaway
Temporal's model is: workflow code is deterministic and replayed from a persisted Event History; everything non-deterministic (I/O) is an Activity with its own retry policy and timeouts; timers are persisted and cost nothing while waiting; external interaction is typed as Signal (async write), Query (read, no history), Update (sync validated write); code evolution needs patching or worker versioning; history has hard limits (51,200 events / 50 MB) forcing continue-as-new. A DSL that already knows its steps (commands, pages, conclusions) can get most of this by *persisting the chain's position* instead of replaying code.

### Cited Findings

**Workflows and determinism**
- "A **Workflow Definition** is the code that defines your Workflow."; workflows "can run—and keep running—for years, even if the underlying infrastructure fails."; Event History "is the source of truth for everything that happens in the Workflow."; on resume, code restarts and replays the history (no memory snapshot); code must not depend on current time, random numbers, or direct network calls; "When a Workflow calls an Activity, the Activity runs once, its result is recorded in the Event History." — [Temporal: Workflows](https://docs.temporal.io/workflows)
- Deterministic constraints: code "makes the same Workflow API calls in the same sequence, given the same input." Safe to change: inputs/return values/timeouts of children and activities, timer durations, signal inputs; not safe: types/IDs of child workflows or activities; command-producing calls (timers, activities, child workflows, signals/cancellations, Nexus ops, patched/GetVersion, search attribute upserts, side effects) must not be reordered/added/removed without versioning. Versioning: patching (`Patched`/`GetVersion`) or Worker Versioning — "This is the recommended way to handle versioning"; the experimental pre-2025 mechanism is removed from Temporal Server in March 2026. Timer gotcha: changing a duration to/from 0 is non-deterministic in Java/Python/Go. — [Temporal: Workflow definition](https://docs.temporal.io/workflow-definition)

**Activities and retries**
- "An Activity is a normal function or method"; retries restart from scratch unless Heartbeat details save progress; "We recommend that it be idempotent, so retries can be processed without duplicate side effects."; Local Activities run in the worker process, skipping the task queue, "not a replacement for regular Activities". — [Temporal: Activities](https://docs.temporal.io/activities)
- Default retry policy: initial interval 1 s, backoff coefficient 2.0, maximum interval 100× initial, maximum attempts unlimited ("Setting the value to 0 also means unlimited"), no non-retryable errors by default; "Temporal's default behavior is to automatically retry an Activity that fails."; "Unlike Activities, Workflow Executions do not retry by default."; "Retry Policies do not apply to Workflow Task Executions."; non-retryable errors matched by Application Failure `type`, "Use non-retryable errors in your code sparingly" (bad input data is a good candidate); Schedule-To-Close Timeout bounds total retry duration. — [Temporal: Retry policies](https://docs.temporal.io/encyclopedia/retry-policies)

**Messages into a running workflow**
- "Signals are asynchronous write requests." (no response, sender cannot await an error, independent of worker availability); "Queries are read requests." (cannot block, never add history entries, work on completed workflows); "Updates are synchronous, tracked write requests." (sender waits for result or error; can validate before acceptance so invalid requests never enter history; accepted updates are recorded). For async read/write: "send a Signal and poll with a Query". — [Temporal: Workflow message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing)

**Timers**
- "Timers in Temporal are persisted"; "Workers consume no additional resources while waiting for a Timer to fire"; durations from one second to "several years"; "your Workflows should not rely on sub-second accuracy for Timers"; "consider the duration as a minimum time". Start Delay delays only the initial run; Signal-With-Start/Update-With-Start end the delay early; Start Delay "is incompatible with both Schedules and Cron Jobs". — [Temporal: Timers and delays](https://docs.temporal.io/workflow-execution/timers-delays)

**Child workflows**
- "A Child Workflow Execution is a Workflow Execution that is spawned from within another Workflow in the same Namespace."; parent close policy propagates cancellation/termination; with `ABANDON` a child "can continue on if its Parent is canceled"; child vs activity: child has workflow APIs but determinism constraints; activity has neither; "When in doubt, use an Activity."; children get their own history, but their events also land in the parent's, so "a single Parent should not spawn more than 1,000 Child Workflow Executions"; children do not carry over on parent Continue-As-New. — [Temporal: Child workflows](https://docs.temporal.io/child-workflows)

**Limits**
- Event History hard limit 51,200 events or 50 MB; warning at 10,240 events or 10 MB; defaults of 2,000 pending activities / child workflows / signals / cancel requests per execution (workflow task fails and retries when hit); 30 incomplete Nexus operations by default. — [Temporal: Limits](https://docs.temporal.io/workflow-execution/limits)

**Continue-As-New and Schedules**
- "Continue-As-New allows you to checkpoint your Workflow's state and start a fresh Workflow."; "The new Workflow Execution has the same Workflow Id, but a different Run Id, and starts its own Event History."; reasons: history growth and versioning (an old run on new code); "Temporal will tell your Workflow when it's approaching performance or scalability problems" via the "Continue-As-New Suggested" flag; "You can repeat Continue-As-New as often as needed, which means that your Workflow can run forever" (Entity Workflows). — [Temporal: Continue-As-New](https://docs.temporal.io/workflow-execution/continue-as-new)
- "A Schedule contains instructions for starting a Workflow Execution at specific times."; "A Schedule has an identity and is independent of a Workflow Execution." (unlike a Cron Job, which is a property of the execution); spec = intervals or calendar expressions (cron strings or JSON fields), phase offset, start/end bounds, exclusions, jitter, time zones; overlap policies `Skip` (default), `BufferOne`, `BufferAll`, `CancelOther`, `TerminateOther`, `AllowAll`; "The Catchup Window controls how late an automated Action can be taken." (default one year, minimum ten seconds); pause, backfill, pause-on-failure, action limit, last completion result/last failure readable by the next run; Schedules are implemented as workflows internally and listings are eventually consistent. — [Temporal: Schedules](https://docs.temporal.io/schedule)

**Workflow id as idempotency handle**
- "Temporal guarantees that there can be at most one Workflow Execution with a given ID running at any point in time."; Reuse Policy (closed runs): Allow Duplicate (default), Allow Duplicate Failed Only (can "guarantee that the Completed Workflow Execution will not be re-executed"), Reject Duplicate, Terminate if Running; Conflict Policy (open runs): Fail (default, "Workflow execution already started"), Use Existing (success response with the open run id), Terminate Existing. — [Temporal: Workflow Id / Run Id](https://docs.temporal.io/workflow-execution/workflowid-runid)

### Inferences (ObjectFlow notes)
- **[BIG] Durable process position instead of durable code replay.** Temporal pays for "arbitrary code is durable" with determinism rules, history limits and versioning ceremony. A DSL with explicit steps (commands, batch pairs, successor commands) can store *the step index and typed process data* and avoid replay altogether — this is what BPMN engines and Eventuate sagas do. The lesson to take is the *vocabulary*: step, retry policy per step, timeout per step, compensation per step, and a process instance id.
- **[BIG] Typed interaction channels with a process instance.** Signal/Query/Update is a clean three-way split that ObjectFlow lacks for anything longer than a session: fire-and-forget input, read-only state, synchronous validated input. ObjectFlow's command preconditions correspond to Update *validators* (reject before anything is recorded).
- **[SMALL] Retry policy and timeout as declarations on a step** (initial interval, backoff, max attempts, non-retryable problem types, overall deadline). ObjectFlow's batch exception strategies are the nearest existing concept; Temporal's distinction "retry activities, not whole workflows" suggests retries belong on service-method/consumer steps, not on commands.
- **[SMALL] Process id reuse/conflict policy** is a crisp language-level specification of idempotent start ("start process for order 4711; if one is running, use existing").
- **[SMALL] Persisted timers** are the same need as Axon deadlines (Q1): "wait N days then continue" as a step, surviving restarts.
- **[SMALL] Schedules as first-class objects.** Temporal's move from "cron as a property of the workflow" to "schedule with identity, overlap policy, catch-up window, pause/backfill" is directly applicable to ObjectFlow's cron on batch pairs: the overlap policy (skip / buffer / allow) and catch-up window are exactly the decisions a batch job needs declared instead of implied.
- **[SMALL] Entity workflows (continue-as-new forever)** are Temporal's way of modelling a long-lived business object as a process; for ObjectFlow the entity with a status machine already plays that role, which is an argument for keeping process state on entities rather than in a separate process engine where possible.
- Versioning lesson: any persisted process instance outlives the code that created it. Even a position-based DSL process must define what happens to running instances when a step is inserted/removed (Camunda does it by versioned deployments; Temporal by patches/worker versions).

## Key question 4 — Camunda 8 (Zeebe): BPMN-driven processes, user tasks, DMN decision tables, external task (job worker) pattern; strengths/weaknesses vs code-first

### Takeaway
Camunda 8 persists process state as a BPMN 2.0 model executed by Zeebe; integration is pull-based job workers with at-least-once delivery and retries; user tasks carry assignee/candidates/due dates/forms/listeners declaratively; business rule tasks call DMN decisions with version binding; DMN hit policies define multi-match semantics precisely. Its strength is the shared, versioned, visual model; the cost is a second artefact (XML) that developers must keep in sync with code, which code-first engines avoid.

### Cited Findings

**Processes and BPMN**
- A process is a "defined sequence of distinct steps or tasks representing your business logic"; "Camunda uses Business Process Model and Notation (BPMN) 2.0 to represent processes."; Zeebe creates a job when execution reaches a task, a job worker completes it, "the job could be retried until it's successfully completed."; "Variables are key-value pairs and part of the process instance."; "The visual nature of BPMN enables greater collaboration between different teams". — [Camunda 8: Processes](https://docs.camunda.io/docs/components/concepts/processes/)

**Job workers (external task pattern)**
- "Job workers request jobs of a certain type on a regular interval (i.e. polling)."; "Zeebe ensures each job is sent to only one of the workers."; on fail the worker sets remaining retries; with none left "the job is not retried until the incident is resolved"; retry back-off supported; activation timeout reassigns the job without consuming a retry and can be extended with `UpdateJobTimeout`; delivery is at-least-once, so the same job may run twice, possibly concurrently; a second completion is rejected with `NOT FOUND`; backpressure via gRPC/HTTP2 flow control, "The gateway only sends as much data as the client can consume over a specific connection." — [Camunda 8: Job workers](https://docs.camunda.io/docs/components/concepts/job-workers/)

**User tasks**
- `zeebe:AssignmentDefinition` with `assignee`, `candidateUsers`, `candidateGroups` (static or FEEL); `zeebe:taskSchedule` with `dueDate`/`followUpDate` (ISO 8601 with timezone); `zeebe:priorityDefinition` 0–100 default 50; forms via `formId` with `bindingType` latest/deployment/versionTag or `externalReference`; task listeners for creating, assigning, updating, completing, canceling (retries default 3); "The process instance stops at this point and waits until the user task instance is completed."; Camunda user tasks (since 8.6) are recommended; "The job worker implementation for user tasks is deprecated." — [Camunda 8: User tasks](https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/)

**Business rule tasks and DMN**
- A business rule task "must define the DMN decision id of the called decision as `decisionId`" (static or FEEL); `bindingType` `latest` (default), `deployment` ("The version that was deployed together with the currently running version of the process"), `versionTag`; `resultVariable` required; "If the decision evaluation is unsuccessful, an incident is raised at the business rule task."; "When the incident is resolved, the decision is evaluated again." Alternatively a job worker implements the task like a service task. — [Camunda 8: Business rule tasks](https://docs.camunda.io/docs/components/modeler/bpmn/business-rule-tasks/)
- DMN: "Decisions are modeled and executed using a language both business analysts and developers can understand."; a BKM "is a reusable function containing a piece of decision logic"; "Currently, you can only reuse BKMs within the same decision."; FEEL is the expression language. — [Camunda 8: DMN](https://docs.camunda.io/docs/components/modeler/dmn/)
- Hit policies: Unique (default) — "Only a single rule can be satisfied or no rule at all", several matches make the table invalid; Any — "all satisfied rules must generate the same output"; First — "contains only the output of the first satisfied rule"; Rule order — "output of all satisfied rules in the order of the rules in the decision table"; Collect — "output of all satisfied rules in an arbitrary order as a list", with SUM/MIN/MAX/COUNT aggregators (single output only). — [Camunda 8: Decision table hit policy](https://docs.camunda.io/docs/components/modeler/dmn/decision-table-hit-policy/)

**BPMN vs code-first (secondary sources, treat as directional)**
- "Camunda models workflows as visual BPMN diagrams executed by the Zeebe engine; Temporal models workflows as ordinary application code with deterministic replay."; "Pick Camunda 8 when business analysts need to read, audit, or change the workflow itself; pick Temporal when the workflow is application logic written by engineers who want durability without a modeling tool in the middle."; licensing: Camunda Source Available vs Temporal MIT (self-hosted). — [automationatlas comparison (vendor-adjacent)](https://automationatlas.io/guides/camunda-vs-temporal-2026-comparison/)
- Temporal's "code-first approach is less accessible to non-developers" — [Kestra (vendor)](https://kestra.io/resources/infrastructure/camunda-alternatives)
- Code-first critique of BPMN tools: "traditional BPMN tools store the process as an XML file that a graphical designer generates, and that XML is the source of truth" — [Viewflow (vendor)](https://docs.viewflow.io/articles/python_native_bpmn.html); "designing workflows directly in a programming language seems more effective for expressing complex scenarios, loops, and agentic decisions", while long-running processes "must 'survive' server restarts and new code deployments" — [GFT blog](https://www.gft.com/pl/pl/blog/rethinking-process-engines-in-the-age-of-ai)

### Inferences (ObjectFlow notes)
- **[BIG] A process type with persisted instance, variables, versioned deployment, and wait states.** Camunda's core runtime concepts (process instance, variables, job, incident, timer/message event, user task as wait state) are exactly the set a "command chain across transactions" needs. MPS already gives ObjectFlow a projectional, graphical-capable model, so the main BPMN selling point (shared visual model, analysts can read it) can be had *without* a second XML artefact: the DSL is the model. This is the strongest single argument for a process concept inside ObjectFlow rather than next to it.
- **[BIG] User task as declarative wait state with assignment.** ObjectFlow commands are already user interactions with roles/scopes; a user task adds *assignee/candidate group/due date/priority/listeners* and the notion "process waits here". Mapping: process step `userTask` → an ObjectFlow command that is offered to a role and whose conclusion resumes the process.
- **[SMALL] Incident as a first-class state.** "Retries exhausted → incident; resolve → re-evaluate" is a cleaner model than silent failure; ObjectFlow's batch exception strategies could gain an `incident` outcome visible to operators.
- **[SMALL] Version binding (latest / deployment / versionTag)** for decisions and forms is a precise answer to "which version of a rule does a running process use"; the same question arises if ObjectFlow gets rule objects or specifications.
- **[SMALL] DMN hit policies** give exact names for the multiple-match semantics of a rule table; see Q7.
- Weakness to avoid copying: at-least-once job delivery and "same job may run concurrently" push idempotency onto every worker; a DSL can at least generate the dedup check (Q8).

- Did not fetch BPMN timer/message event or incident concept pages; statements about them come from the job-worker and business-rule pages.

## Key question 5 — Spring Modulith: module boundaries verified by tests, application events with publication registry (outbox-like), documentation from module structure

### Takeaway
Spring Modulith adds three things to a monolith: package-based modules whose API/internal split and dependency graph are *verified by a unit test*; a `@ApplicationModuleListener` style (async, own transaction, after commit) backed by an *event publication registry* written in the business transaction with completion tracking, statuses, staleness detection and resubmission; and a `Documenter` producing C4/UML diagrams and per-module canvases (beans, aggregates, events published/listened, properties). Its own docs say the native externalization "lacks critical features developers might expect from actual outbox pattern implementations".

### Cited Findings

**Modules and verification**
- A module has a *provided interface* ("An API exposed to other modules implemented by Spring bean instances and application events published by the module"), internals, and a *required interface*; "By default, each direct sub-package of the main package is considered an _application module package_."; sub-packages such as `order.internal` are internal and "Code within those must not be referred to from other modules."; `@ApplicationModule(allowedDependencies = "order")`, `"order :: spi"` for named interfaces, `@NamedInterface("spi")` on a package; `@ApplicationModule(type = Type.OPEN)` for legacy code. — [Spring Modulith: Fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html)
- `ApplicationModules.of(Application.class).verify();` checks: "The dependencies between modules have to form a directed acyclic graph."; "All references to types that reside in application module internal packages are rejected."; explicitly allowed dependencies if declared; jMolecules ArchUnit DDD/architecture rules run automatically if on the classpath; `detectViolations().filter(...).throwIfPresent()`; `VerificationOptions.defaults().withAdditionalVerifications(JMoleculesArchitectureRules.ensureHexagonal(VerificationDepth.STRICT))`. — [Spring Modulith: Verification](https://docs.spring.io/spring-modulith/reference/verification.html)

**Events and the publication registry**
- "To keep application modules as decoupled as possible from each other, their primary means of interaction should be event publication and consumption."; synchronous publication keeps one transaction, "for the bad as more triggered related functionality will widen the transaction boundary and potentially cause the entire transaction to fail"; async after-commit without a registry: "if the listener fails for whatever reason, the event publication is lost ... the system might fail before the method is even invoked." `@ApplicationModuleListener` = `@Async @Transactional(REQUIRES_NEW) @TransactionalEventListener`. Registry: "On event publication, it finds out about the transactional event listeners that will get the event delivered and writes entries for each of them ... into an event publication log as part of the original business transaction."; the listener aspect marks the entry completed on success, leaves it on failure "so that retry mechanisms can be deployed"; `spring.modulith.events.republish-outstanding-events-on-restart`. Statuses since 2.0: PUBLISHED, PROCESSING, COMPLETED, FAILED, RESUBMITTED; completion attempts "Incremented when moving to `PROCESSING`, so a crash during the listener still leaves the attempt count updated."; Staleness Monitor marks hung publications FAILED but is off by default; `FailedEventPublications.resubmit(ResubmissionOptions)` with batch size, max in-flight, min age, filters. Completion modes UPDATE (default, must purge), DELETE, ARCHIVE. Stores: JPA, JDBC, MongoDB (replica set), Neo4j. Externalization: `@Externalized("customer-created::#{#this.getLastname()}")` to Kafka/AMQP/JMS/Spring Messaging; `serialize-externalization=true` to avoid reordering on resubmission; the native approach "lacks critical features developers might expect from actual outbox pattern implementations", with `externalization.mode=outbox` delegating to Namastack or JobRunr. Testing: `AssertablePublishedEvents` in `@ApplicationModuleTest`. — [Spring Modulith: Events](https://docs.spring.io/spring-modulith/reference/events.html)

**Documentation generation**
- `new Documenter(modules).writeModulesAsPlantUml().writeIndividualModulesAsPlantUml();` (C4 default, `DiagramStyle.UML` option); `writeModuleCanvases()` produces per-module canvas with base package, Spring components by stereotype, aggregate roots (entities with repositories or jMolecules aggregates), published events (jMolecules `@DomainEvent`, plus the methods that create them), events listened to (`@EventListener`, `@TransactionalEventListener`, `@DomainEventHandler`), configuration properties; `writeAggregatingDocument()` collects everything into one Asciidoc. — [Spring Modulith: Documentation](https://docs.spring.io/spring-modulith/reference/documentation.html)

### Inferences (ObjectFlow notes)
- **[SMALL, but high leverage] Module boundaries as DSL-level constraints.** ObjectFlow already has structural knowledge MPS can check at edit time; Modulith shows the three checks worth having: acyclic module graph, API vs internal visibility, explicit allowed dependencies. In a projectional DSL these become type-system errors rather than a test.
- **[BIG] Event publication registry = the minimal viable "outbox" for an in-process monolith.** The pattern "write a log entry per listener in the business transaction, mark complete after the listener succeeds, resubmit incomplete ones" needs no broker and fits ObjectFlow's session commit. Statuses and completion attempts are a ready-made state model for "handler execution". The documented caveats (purging, staleness off by default, ordering on resubmission) are the design decisions a DSL would have to make explicit.
- **[SMALL] Event-driven module canvas from the model.** ObjectFlow can generate an equivalent canvas (entities, commands, services, events published/consumed per module) directly from the model; Modulith shows which facts stakeholders find useful.
- **[SMALL] `AssertablePublishedEvents`** maps directly onto ObjectFlow's headless test DSL: "running command X publishes event E with orderId = …".
- Design note: Modulith's own admission that in-process registry is not a full outbox marks the boundary between "reliable in-process handlers" (registry) and "reliable integration messaging" (outbox + relay, Q2).

## Key question 6 — State machines: Spring Statemachine, Stateless4j, XState concepts; declared transitions vs "one service method per transition"

### Takeaway
All three libraries declare transitions as data: (source state, trigger/event, guard, action, target), with entry/exit actions per state and hierarchical states; Spring Statemachine adds regions, choice/junction/fork/join, history, deferred events and persistence; XState adds eventless and delayed transitions, guarded transition arrays with a default, composable guards (`and/or/not`), parallel states and `reenter`. Compared with one service method per transition, a declared machine makes the set of legal transitions, the guard per transition, and the entry/exit behaviour per state *enumerable* (for UI, documentation, test generation, DOT export) and *checkable* (unreachable states, missing default).

### Cited Findings

**Spring Statemachine 4.0.2**
- Configured via `@EnableStateMachine` + `EnumStateMachineConfigurerAdapter`; states: `withStates().initial(...).end(...).states(...)`; hierarchical: a second `withStates()` block with `.parent(...)`; regions: multiple child blocks with own `initial()`, named with `region("R1")` so persistence/reset have stable ids; transitions: `withExternal()`, `withInternal()`, `withLocal()` each with `.source().target().event()` plus `.guard()`, `.guardExpression()` (SpEL), `.action(action, errorAction)`; guards: `Guard<S,E>.evaluate(StateContext)`; actions on transitions or states (`stateEntry`, `stateDo`, `stateExit`); pseudo-states: `withChoice().source(S1).first(S2, guard).then(S3, guard).last(S4)` (a `last` branch is required), junction, `withFork()`, `withJoin()`, entry/exit points, `history(SH, History.SHALLOW|DEEP)`; `withConfiguration()` for `autoStartup`, `machineId`, `transitionConflictPolicy`, `regionExecutionPolicy`; `withPersistence()` / `StateMachineRuntimePersister`; a builder (`StateMachineBuilder.builder()`) for dynamic string-based machines. Verbatim transitions example:
  ```java
  transitions
      .withExternal().source(States.S1).target(States.S2).event(Events.E1).and()
      .withInternal().source(States.S2).event(Events.E2).and()
      .withLocal().source(States.S2).target(States.S3).event(Events.E3);
  ```
  Timers as triggers: `.withInternal().source("S2").action(timerAction()).timer(1000)` fires continuously while in the state; `.timerOnce(1000)` fires once after entry — "Use `timerOnce()` if you want something to happen after a delay exactly once when state is entered." Deferred events: a state can declare deferrable triggers so events are processed "at a more appropriate time". Persistence: a machine "cannot be persisted with normal Java serialization"; `StateMachineContext` "is a runtime representation of a state machine that you can use to restore an existing machine"; `StateMachinePersister` offers `persist`/`restore` over a `StateMachinePersist<S,E,T>` with `write(context, contextObj)`/`read(contextObj)`; `StateMachineRuntimePersister` adds an interceptor "to persist a machine during state changes without needing to stop and start a machine", with `JpaPersistingStateMachineInterceptor`, `MongoDbPersistingStateMachineInterceptor`, `RedisPersistingStateMachineInterceptor`. — [Spring Statemachine reference, sections 22 and 30](https://docs.spring.io/spring-statemachine/docs/current/reference/index.html)
  Limitations stated: machines from one factory share action/guard instances; adapter configuration is fixed at compile time (use builder/`StateMachineModelFactory` for dynamic); session-scoped machines are heavy; blocking APIs deprecated since 3.0 in favour of reactive `ReactiveAction`/`ReactiveGuard`; join guards must be mutually exclusive; a deferred event also accepted by an orthogonal region is consumed; UML model factory does not distinguish machine ids. Requires Java 17+ for 4.0.x (page also contains an outdated JDK 8 statement). — [Spring Statemachine reference](https://docs.spring.io/spring-statemachine/docs/current/reference/index.html)

**Stateless4j 2.6.0**
- Verbatim configuration:
  ```java
  StateMachineConfig<State, Trigger> phoneCallConfig = new StateMachineConfig<>();
  phoneCallConfig.configure(State.OffHook).permit(Trigger.CallDialed, State.Ringing);
  phoneCallConfig.configure(State.Connected)
          .onEntry(this::startCallTimer).onExit(this::stopCallTimer)
          .permit(Trigger.LeftMessage, State.OffHook)
          .permit(Trigger.PlacedOnHold, State.OnHold);
  phoneCall.configure(State.OnHold).substateOf(State.Connected)
          .permit(Trigger.TakenOffHold, State.Connected);
  StateMachine<State, Trigger> phoneCall = new StateMachine<>(State.OffHook, phoneCallConfig);
  phoneCall.fire(Trigger.CallDialed);
  ```
  Full `StateConfiguration` surface (from source): `permit(trigger, dest[, action])` — "Accept the specified trigger and transition to the destination state."; `permitIf(trigger, dest, guard[, action])`; `permitIfElseIgnore(...)`; `permitInternal(trigger, action)` — "Accept the specified trigger, execute action and stay in state." (no exit/entry); `permitInternalIf`; `permitReentry(trigger[, action])` runs exit+entry without changing state, `permitReentryIf`; `ignore(trigger)`, `ignoreIf(trigger, guard)`; `onEntry(action)` — "Specify an action that will execute when transitioning into the configured state.", `onEntryFrom(trigger, action)` incl. typed `TriggerWithParameters1/2/3`; `onExit(action)`; `substateOf(superstate)` — "Sets the superstate that the configured state is a substate of." (substates inherit transitions); `permitDynamic(trigger, destinationSelector[, action])` and `permitDynamicIf(...)` compute the destination at runtime, also from typed trigger arguments. — [stateless4j StateConfiguration.java](https://github.com/stateless4j/stateless4j/blob/master/src/main/java/com/github/oxo42/stateless4j/StateConfiguration.java)
  `isInState(Connected)` is true while in substate `OnHold`; entry/exit handlers may take a `Transition` (trigger, source, destination); moving between a state and its substate does not re-run the parent's entry/exit; a transition action runs only if the transition is taken (between exit and entry); guard clauses, parameterised triggers and reentrant states are listed as supported; "Parallel states are not supported". Maven `com.github.stateless4j:stateless4j:2.6.0`. — [stateless4j README](https://github.com/stateless4j/stateless4j)

**XState v5 (statechart concepts)**
- Transition = `'feedback.good': { target: 'thanks' }`; "If the transition is enabled (no `guard` or its `guard` evaluates to `true`), select it."; deepest active state checked first, then parents; "Eventless (always) transitions are transitions without events."; "Delayed (after) transitions are transitions that are enabled after a specified duration."; targetless self-transitions keep child states; `reenter: true` re-runs exit/entry; wildcard `'*'` "has the least priority" and partial wildcards only as suffix after a dot. — [XState: Transitions](https://stately.ai/docs/transitions)
- "A **guard** is a condition function that the machine checks when it goes through an event."; "Guards should be pure, synchronous functions that return either `true` or `false`."; named guards (`guard: 'isValid'` with implementation in `setup({ guards })`), guard objects with `params`, inline guards discouraged because serialized guards are more reusable and visualizable; guarded transition arrays tested in order with an unguarded default:
  ```ts
  'feedback.provide': [
    { guard: 'sentimentGood', target: 'thanks' },
    { guard: 'sentimentBad', target: 'form' },
    { target: 'form' }, // default
  ],
  ```
  higher-order `and([...])`, `or([...])`, `not(...)`; `stateIn(stateValue)` in-state guards "match the state of the entire machine, not the state node". — [XState: Guards](https://stately.ai/docs/guards)
- "A parent state is a state that can contain more states, also known as child states."; "A parallel state is a state where all of its child states, also known as regions, are active simultaneously."; final states; "Statecharts extend traditional finite state machines to model more complex logic." adding hierarchy, concurrency, communication; "Using state machines makes it easier to find impossible states and spot undesirable transitions." — [XState: State machines and statecharts](https://stately.ai/docs/state-machines-and-statecharts)

### Inferences (ObjectFlow notes)
- **[BIG] Status type → declared state machine.** ObjectFlow's status type already has states with persistence values and colours; adding a `transitions` block (`from DRAFT on submit [guard] -> SUBMITTED`) turns the convention "one service method per transition" into data. Concrete gains: (1) the generator can derive the service method skeleton *and* the precondition "status must be in {sources}" for every transition, (2) UI can enumerate enabled transitions for the current status (Stateless4j `canFire`/permitted triggers), (3) the model can be rendered (DOT/PlantUML) and tested for unreachable or dead-end states, (4) the test DSL can assert status paths.
- **[SMALL] Guard ≈ precondition, action ≈ service-method body.** XState's split "guard must be pure and synchronous" vs "action has effects" is the same distinction ObjectFlow already draws between preconditions (user-correctable) and the method body; guarded transition arrays with a default correspond to a `validation` block feeding a choice.
- **[SMALL] Entry/exit actions per state** are a new place for logic that today would be duplicated in every transition method (e.g. "on entering CLOSED, stamp closedAt").
- **[SMALL] Hierarchical states** (substateOf) express "OnHold is still Connected": useful for status types where many sub-statuses share transitions (all `IN_PROGRESS.*` can be cancelled). Parallel regions are rarely needed for business entity status and are the feature most libraries find hardest (Stateless4j does not support them; Spring Statemachine has caveats); a DSL can skip them initially.
- **[SMALL] Delayed (`after`) transitions** are the state-machine form of deadlines (Q1/Q3): "if in AWAITING_PAYMENT for 14 days → EXPIRED" — only meaningful if the runtime has persisted timers.
- Comparison summary, declared transitions vs one method per transition: method-per-transition keeps logic local and needs no runtime, but the legal-transition set exists only implicitly in preconditions and cannot be enumerated or verified; a declared machine makes the set explicit and derivable, at the cost of a second place where behaviour is described (XState's "serialized guards are visualizable" is precisely this trade-off).

- Additional inference from the full API: Stateless4j's transition kinds — external (`permit`), internal (`permitInternal`, no exit/entry), reentry (`permitReentry`, exit+entry), ignore, dynamic destination — are a compact checklist of the transition semantics a DSL `transitions` block should be able to express; Spring Statemachine's `timer`/`timerOnce` show how a timed transition reads when declared on the state rather than as a separate scheduler call. **[SMALL]**

### Gaps
- Stateless4j's DOT-graph export was not confirmed from fetched sources. Spring Statemachine's "Persist" recipe and distributed-machine features were not read.

## Key question 7 — Specification pattern, business rule engines (Drools, Easy Rules) and decision tables (DMN) as declarative rules vs preconditions in code

### Takeaway
Specifications package a predicate as an object (`isSatisfiedBy`) that can be composed (and/or/not), reused for validation, selection (queries) and building-to-order, and — with composites — explained and compared (subsumption, remainder). Rule engines (Drools DRL, Easy Rules) externalize condition→action pairs with priorities; decision tables (DMN) give a tabular form with exact hit policies. Versus preconditions in code, the gain is reuse across contexts (UI check, query filter, explanation) and business-readable rule sets; the loss is indirection and, for engines, hard-to-reason-about control flow.

### Cited Findings

**Specification (Evans & Fowler, 1998)**
- "The central idea of Specification is to separate the statement of how to match a candidate, from the candidate object that it is matched against. As well as its usefulness in selection, it is also valuable for validation and for building to order."; the specification "has a method isSatisfiedBy (anObject) : Boolean"; benefit "decouple the design of requirements, fulfillment, and validation". Implementation strategies: Hard Coded Specification (a Strategy; "requires programming for every new specification"); Parameterized Specification ("allows new specifications to be built without programming, indeed at run time, but you are limited ... by what the programmers have set up", and parameters can make it "too complex to use and difficult to maintain"); Composite Specification ("uses an interpreter [Gang of Four] to cut a very agreeable middle path", programmers provide leaves and combinators, users assemble). Subsumption: `isGeneralizationOf(Specification)` compares specifications so that "satisfying one implies satisfaction of the other"; Partially Satisfied Specification: `remainderUnsatisfiedBy` returns the remaining specification, which can tell the user why the specification was not met. — [Evans & Fowler, Specifications (PDF, text extracted locally)](https://www.martinfowler.com/apsupp/spec.pdf)
- Wikipedia summary: business rules "can be recombined by chaining the business rules together using Boolean logic"; interface `IsSatisfiedBy`, `And`, `AndNot`, `Or`, `OrNot`, `Not`; used to convert ad-hoc search criteria into repository logic; example: invoices go to collection if overdue AND notice sent AND NOT already in collection; cites Evans DDD p. 224. — [Wikipedia: Specification pattern](https://en.wikipedia.org/wiki/Specification_pattern)

**Aggregates and invariants (Vernon, DDD context for where rules live)**
- "An invariant is a business rule that must always be consistent."; rule "Model True Invariants In Consistency Boundaries"; "Limiting the modification of one aggregate instance per transaction may sound overly strict. However, it is a rule of thumb and should be the goal in most cases."; "we cannot correctly reason on aggregate design without applying transactional analysis"; rule "Design Small Aggregates"; consistency across aggregates "achieved with eventual consistency between aggregates". — [Vernon, Effective Aggregate Design Part I (PDF, text extracted locally)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_1.pdf)

**Vernon Part II (relations between aggregates)**
- Rule "Reference Other Aggregates By Identity" — with the acknowledged cost: "Limiting a model to using reference only by identity could make it more difficult to serve clients that assemble and render user interface views. You may have to use multiple repositories in a single use case to populate views."; Rule "Use Eventual Consistency Outside the Boundary" — "referencing multiple aggregates in one request does not give license to cause modification on two or more of them", citing Evans: "Any rule that spans AGGREGATES will not be expected to be up-to-date at all times."; eventual consistency "requires the use of some kind of out-of-band processing capability, such as messaging, timers, or background threads"; four reasons to break the rules: user interface convenience, lack of technical mechanisms, global transactions (legacy two-phase commit policies), query performance (direct references to ease repository queries). — [Vernon, Effective Aggregate Design Part II (PDF, text extracted locally)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf)

**Easy Rules**
- `@Rule(name, description, priority = 1)`; priority is static but "you can override it with a method annotated with `@Priority` annotation" (lower value = higher priority by default); `@Action(order = n)` orders several actions. Composite rules (`easy-rules-support`): `UnitRuleGroup` — "Either all rules are applied or nothing is applied."; `ActivationRuleGroup` — fires the first applicable rule by priority and ignores the rest (XOR); `ConditionalRuleGroup` — the highest-priority rule gates the others; composite rules are not thread-safe. Usage: `rules.register(myUnitRuleGroup); new DefaultRulesEngine().fire(rules, someFacts);`. — [Easy Rules wiki: Defining rules](https://github.com/j-easy/easy-rules/wiki/defining-rules)
- Rules as annotated POJOs (`@Rule(name, description)`, `@Condition` returning boolean with `@Fact("rain")` parameters, `@Action`), fluent `RuleBuilder().name().when(facts -> ...).then(facts -> ...)`, expression rules `new MVELRule().when("rain == true").then("...")` (also SpEL, JEXL), YAML descriptors (`condition: "rain == true"`, `actions: [...]`) loaded via `MVELRuleFactory(new YamlRuleDefinitionReader())`. Status: "As of December 2020, Easy Rules is in maintenance mode", only 4.1.x supported, bug fixes only. — [Easy Rules README](https://github.com/j-easy/easy-rules)

**Drools / Apache KIE**
- drools.org redirects to kie.apache.org; the site links documentation and downloads for version 10.2.0; Apache KIE comprises Drools, OptaPlanner, jBPM, Kogito, SonataFlow and tools; "Apache KIE is an effort undergoing incubation at The Apache Software Foundation (ASF), sponsored by the Apache Incubator." — [Apache KIE](https://kie.apache.org/)
- Drools 10.2 DRL (Apache KIE docs): a DRL file has `package`, `unit`, `import`, optional `declare` and `query`, and `rule` blocks; a rule has optional attributes (`salience`, `enabled`, `no-loop`, `activation-group`, `date-effective`, `date-expires`, `duration`, `timer`, `calendar`, `auto-focus`, `lock-on-active`, `dialect`), then `when` (conditions as OOPath patterns with constraints, e.g. `/persons[ age == 50 ]`, with `and`, `or`, `not`, `exists`, `forall`, `accumulate`, `groupby`) and `then` (`modify`, `update`, `insert`, `insertLogical`, `delete`; `retract` legacy). Rule units are declared with `unit` and implement `RuleUnitData` with typed data sources: `DataStream` (append-only), `DataStore` (add/remove), `SingletonStore`; in rule units `DataStore.add`/`addLogical` replace `insert`. Example lines: `rule "start-up"` … `alerts.add( new Alert("INFO", "System started") );`. — [Apache KIE: Drools language reference 10.2.x](https://kie.apache.org/docs/10.2.x/drools/drools/language-reference/index.html)
- Older material (background only): in a Drools decision table "each row is a rule and each column in that row is either a condition or action for that rule", authored in XLS or CSV; Kogito rule units aggregate rules with a description of the working memory (data sources). — [mastertheboss tutorial](https://mastertheboss.com/bpm/drools/getting-started-with-decision-tables-in-drools/), [Red Hat Developer 2021](https://developers.redhat.com/articles/2021/05/26/rule-based-services-java-and-kogito)

**DMN decision tables** — see Q4 findings for hit policies, FEEL, BKM reuse limits and version binding ([hit policies](https://docs.camunda.io/docs/components/modeler/dmn/decision-table-hit-policy/), [business rule tasks](https://docs.camunda.io/docs/components/modeler/bpmn/business-rule-tasks/)).

### Inferences (ObjectFlow notes)
- **[BIG] Named, composable specifications as a DSL concept.** ObjectFlow preconditions are predicates bound to one service method. Lifting them to a named `specification OverdueInvoice on Invoice { ... }` with and/or/not composition gives the three Evans/Fowler uses at once: (1) precondition (`requires OverdueInvoice`), (2) query filter for SEARCH commands (the same predicate compiled to SQL/JPQL where possible), (3) *explanation*: the "partially satisfied / remainder" idea is precisely what a user-correctable precondition message should carry. Composite specifications also suit a projectional editor because the leaves are typed expressions and the tree is the model.
- **[SMALL] Guards vs preconditions already match Evans' validation vs. technical split**; specifications would only cover the user-facing kind.
- **[SMALL] Decision tables as an expression form.** A DMN-style table (inputs, outputs, hit policy) is a strictly more readable form for "derive discount/priority/approver from several attributes" than nested ifs; the hit policy vocabulary (Unique, First, Any, Collect+SUM) is directly reusable as a DSL enum, and Unique's "several matches → error" is a useful model-time or test-time check. Easy Rules' maintenance status and Drools' incubation status argue for a *table expression* in the DSL rather than embedding an engine.
- **[SMALL] Vernon's rules apply to ObjectFlow's session model.** "One aggregate instance per transaction" is in tension with a GRAPH_OWNER session that edits a graph; the DDD answer is that the graph *is* the aggregate (true invariants inside) and everything else is eventually consistent via events. This is the design argument for domain events (Q1) rather than widening sessions.
- Criticism to carry: rule engines (forward chaining, priorities, agenda) make control flow opaque; DMN's strength is that a table has *no* control flow beyond the hit policy. Easy Rules' composite groups map almost one-to-one onto DMN hit policies (`ActivationRuleGroup` ≈ First/Priority, `UnitRuleGroup` ≈ all-or-nothing, which DMN lacks), and the DRL attribute list (`salience`, `no-loop`, `activation-group`, `date-effective/expires`, `lock-on-active`) is a catalogue of the control knobs a rule system accumulates once rules can fire each other; a DSL table expression should deliberately offer only hit policy and, at most, validity dates.
- **[SMALL] Vernon's "reasons to break the rules" are ObjectFlow's reality.** His first two reasons — UI convenience and "no provision for messaging, timers, or background threads" — describe exactly why a GRAPH_OWNER session edits several entities in one transaction today. Introducing events plus a persisted scheduler removes the second reason; the first stays a legitimate trade-off the DSL should allow explicitly (session = consistency boundary).

### Gaps
- Drools spreadsheet decision tables and DMN support in KIE 10.x were not confirmed (the fetched language-reference excerpt did not cover them). Easy Rules engine parameters (`skipOnFirstAppliedRule`, `rulePriorityThreshold`) and `InferenceRulesEngine` were not on the fetched wiki page.
- Vernon's Part II text is partially garbled in extraction (two-column PDF); the "whose job is it" heuristic for choosing eventual consistency could not be located verbatim and is therefore not cited.

## Key question 8 — Deadlines/timers, retries and idempotency as language-level concerns

### Takeaway
Across the surveyed systems, time (deadlines, persisted timers, due dates), retry policy (backoff, max attempts, non-retryable error classes, overall timeout), and idempotency (idempotency keys, process-id reuse/conflict policies, idempotent consumers) recur as declarative knobs attached to a step, task or request — and all of them are consequences of at-least-once delivery, which every framework here accepts.

### Cited Findings
- **Deadlines scoped to the scheduling instance, cancellable, not stored as events**: Axon `DeadlineManager.schedule(Duration|Instant, name, payload)` + `@DeadlineHandler` in the same aggregate/saga; `cancelAllWithinScope`. — [Axon: Deadline managers](https://docs.axoniq.io/axon-framework-reference/4.11/deadlines/deadline-managers/)
- **Persisted timers that cost nothing while waiting**: "Timers in Temporal are persisted"; "Workers consume no additional resources while waiting"; durations from one second to "several years"; treat duration as a minimum; no sub-second accuracy. — [Temporal: Timers](https://docs.temporal.io/workflow-execution/timers-delays)
- **Due dates on human work**: Camunda user task `dueDate`/`followUpDate` as ISO 8601 with timezone, priority 0–100. — [Camunda 8: User tasks](https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/)
- **Retry policy fields and defaults**: initial interval 1 s, backoff 2.0, max interval 100× initial, unlimited attempts, non-retryable error types matched by name, Schedule-To-Close timeout bounds total retry time; activities retry by default, workflows do not. — [Temporal: Retry policies](https://docs.temporal.io/encyclopedia/retry-policies)
- **Retries with explicit remaining count and incident**: Camunda job `fail` sets remaining retries; zero retries → incident until resolved; back-off supported; activation timeout reassignment does not consume a retry. — [Camunda 8: Job workers](https://docs.camunda.io/docs/components/concepts/job-workers/)
- **Streaming processor retry**: Axon streaming processors retry "at an incremental interval (starting at 1 second, up to max 60 seconds)" and support dead-letter queues. — [Axon: Event processors](https://docs.axoniq.io/axon-framework-reference/4.11/events/event-processors/)
- **Handler-attempt tracking in the publication log**: Spring Modulith counts completion attempts "when moving to `PROCESSING`, so a crash during the listener still leaves the attempt count updated", staleness marks hung publications FAILED, `ResubmissionOptions` filters by attempts/age. — [Spring Modulith: Events](https://docs.spring.io/spring-modulith/reference/events.html)
- **Idempotent consumers are a consequence of outbox**: duplicates possible when the relay crashes after publishing, "consumers must therefore be idempotent, for example by tracking processed message IDs". — [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html); Camunda: job delivery is at-least-once, same job may run twice, second completion rejected `NOT FOUND`. — [Camunda 8: Job workers](https://docs.camunda.io/docs/components/concepts/job-workers/); Temporal: activities "should be idempotent, so retries can be processed without duplicate side effects". — [Temporal: Activities](https://docs.temporal.io/activities); Microsoft: saga steps must "ensure idempotence"; retryable transactions "are idempotent". — [Microsoft: Saga](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)
- **Idempotency keys as an API contract (Stripe)**: client-generated key (UUID v4 recommended, up to 255 chars) in an `Idempotency-Key` header on POST; Stripe "saves the status code and body of the first request made with a given idempotency key after endpoint execution begins. Retries with the same key return the saved response, including `500` errors."; keys pruned after at least 24 hours; "The idempotency layer compares incoming parameters to those of the original request and errors if they're not the same to prevent accidental misuse."; no result saved if validation fails or a concurrent request with the same key is executing. — [Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests)
- **Idempotent process start**: Temporal Workflow Id uniqueness ("at most one Workflow Execution with a given ID running at any point in time"), Reuse Policy (Allow Duplicate / Allow Duplicate Failed Only / Reject Duplicate / Terminate if Running) and Conflict Policy (Fail / Use Existing / Terminate Existing). — [Temporal: Workflow Id](https://docs.temporal.io/workflow-execution/workflowid-runid)

### Inferences (ObjectFlow notes)
- **[BIG] Time as an event source in the language.** Today ObjectFlow has only cron on batch pairs. Three distinct constructs appear across frameworks and would each be a declaration: (a) *deadline on an instance* ("30 days after X unless cancelled by Y" — Axon), (b) *timer step in a process* ("wait until date" — Temporal, BPMN timer), (c) *due/follow-up date on a user task* (Camunda). All need a persisted scheduler (db-scheduler-style single table is the lightweight option named by Axon).
- **[SMALL] Retry policy as a reusable declaration** with exactly the Temporal fields, attachable to batch consumers, event handlers and process steps; plus Camunda's "incident" terminal state and Axon's dead-letter queue as the two places failed work can go. ObjectFlow's exception strategies are the hook.
- **[SMALL] Idempotency key on commands/service methods.** Stripe's semantics (store first result keyed by client key, return stored result on retry, reject mismatched parameters, bounded retention) can be generated for any command marked `idempotent by <key expression>`; for event handlers the equivalent is a processed-message table keyed by event id (idempotent consumer). Temporal's reuse/conflict policies are the vocabulary for "start process P for business key K".
- **[SMALL] Problem classification feeds retries.** ObjectFlow already distinguishes preconditions (user-correctable) from guards (technical). Temporal's "non-retryable error types" and Camunda's "incident" suggest a third axis: *transient* (retry) vs *permanent* (fail/incident) technical problems; this is a natural extension of the existing precondition/guard split.

### Gaps
- No single source compares these concerns across frameworks; the synthesis above is mine. Spring Statemachine's timer-based triggers and Temporal Schedules (cron replacement) were not fetched.
